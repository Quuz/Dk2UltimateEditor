# Исторический WIP этапа 139: оригинальный reader Map

Продолжение завершило проверки и публикацию этапа139; актуальный результат — `NATIVE_MAP_READER_RU.md` / `phase139-validation.json`, пакет118компонентов. Текст ниже сохранён как журнал ранних затруднений и не является текущим статусом.

Публикуемый пакет остаётся на этапе138:117компонентов. Новые исполняемые проверки этапа139 **не завершены**, компонент в пакет не добавлен. Исходные EXE, игровые данные и параллельный редактор не изменялись.

Получены новые Ghidra-материалы для исходных `56D2D0`, `5B3EB0`, `5B3980`, `5B6EA0`. По исходному EXE локально прослежен путь `5B3EB0` → оригинальный MyFile vslot8 (`5B6EA0`) → оригинальный Disc stream vslot4 (`5FFFB0`) → IAT ReadFile `66C1D4`. В последнем звене вызывается адрес внешнего импорта `28CF2A`; IAT не меняется. Native Disc seek `600030` использует IAT `66C1D8`, внешний адрес `28CF42`.

Новая реализация fixture:

- `native_unicorn_mapreader.py`: отдельный CPU backend с root stack_args, защитой всей исходной IAT и файловых vtable; исторический backend не изменён.
- `native_file_api_fixture.py`: объявленные внешние ReadFile/SetFilePointer/InterlockedIncrement для одного памяти-основанного handle. Ни одно тело функции игры или IAT/vtable не заменяется.
- `emulate_native_map_reader.py`: исходный reader `56D2D0`, native MyFile constructor/pushStream; отдельные режимы реального World callback и capture-only для проверки границы чанка/усечённых данных. Путь начинается с позиции12 после внешнего дескриптора Map; полного native outer-dispatcher/World header bootstrap пока нет.

Статическая зацепка требует динамического подтверждения: `5B3EB0` кладёт BOOL равенства фактически прочитанного и запрошенного размера в result, а `56D2D0` проверяет только отрицательность result. Поэтому короткое чтение может не прерывать parser. Возможное использование остатка глобального буфера при усечении payload **пока не подтверждено исполнением**; не переносить эту гипотезу в правила редактора.

Первые два World exploration запуски завершились ошибками неполного fixture. Вначале отсутствовал neutral owner tag8; затем не-solid Terrain на границе вызывал чтение внешнего соседа без bounds check. Подготовлена следующая версия с исходным Terrain1 на solid-периметре, его настоящим loader и полными player-tag указателями; **она ещё не запускалась**. Эти ошибки не являются доказательством краша нормальной игры. Capture-only сценарии также ещё не выполнены.

Продолжение остановлено двумя внешними условиями:

1. Автоматическая проверка эскалированной команды Ghidra не завершилась из-за лимита использования сервиса. Сообщение прямо указывает, что это review failure, а не заключение о небезопасности. Команда не была выполнена; обход проверки не предпринимался.
2. После этого локальный запуск Python не смог создать служебный setup log: Windows error112, «Недостаточно места на диске». Резервный Node REPL также не создал kernel assets по той же причине. Даже проверить свободное место сейчас не удалось; конкретный заполненный том не установлен. Ничего из пользовательских файлов или прежних доказательств не удалялось.

Живых процессов native/Ghidra проверки этапа139 не осталось. Затем получить независимые Ghidra CPU-контроли и недостающие полные диапазоны функций, когда automatic approval review снова доступен.
