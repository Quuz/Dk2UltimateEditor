# AutoSave.kwd: незаполненные области Level и native-сохранение

Этап35,26 октября 2026. Исследованы предоставленные Editor Pro `493200`, converters игры `56C100` и редактора `42BDE0`. Хеши EXE закреплены в `executable-hash-verification.json`. Все raw-смещения ниже относятся к полезной части блокаDF, без56-байтового заголовка секции Level. Проверки выполнялись в памяти, исходные файлы не менялись.

## Что оказалось в неизвестных областях

| Raw DF | Размер | Baseline-имя | Converter обоих EXE | Native writer493200 |
|---|---:|---|---|---|
|1184..138B|520|UnknownHistory|Не копирует в intermediate|Оставляет прежние байты scratch при строках в пределах полей|
|63C1..63C2|2|Unknown63C1|Не копирует в intermediate|Оставляет scratch|
|63CA|1|UniqueCreatureTypeId|Копирует в intermediate64FE|Не присваивает, оставляет scratch в проверенных прогонах|

`UnknownHistory` — сохранённое старое имя, а не установленная структура истории. Writer не получает для этой области объект истории и не вычисляет её содержимое в проверенном пути. При смене начального стека00/A5/FF меняются все520 байт, а при неоднородном шаблоне сохраняется и его порядок. Это относится к конкретному EXE и описанным условиям; историческое предназначение области не установлено.

В converters промежуточный payload начинается по+134, общий размер25991 байт, первые77 DWORD — presence-поля. Два пропущенных диапазона сохраняются из начального intermediate-буфера; FlagsWORD объединяется с прежним значением черезOR. Девять полных прогонов каждого EXE с разными raw-значениями и intermediate seeds сравнивают все25991 байт. Не следует путать «не перенесено этим converter» с доказательством неиспользования во всех версиях и путях игры.

Для raw63CA установлен иной случай: byte действительно переносится обоими converters, хотя проверенный native writer его не заполняет. Игровой смысл baseline-имени UniqueCreatureTypeId этим этапом не подтверждён. При реализации своего сохранения этот байт обязательно сохранять.

## Сборка всего файла и список существ

Полный writer выводит последовательно:12 байт заголовкаDC,36 байт DD,8 байт DF tag/length и25683 байта payload,8 байт DE tag/length, затемN ссылок по72 байта иK DWORD доступных существ. Он записывает:

```text
wholeSectionBytes = 0x6493 + 72*N + 4*K
DE dataBytes      = 72*N + 4*K
```

Внутри generic parser `Section.records[0]` для Level содержит DF payload **вместе** с DE и ссылками. Граница DF определяется последним DWORD заголовка, а не длиной этого record-буфера. Точечная правка DF должна удерживать весь хвост DE без изменений.

Список доступных существ физически состоит из DWORD. Native getter48C030 возвращает ID вAL, writer присваивает только этот байт локальному DWORD и выводит все4 байта. В полных прогонах с ID7/81/255 старшие24 бита сохранились из scratch, в том числе при неоднородном шаблоне. Ранее уже было установлено, что проверенный loader использует low8; теперь объяснён источник старших байтов в native writer. Наше сохранение должно удерживать все4 исходных байта и не считать старшие байты частью ID.

Перед сохранением writer очищает modelFlagsDC bit04 и устанавливает снова, если у какой-либо модели игрока unsigned byte1C>=3 и byte40==0. Остальные биты сохраняются. Назначение этих двух player-полей и игровое имя Level-флага здесь не устанавливаются. Payload byte6404 получает low8(число моделей игроков−2); проверены модели с2 и4 игроками.

## Строковые helpers: count не ограничивает копирование

В writer реально выполняются48CF90 и4AB3B0, а не заменители строковой записи. Они читают сохранённую длину CString и копируют **все** её байты; параметр count служит для дополнения нулями, если строка короче. При слишком длинной строке обрезания нет.

48CF90 расширяет каждый знаковый byte доWORD:80→FF80,FF→FFFF. Это не общая Unicode-конверсия. Прямой редактор формата может работать с UTF-16LE файла; имитацию старого ANSI writer следует отделять от сохранения исходного текста.

Проверен и пограничный случай, который ограничивает вывод о scratch: при синтетической Information длиной1027 байт (1026 `I` и заключительный80) native writer записываетFF80 в первые2 байта raw1184. Последующие присваивания Trigger/TPS восстанавливают два предшествующих WORD, но начало520-байтового диапазона уже изменено. Это изолированная модель в EmulatorHelper; она не доказывает, что реальное окно разрешает такой ввод. Поэтому «область не присваивается» относится к строкам, не выходящим за свои поля, а не ко всем повреждённым моделям.

В отличие от writer, converters используют ограниченные strncpy/wide-strncpy, дополняют послеNUL и принудительно завершают последний byte/WORD строковых полей. Их нормализация не является правилом lossless-сохранения raw строк.

## Корпус, воспроизводимость и применение

Проверены113 Level:112 файлов карт и отдельно AutoSave, все с DF25683. У55 файлов520-байтовая область ненулевая; найдено53 разных буфера. Unknown63C1 ненулевой у112, raw63CA — у89. Эти наблюдения не превращают каждый конкретный исторический буфер в доказанную утечку именно этого EXE.

`level-descriptor-semantics.json` —46-й компонент пакета; API `native_level_descriptor.py` сохраняет raw и отдельно моделирует native-проекции с явным scratch seed. Документация не предлагает заполнять существующие неизвестные области случайными или нулевыми данными. Для создания нового файла нулевая инициализация — явная политика нашего редактора, а не воспроизведение гарантированного native-результата.

38 native-прогонов:14 полных writer (13 со строками в пределах полей и1 с длинной Information),18 полных converters (по9 наEXE),6 отдельных строковых helpers. Побайтово сравнён весь вывод writer, включая заголовки, DE, ссылки и DWORD существ; все14 файлов прошли parse→pack без различий. Выполняются настоящий stack probe4AD490, строковые helpers, setter флагов и getter массивов. CString ownership, получение имени/сообщений, дата и file virtual callback заменены явными fixtures; настоящие файловые/оконные операции не выполнялись.

`audit_level_descriptor.py` / `phase35-validation.json`:2054 граничных случая,1017 точечных пересборок в памяти с сохранением DE,1456 инструкций,23 повторных disassembly и23 диапазона памяти Ghidra совпали с PE.17 входных файлов и2 EXE сохранили хеши. Старый DF25603 поддерживается физическим raw API; native эмуляция этого этапа проверяет только25683.

Отдельный полный поиск displacement-кандидатов не установил новых потребителей Terrain198/224, Traps204, Objects34C. Эти поля, ActionPoint04/08 и другие оставшиеся вопросы не объявлены расшифрованными.
