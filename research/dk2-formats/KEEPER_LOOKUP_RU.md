Продолжение этапа 83 — `KEEPER_ARRAY_RU.md`: нормальная вставка122-байтных Keeper definitions теперь выполнена,включая сортировку и дубликаты. Это уточняет прежнюю границу «порядок после loader не установлен». Дополнительно проверены first/next/previous/index/order lookup. Физический порядок raw и runtime-порядок различаются;автоматическая нормализация файла не вводится.

Этап72, 27 октября2026. Полные getters текущего DX50DD60 и предоставленного старого EXE5027A0 проверены в26 native-сценариях, по13 на профиль. Назначение неизвестного DWORD C8 не установлено. Профили определяются точным SHA из машинной схемы, не названием папки или предполагаемым номером retail-версии.

## Как ищется определение

В обоих EXE worldDWORD1604 указывает на массив122-байтных definitions, worldDWORD160C содержит count, ID расположен в BYTE75 каждой записи. Native old world vslot110 по65F31C действительно содержит5027A0; ранее найденные5027DB/5028CB не следует автоматически считать началами getter: это инструкции внутри других тел.

Getter использует:

```text
key = argument & 255
index = min(key - 1, count - 1)
пока index >= 0:
    если ID[index] == key: вернуть адрес записи
    если ID[index] < key: вернуть NULL
    index -= 1
вернуть NULL
```

Проверены пустота, физический ID0, первое/среднее/последнее совпадение, пропущенные значения, старшие биты аргумента, дубликаты, несортированный массив, единственный ID255. Важные случаи:

- ID0 не находится даже при наличии такой строки массива.
- Для `[0,1,2]` поиск ID1 начинает с index0 и прекращается на ID0. Физически существующая строка1 оказывается скрыта этим алгоритмом.
- Для `[1,7,3]` поиск7 начинает с последнего3 и прекращается, хотя7 существует выше.
- Для `[1,3,7]` поиск7 успешно возвращает третью строку: разреженность ID выше count сама по себе не запрещена getter.
- Для `[1,1,3]` поиск1 возвращает первую строку, потому что стартует с index0. Универсальное правило «последний дубликат» неверно.
- Аргумент12340003 означает3, а100hex означает0.

Это правила массива в памяти игры. Нормальная вставка/сортировка загрузчиком исследуется отдельно; искусственный несортированный стенд не доказывает, что обычный loader оставляет такой порядок. Физический порядок raw-файла нельзя автоматически сортировать, перенумеровывать или удалять на основании результата lookup. В независимом редакторе это диагностическая информация.

## Что добавлено для C8

Предыдущий проход этапа64 работал внутри размеченных функций и не прослеживал полноценные direct-callee аргументы. Новый ограниченный поиск берёт seeds во всей линейно декодированной PE.text, проверяет ECX и первые восемь потенциальных stack arguments, переносы через ESP/EBP и до трёх уровней прямых вызовов. Общая политика чтения учитывает TEST/CMP memory operands.

| Профиль | Корни | Root states | Callee summaries | Зацепки известных полей | Зацепки C8 |
|---|---:|---:|---:|---:|---:|
|DX|45|835|9|27|0|
|Старый EXE|48|711|5|27|0|

Точный getter является установленным источником definition; совпадающий virtual slot110 у произвольного другого класса остаётся нетипизированной зацепкой. Стековые позиции поиска — потенциальные аргументы, а не удостоверенные сигнатуры. Известные Recharge/ManaCost/ShotId служат контрольными чтениями, но наличие контроля не превращает поиск в полный анализ игры.

Ни один лимит числа состояний/аргументных контекстов в этих проходах не исчерпан. При этом остаются ограничения глубины, динамических индексов, indirect calls/returns, неизвестных helper identities, heap spills и вычисляемых переходов. Исчезновение alias или остановка на indirect branch тоже ограничивают охват. Поэтому ноль кандидатов C8 не является доказательством глобального неиспользования и не увеличивает число расшифрованных игровых назначений.

У старого loader отдельно сверён16-байтный фрагмент4EC919: presence18 разрешает копирование DWORD intermediate140 в definition3A. Это подтверждает внутреннее смещение для поиска; новый этап не исполняет полный старый loader и не выдаёт этот фрагмент за новый полный raw→runtime pipeline. Текущий rawC8→mid140→def3A и writer уже закреплены этапами26/44.

## Проверки и артефакты

Все26 эмуляций сохраняют native EAX до наблюдателя и проверяют точный адрес/null. Сравниваются неизменными весь5888-байтный world fixture и весь заданный массив122-байтных строк. Определения различаются в том числе содержимым DWORD3A; это проверка getter, не тест всех игровых эффектов C8. Нативные инструкции и вызовы не подменяются; providers нет.

После выполнения два полных тела getter повторно считаны из Ghidra и сопоставлены с исходными PE. Отдельно сверены native old world-vslots и помеченный scalar-loader fragment. Исторические SHA82 исходных файлов и четырёх EXE совпали. Новых raw-пересборок нет: прежние проверки Keeper остаются самостоятельными доказательствами и не считаются повторно.

`keeper-lookup-review.json` вложен в `keeper-pipeline-semantics.json.phase72_lookup_review`; пакет сохраняет67 компонентов. `native_keeper_lookup.py:lookup_index` возвращает индекс по явно заданной последовательности runtime ID и не изменяет исходные записи. Итоги: `phase72-validation.json`. Воспроизведение: `emulate_keeper_lookup.py`, `prepare_keeper_lookup_primary.py`, `ghidra_probe.py phase72-primary-queries.json`, `prepare_keeper_pointer_search.py`, `scan_keeper_pointer_arguments.py`, `scan_old_keeper_pointer_arguments.py`, `build_keeper_lookup_review.py`, `build_format_package.py`, `audit_keeper_lookup_review.py`.
