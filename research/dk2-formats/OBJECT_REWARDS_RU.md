Этап 89, 28 октября 2026. Профиль — тот же предоставленный `DKII-DX.exe` с SHA-256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a`. Схема `object-reward-semantics.json` встроена в `sacrifice-semantics.json.phase89_object_rewards`. Правила сопоставления рецептов этапа88 остаются прежними; здесь проверена следующая часть цепочки — создание награды.

Выполнены 25 разных сценариев: девять factory и 16 храмового dispatcher. Каждый имеет два одинаково подготовленных native-повтора для чтения 393 байт через восемь YMM-регистров: всего 50 завершений. Получены полные образы 13 успешно созданных объектов. Остальные сценарии подтверждают отсутствие создания; их снимки памяти не выдаются за объекты. Это не атомарные дампы живого процесса и не игровая сессия.

## Что действительно исполнялось

Исходные `4B7A90`, allocator `554B30`, конструктор `4B7190`, initializer `49B1C0`, регистрация tag/карты/владельца, movement и методы настоящих World/Object vtable выполняются без изменения инструкций и таблиц. Определение объекта — явно подготовленные 285 байт, экземпляр — 393 байта. Pool округляет запрос до 396 и учитывает ещё12 байт заголовка: 408 байт. Проверены свободный блок512, точный408, недостаточный404, пустой pool, gate0 и ID0.

Независимо проверяются весь World, владелец, карта, массивы tag/alive, списки free/used, счётчики pool, исходные definitions/аргументы и охранные байты вокруг объекта. У нового экземпляра отдельно проверены исходная CObject vtable, ID, тип2, definition pointer, HP1000, friction65535, speed1234h, owner и позиция. Полный образ не означает расшифровки остальных байтов: они сохраняются opaque, в том числе при разных исходных заполнениях памяти.

Две композиции проходят всю цепочку **raw16 → `51DB30` → `50F7E0` → `4F1600` → `4F1660` → `4F1780` → настоящая factory**. Промежуточный рецепт и output награды также сравниваются побайтово. Синтетический driver только соединяет исходные функции и наблюдает результат.

## ID, владелец и позиция награды

У reward type2 factory использует младший BYTE значения. DWORD `00000011` и `FEDCBA11` создают один и тот же Object ID17: все393 байта совпали. Raw-цепочки с обоими значениями дали те же образы. Старшие биты нельзя удалять при сохранении файла только потому, что этот consumer их не использует.

Владелец берётся из отдельного global WORD6F2548. В проверке он равен7, тогда как owner комнаты равен8; объект действительно привязан к7. Это доказывает отдельный источник владельца, но не назначает всем версиям универсальное числовое значение «нейтрального игрока».

`4E4D90` выбирает клетку комнаты5/6. Переданная caller позиция9.5/10.5 не используется для этого выбора. Для объекта исходный Z0 затем ограничивается высотой пола4096 в `4B5020`. Проверен настоящий путь RTTI CThing→CMovingThing; native RTTI-метаданные подтверждают наследование CObject.

После отказа factory из-за gate0, отсутствующего/малого pool или ID0 история жертв уже очищена. В проверенной цепочке награда не появляется; отложенная выдача или повторная попытка этим кодом не установлены.

## Золото — отдельная награда

Reward type3 вызывает `4BA420`. В сценарии без доступных Treasury комнат положительная награда при обычных ненулевых координатах создаёт Object ID1 через настоящий `4B7A90`, затем `49C760` записывает сумму по instance+14A. Проверены суммы1,1000,5000. Для Object IDs1/2 этот helper также меняет scale по +48/+4C и обнуляет +58/+5C:

| Сумма | Содержимое +14A | Scale +48/+4C |
|---:|---:|---:|
| 1 | 1 | 2048 |
| 1000 | 1000 | 2548 |
| 5000 | 5000 | 4548 |

Ниже5000 вычисление использует исходные double−0.5 по66D428 и `634F30` с округлением к нулю: для положительной суммы результат равен2048+floor(amount/2). От5000 scale фиксирован4548; это ограничение масштаба, не доказанный предел суммы золота.

Выдать type2/Object ID1 и выдать type3/Gold5000 — разные операции. В первом случае созданный объект в этом fixture содержит0 по+14A; во втором —5000.

При положительном запросе и нулевой координате клетки `4BA420` добавляет сумму непосредственно к ownerDWORD7E. Проверка y0 подтвердила прибавление5000 владельцу комнаты8 без выделения объекта. Это отдельная ветка, её нельзя распространять на обычные координаты. Amount0 ничего не создаёт; FFFFFFFF идёт как отрицательный запрос в путь изъятия и ничего не даёт при пустом списке Treasury. Заполнение/изъятие настоящего Treasury содержимого остаётся непроверенным.

При gate0 обычная награда5000 не создаёт мешок и не переносится в прямой баланс. История жертв к этому моменту очищена. Уведомления, подбор мешка, изображение и последующие игровые тики не проверялись.

## Внешние зависимости эмулятора

Сохраняются явные внешние providers: graphics возвращает NULL с пятью аргументами и RET20, sound — фиксированный результат с четырьмя аргументами и RET16. Оригинальные игровые функции при этом не заменяются.

Путь ниже пола вызывает native RTTI, который обращается к импортированной `KERNEL32!IsBadReadPtr`. В данном PE IAT66C1B8 содержит связанный адрес28CFA4 вне образа игры. В этом адресе подготовлен отдельный OS-import provider: размер0 допустим, переполнение адреса запрещено, весь диапазон должен попадать в читаемую PE-секцию или подготовленную область данных. Это модель доступной памяти эмулятора, не вызов Windows API в живой игре. Каждый успешный сценарий ниже пола вызвал одну принятую проверку; счётчик недопустимых проверок остался0. `__RTDynamicCast` и его игровые caller выполнялись исходными.

При подготовке были сохранены отдельные диагностики: неверное число аргументов внешнего GFX provider, ошибочные ожидаемые счётчики, отсутствующие import/World-global. Они исправлены по первичным инструкциям и не включаются в50 итоговых повторов. Попытка ограниченной Java-трассы не исполнилась: inline scripts отключены в текущем MCP. Это не мешало завершить проверку через доступную эмуляцию; Ghidra не перезапускалась.
