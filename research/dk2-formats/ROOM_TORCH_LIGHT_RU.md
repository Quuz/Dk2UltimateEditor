# Rooms: путь интенсивности факела до записи света

Этап 123, 29 октября 2026. **Байт `TorchIntensity` переводится в параметр записи света по формуле `N / 128`.** Это подтверждено полным исполнением двух оригинальных обработчиков `599960` и `599C60`, включая настоящий allocator и постановку в очередь.

| Raw BYTE | Полученный float |
|---:|---:|
| 0 | 0 |
| 1 | 0,0078125 |
| 64 | 0,5 |
| 128 | 1,0 |
| 255 | 1,9921875 |

Это точный параметр на стадии подготовки света. Он не объявляется измеренным процентом итоговой яркости пикселя: итоговое затухание, смешивание и вывод кадра здесь не исполнялись.

Схема — `room-torch-light-semantics.json`, компонент пакета `room_torch_light_semantics`. Физическое поле по-прежнему u8 `Rooms+36E`; соседний `36F` сохраняется отдельно как opaque, согласно этапу122. Для физических полей используйте `effective_catalogue_layouts`.

## Первичный путь от комнаты

`439B90` получает Room-tag из младших12бит WORD `cell+2`. `4559B0` использует его для поиска живой сущности в реестре `6EE540`. В ветке существующей комнаты код получает definition через `RoomEntity+19` и читает BYTE `definition+45E`.

Этот байт передаётся в создание источника света через слот `A4` CBridge. Начало настоящей vtable — `66CC94`: его сохраняет конструктор `43A740`, а слот содержит `4397E0`. Эта функция выделяет326байт, вызывает исходный конструктор `43A0D0` и initializer `43A1E0`. Последний сохраняет младшие8бит пятого из семи аргументов в **`CLight+145`**. Конструктор по умолчанию задаёт там128, но initializer затем записывает переданное значение.

Эта часть цепочки подтверждена инструкциями и таблицами, **не новым исполнением размещения факела на стене**. Новый CPU-стенд начинается с явно подготовленного CLight. Полной исполненной цепочки rawRoom→loader→placement→CLight этим этапом не добавлено.

Ранняя попытка вычислить начало таблицы от отдельной ссылки дала внутренний адрес `66CCA0` и неверный target `43A910`. Проверка конструктора отвергла её: `43A910` — getter. Эта зацепка не используется как доказательство создания света.

## Полное исполнение двух обработчиков

Оба обработчика читают интенсивность как **unsigned BYTE**, умножают её на оригинальную float-константу `670524 = 1/128` и записывают результат в два поля `30h/34h` записи размером56байт.

Исполняются настоящие `57CEB0 → 57CD30` для выделения памяти, `599BD0` для режимных флагов и `571A90/571AB0` для очередей. Первая функция помещает запись в очередь `context+34`, вторая — `context+38`, через глобальный указатель `760B80`.

Нулевая интенсивность сама по себе не запрещает создание записи: при подходящих kind2 и ненулевом radius запись всё равно выделяется и ставится в очередь, с обоими float равными0. Радиус0 и другой kind в проверенных ветках пропускают выделение. Это разные условия; автоматически превращать intensity0 в удаление факела на основании этого результата нельзя.

В подготовленной сцене нет mesh-ресурса, а `CLight+12E=0`. Подвижная ветка с двумя позициями, полный кадр и CPU/GPU-растеризация не исполнялись. Для allocator подготовлен настоящий свободный блок128байт из класса28; выбранный путь запросил56байт. Исходный allocator, функции и нативные vtable не заменяются; внешних API-заглушек нет.
