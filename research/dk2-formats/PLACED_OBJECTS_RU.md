# Things: размещённые Objects, этап30

Подтверждено по предоставленным `DKII-DX.exe` и `DK2 Editor pro.exe`. Это записи размещений `0xC2` внутри Things, отдельно от определений каталога Objects. Полные SHA-256, assembly и границы проверки — в `placed-object-semantics.json` и `phase30-validation.json`. Исходные игровые файлы не изменены.

## Физическая запись

Оболочка — `u32 194, u32 24`, затем24 байта payload. Смещения таблицы относятся к payload.

| Смещение | Размер | Подтверждённое использование |
|---|---:|---|
| 00 | 4 | X клетки, сохранять все32 бита |
| 04 | 4 | Y клетки, сохранять все32 бита |
| 08 | 4 | Третий DWORD позиции, назначение не установлено; для размещения здесь Z=0 |
| 0C | 4 | Перегруженный селектор: младший байт содержимого книги; полный DWORD для старого ObjectId7 |
| 10 | 4 | Прибавляемое количество золота при соответствующем флаге определения |
| 14 | 2 | TriggerId; скопирован в intermediate, этот game callback его не передаёт создателю |
| 16 | 1 | ObjectId |
| 17 | 1 | PlayerId |

Конвертер игры `56F730` переносит запись в48-байтовый intermediate: XYZ→18/1C/20, selector→24, money→28, trigger→2C, object/player→2E/2F. Шесть DWORD признаков присутствия0..14 получают1. Поэтому размер поля0C нельзя уменьшать до byte из-за одного потребителя.

Callback `520BB0` сначала вызывает world checksum `5108C0(mid,48)`. Таким образом, неизвестный DWORD08 и неиспользованные здесь поля всё равно поступают в путь контрольной суммы. Для создания используются `X=low32((rawX<<12)+800h)`, аналогичноY и **Z=0**. Владелец передаётся как WORD из структуры игрока, а не просто как исходный byte PlayerId; допустимый диапазон PlayerId этим выражением не установлен.

## Старый ObjectId7 и специальные предметы

Raw ObjectId28 пропускается: callback после checksum возвращает1 без вызова создателя. В самостоятельном Objects.kwd ID28 называется `Portal Gem`. Это вывод об одном загрузчике, а не утверждение, что Portal Gem не используется нигде в игре.

Для raw ObjectId7 callback сначала меняет ID по **полному DWORD0C**, независимо от флагов будущего определения:

| DWORD0C | Создаваемый ObjectId | Имя в предоставленном Objects.kwd |
|---:|---:|---|
| 2 | 117 | Special [ Increase Level ] |
| 6 | 118 | Special [ Reveal Map ] |
| 7 | 119 | Special [ Make Safe ] |
| 8 | 120 | Special [ Destroy Walls ] |
| 10 | 121 | Special [ Increase Gold ] |
| 11 | 122 | Special [ Mana Boost ] |
| 12 | 123 | Special [ Stun Imps ] |
| 13 | 124 | Special [ Receive Imps ] |
| 14 | 125 | Special [ Make Happy ] |
| 15 | 126 | Special [ Make Unhappy ] |
| 16 | 127 | Special [ Kill Creatures ] |
| 17 | 129 | Special [ Locate Hidden Land ] |
| 18 | 128 | Special [ Heal All ] |

Для остальных значений, включая3/4/5/9,258 иFFFFFFFF, остаётся7. Для raw ID!=7 этой замены нет. В самостоятельном каталоге ID7 называется `Special [ <not used> ]`, имеет Special bit4 и не имеет Book bit8. Baseline имя `KeeperSpellId` не означает, что все эти значения — ссылки на KeeperSpells: здесь поле хранит также старый селектор специальных предметов.

Таблицы переходов `520D64`, `520DA8`, `520DC0` прочитаны непосредственно из PE, сохранены целиком и сверены с исходными инструкциями. Имена из каталога приведены как справочник одного файла; наличие целевого определения в реальном Globals нужно проверять отдельно.

## Данные созданного объекта

После успешного `4B7A90` читаются флаги **возвращённого** определения (`instance12D→definitionF4`), соответствующие raw Objects+344. Приоритет:

1. **Gold bit40**: вызвать `49C760(raw DWORD10)`.
2. Иначе **Spell Book bit08**: `instance14A DWORD=4`, `instance14E byte=low8(raw DWORD0C)`.
3. Иначе **Crate bit10**: проверить **actual instance ObjectId12C**.
4. Иначе оставить существующие поля14A/14E.

Совместные flags58 выбирают Gold; flags18 выбирают Book. Для ящика:

| Actual ObjectId | DWORD14A | BYTE14E |
|---|---:|---:|
| 5,36..44,92,138 | 1, тип ловушки | actual ObjectId |
| 52..57 | 0, тип двери | actual ObjectId |
| Остальные | прежнее значение | прежнее значение |

В14E здесь записывается ID **объекта ящика**, не DoorId/TrapId одноимённого каталога. Значения типов0/1 также согласуются с ранее проверенным manufacture helper5066E0; соответствие ящика определению двери/ловушки относится к отдельному пути.

`49C760` прибавляет raw количество к текущему DWORD14A по модулю2³². Если у суммы установлен знаковый бит, записывает0; иначе записывает сумму. Примеры:55+FFFFFFFF→54;0+FFFFFFFF→0;7FFFFFFF+1→0. Это не насыщение на INT_MAX и не безусловное присваивание. Начальное количество зависит от создателя и здесь не объявляется всегда нулевым.

У actual ID1/2 helper также меняет поля48/4C/58/5C, использует порог5000 и x87. Эти инструкции сохранены, но графические единицы и результат дробной ветви этим этапом не проверены. В эмуляциях Gold используется ID3, оригинальная целочисленная часть helper выполняется полностью.

## Что читает и сохраняет Editor Pro

Загрузка `4916B0` использует setter `4206A0`: если **не Gold** и есть **Book или Crate**, сохраняет low8(DWORD0C) в model19. Иначе прежний model19 остаётся. Setter `420730` сохраняет полный money DWORD в model1C только при **Gold или Special**.

Далее для определения ID7 редактор получает селектор через `420610`: только **не Gold и Book** возвращает model19, иначеAL0. Результат явно маскируетсяFF перед таблицей переходов. Поэтому при специально заданном Book bit8 raw ID7/selector258 редактор меняет ID на117, а игра оставляет7. При **штатных флагах предоставленного определения ID7** Book отсутствует и редактор этой замены не делает. Не следует переносить синтетический пример на любую карту без проверки её определений.

Писатель `4947C0`, payload-фрагмент `494DEA..494E73`:

| Поле | Запись Editor Pro |
|---|---|
| DWORD08 | 0 |
| DWORD0C | zero-extended model19 при неGold+Book, иначе0 |
| DWORD10 | полный model1C при Gold или Special, иначе0 |
| ObjectId | definition168 для текущего model ID |
| TriggerId | low16 виртуального getter |
| PlayerId | byte1C owner model |

В `420670` перед `MOV AL` есть `XOR EAX,EAX`: старшие24 бита здесь действительно нулевые. Декомпилятор показал неопределённую часть возвращаемого значения, но это не соответствует реальным инструкциям писателя.

Один лишь Crate bit10 позволяет setter сохранить байт selector в модели, однако writer getter его не возвращает. Таким образом, native save может занулить raw0C. Это поведение оригинального редактора; независимый редактор должен по умолчанию сохранять все32 исходных бита. Полная проекция load→save также требует определения уже **после** изменения model ID, поэтому API не выдаёт одну упрощённую формулу для всей карты.

## Проверка и API

`native_placed_objects.py` разделяет `record_view`/`patch_raw`, `game_created_id`, `game_payload`, `gold_add`, `editor_load_projection` и `editor_getters`. Patch принимает полную32-байтовую оболочку+payload; сохраняет все байты вне выбранного диапазона. API не создаёт сущности мира и не гарантирует наличие ссылочных определений.

`phase30-validation.json`:99 native-прогонов —74 полных game callbacks,12 полных editor load callbacks,10 writer payload fragments,3 converters;1586 граничных проверок и96 точечных пересборок двух настоящих Things в памяти. В native-прогонах создатели/checksum/I/O и некоторые поставщики значений заменены явными fixtures; настоящие getter/setter/lookup/vector и integer Gold helper выполняются. Все24 записанных байта payload проверены шестью DWORD. Проверены562 инструкции и12 повторных полных assembly без изменений. Сохранились SHA-25617 исходных данных и2 EXE.

В109 файлах карт —1805 Objects, из них12 raw ID28. DWORD08 всегда0. Raw ID7 не встречается, поэтому переходов7→117..129 в этом корпусе нет; это не отменяет подтверждённый кодом и эмуляцией путь.12 ненулевых selector распределены между ID4 (9 записей) и ID102 (3 записи). Поле money ненулевое у652 записей, значения50..32000. Все исходные биты сохраняются независимо от их использования. Назначение DWORD08 за пределами проверенного пути и использование TriggerId другими подсистемами остаются открытыми.

Ранний дополнительный fixture позиции ошибочно перекрыл region checksum вместо region readout. Он сохранён как `phase30-superseded-position-fixture-overlap.json`, исключён из99 прогонов. Исправленные fixtures не пересекаются; проверка непересечения регионов добавлена в сборщик.

Воспроизведение: `emulate_placed_objects.py`, `build_placed_objects.py`, `build_format_package.py`, `audit_placed_objects.py`. Для повторного аудита сохранённых доказательств живая Ghidra не требуется.
