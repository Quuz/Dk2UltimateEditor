# KeeperSpells DB: порядок игровой панели и выбор заклинания, этап 84

Байт **raw `DB`** управляет перебором обычной игровой панели заклинаний. Подтверждена цепочка raw406 → intermediate526 → definition122 → методы UI → обработчик выбора → локальная очередь Session. Историческое имя поля `OrderInEditor` сохранено как alias; новая семантика опирается на оригинальные инструкции игры.

Выполнены 28 независимых сценариев, внутри них 329 native-цепочек инициализации/конвертации/вставки raw, 420 вызовов селектора, 28 проверок вкладки и 28 вызовов обработчика выбора. Получено 20 новых записей настоящей локальной очереди. Исходные игровые файлы не перезаписывались.

Схема — `keeper-ui-semantics.json`, включена в `keeper-pipeline-semantics.json.phase84_ui_order`. Итоги — `phase84-validation.json`. Общее исследование и назначение C8 остаются открытыми.

## Как строится обычный список

Цепочка поля: BYTE raw `DB` → BYTE intermediate `153` → BYTE definition `6C`. ID остаётся отдельным BYTE raw `EE` / definition `75`.

Native UI `4115E0`, `416E20`, `411140` используют World из `UI+53`. В оригинальных `402D00/4039A0` туда записывается `*( *(UI+4) +14 )`, то есть World текущего Session. В стенде использованы оригинальные World-vslots: `114=508F10` возвращает число определений, `120=50DE00` находит ID по порядку, `260=508C40` возвращает игрока по внутреннему тегу.

Панель перебирает **порядки от 1 до числа определений включительно**. Для каждого порядка `v120` возвращает ID первой подходящей runtime-строки. Отсутствующий порядок даёт 0. Далее настоящий `4BAFA0` ищет состояние этого ID в массиве игрока: записи по 17 байт, ID по `+0`, DWORD состояния по `+1`; число и указатель находятся по player `6E/72`.

Обычный элемент включается в список, если:

- найденное DWORD-состояние **не равно 1**; отсутствующее состояние метод трактует как 1;
- ID не равен **5** и **14**.

Проверены состояния 0, 2, `100h`, `FFFFFFFF`: все проходят числовое условие `!=1`. Полный enum состояний, возможность исследования и возможность применения заклинания из этого не выводятся.

Исключение 5/14 сделано по ID. В standalone ID 5 назван Summon Horny, в исследованных Qz-картах — Turncoat; переименование не отменяет фильтр. Другие источники активации этих ID и кнопки вызванных объектов данным опытом не исследованы.

DB 0 и DB выше числа определений не опрашиваются. Поэтому разреженные ID сами по себе допустимы, но служебный порядок должен попадать в реально перебираемый диапазон, чтобы строка участвовала в этом списке. Эти ограничения описывают runtime; сериализатор сохраняет исходный BYTE и не исправляет его молча.

## Что происходит в Qz и Qz2

В `Battle for the Sun QzGlobals.kld` и `Battle for the Sun Qz2Globals.kld` одновременно заданы:

| ID | Имя в карте | DB |
|---:|---|---:|
| 9 | Raise Dead | 9 |
| 13 | Create Gold | 9 |

Порядок 10 отсутствует. В предыдущем этапе было доказано только поведение локального lookup. Теперь полные исходные каталоги прошли настоящие raw-конвертацию и вставку, после чего выполнены UI-методы и обработчик выбора.

При подготовленных состояниях игрока 0 обычный список Qz/Qz2 равен:

```text
4, 6, 2, 10, 1, 3, 8, 7, 9, 11
```

Create Gold, ID 13, отсутствует. Девятая позиция выбирает Raise Dead, ID 9, и в Session появляется действие выбора с этим ID. В standalone-каталоге девятая позиция выбирает ID 13; название ID 9 там Inferno, а его порядок 10.

Сильный контроль: если только ID 13 имеет состояние 0, а остальные — 1, standalone даёт список `[13]` и включает вкладку заклинаний. Та же подготовка игрока с исходным Qz2 даёт пустой список, отключённую вкладку и отсутствие нового действия выбора. `416E20` действительно записывает DWORD `button+61` в 0 или 1 для подготовленной кнопки типа 2.

Перестановка физических строк Qz2 не устранила эффект: native-вставка снова упорядочила их по ID. Два изменения только в памяти эмулятора дали разные корректные размещения:

- DB у Create Gold 9→10: Raise Dead остаётся девятым, Create Gold становится десятым;
- DB у Raise Dead 9→10: Create Gold становится девятым, Raise Dead — десятым.

Каждый вариант также проверен точечной пересборкой целого контейнера для обоих файлов. Менялся ровно один байт DB, остальные байты совпали. **Ни один вариант в игровые карты не сохранён.** Не установлено, кто создал совпадение порядка, было ли оно намеренным и участвовал ли оригинальный редактор.

## Позиция, возврат и некорректный нулевой индекс

`4115E0(ordinal,outByte,UI)` выбирает 1-й, 2-й и последующие подходящие элементы. При обычной неудаче возвращает 0 и оставляет выходной байт прежним. Номера позиций считаются после фильтрации.

Особенность инструкций: сравнение накопленного числа с ordinal стоит после фильтра, но за пределами его условного блока. Поэтому ordinal 0 не имеет универсального смысла «не найдено». В сценарии, где все состояния равны 1, он вернул успех и ID 4 из первой отфильтрованной строки. Это проверка края native API; не утверждается, что обычная мышь посылает такой индекс.

В обработчике `411140` позиция вычисляется как входной ordinal плюс `UI.E5 * UI.B5`. В стенде первая величина 0, вторая 4. Вызванные объекты в списках игрока отсутствуют, поэтому выполняется ветвь обычных заклинаний.

## Полный обработчик выбора и действие Session

Исполнены настоящие `4094C0`, `40C180`, `422600`, `4346E0`, `527130`, `525F00`. В подготовленном UI исходный режим руки равен 0, состояние курсора `12F6=C`; World `7291=FF` отключает дополнительную ветку синхронизации выбора. Остальные ветви этих методов не выдаются за проверенные.

При найденном ID обработчик:

1. записывает UI DWORD `13DB=8`, BYTE `13E8=ID`;
2. вызывает исходную настройку состояния курсора;
3. вызывает внешний звук с opcode `104h` и сохраняет handle в UI `2E`;
4. увеличивает счётчик действий UI `A`;
5. формирует и передаёт в настоящую локальную очередь 18 байт:

```text
DWORD 5, DWORD выбранный Spell ID, DWORD 0, DWORD 72h, WORD тег игрока
```

Для игрока 7 standalone сохранил `(5,13,0,72h,7)`, Qz/Qz2 — `(5,9,0,72h,7)`. Это действие выбора; применение заклинания, расход маны и последствия для мира здесь не выполнялись.

Очередь начинается с `Session+1C`, имеет 32 слота по 18 байт. Относительно очереди DWORD `240` — count, `244` — read index, `248` — write index. При валидных индексах копируются 18 байт, write увеличивается и при достижении 32 сбрасывается в 0. Проверен переход 31→0.

При count ровно 32 очередь возвращает отказ и ничего не копирует. UI-обработчик не использует этот результат: выбранный ID, звук и счётчик UI меняются, но нового действия нет. Не выводится универсальная защита `count>=32` или корректность повреждённых индексов.

## Что проверено и что остаётся открытым

В Ghidra запущены оригинальные native-инструкции и таблицы World/UI. Применены только явно заданные внешние sound-обработчики и null graphics provider на загрузке. Настоящие raw-converter, сортировка массива, player-state lookup, UI-селектор, проверка вкладки, обработчик выбора и Session-ring выполнялись целиком в описанных ветвях.

Каждый запуск сравнивает полный World, массив с соседними байтами, все raw-строки, итоговый intermediate, Session с очередью, UI, кнопку, игрока, состояния, tag-table, globals, sound-счётчики и FS. Первые 128 байт очереди дополнительно считаны через XMM; оставшаяся память проверена полным сравнением, а не выдаётся за полный сырой дамп.

После выполнения 33 диапазона функций, включая 22 с исполненными путями, и пять диапазонов данных повторно прочитаны из Ghidra и совпали с PE. В исходном packed-описании кнопок имеется pointer `411140` по `68FDFE`. Полная регистрация события мыши, доставка физических нажатий и реальная отрисовка окна не исследованы. Статические render/caller-контексты поддерживают принадлежность этого поведения UI, но не подменяют такой тест.

Новый поиск содержал 12 литеральных call-кандидатов: десять относятся к UI-полю World `+53`; два других имеют иной либо неустановленный receiver и три аргумента, поэтому не используются как доказательство вызова World.v120. Глобальная полнота call-анализа не заявляется.

Шесть значений raw C8 у Create Gold — 0, 1, `7FFFFFFF`, `80000000`, `FE0C0000`, `FFFFFFFF` — прошли полную цепочку. Результат выбора, вкладка и полные проверенные UI/Session-буферы совпали; менялись известные данные определения и checksum. **Игровое назначение C8 остаётся неизвестным**, глобальная неиспользуемость не доказана.

Сверены 82 исходных Keeper-файла и четыре EXE. Новых точечных пересборок — четыре; прежние 246 DB-тестов и 82 перестановки этапа 83 не пересчитаны как новые. Новые схемы включены в прежние 67 компонентов пакета.

Воспроизведение: `scan_keeper_order_calls.py`, `native_keeper_ui.py`, `emulate_keeper_ui.py`, `prepare_keeper_ui_primary.py`, `build_keeper_ui.py`, `build_format_package.py`, `audit_keeper_ui.py`. Native-входы/результаты перечислены в `phase84-keeper-ui-emulations.json`. Общая цель всех 15 семейств форматов не завершена.
