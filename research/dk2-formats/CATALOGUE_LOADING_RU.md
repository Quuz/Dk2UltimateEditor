## N определяет выделение памяти

`0x51DD40` вызывает проход описателя `0x51DE50`, затем выделение памяти `0x51E2C0`. Обработчик ссылок `0x51EA40` при соответствующем состоянии загрузки вызывает `0x51DF90`, который регистрирует callbacks заголовков каталогов. Например, `0x51EB30` добавляет N Terrain в `world+0x15A8`, а `0x520040` добавляет N Traps в `world+0x15E8`. Счётчики складываются; это не вычисление максимального ID.

Следовательно, учитывается сумма N каталогов, посещённых настоящим проходом подсчёта. Нельзя автоматически считать отдельный файл полной областью загрузки. Наш инструмент принимает область явно и не угадывает содержимое ссылок описателя.

## Terrain: ID является индексом

Аллокатор `0x51E2C0` выделяет `сумма N + 1` записей по 460 байт. В assembly `0x51E2E2` увеличивает счётчик на один, `0x51E324` передаёт размер `0x1CC` конструктору массива. Начальные четыре служебных байта перед массивом хранят его размер; это не дополнительная доступная запись.

Callback `0x51EB50` берёт ID из intermediate+`0x28E` (raw записи +`0x1D6`) и вызывает загрузчик по адресу `array + ID*460`. В `0x51EB99..0x51EBBF` нет сравнения ID с ёмкостью. Getter `0x508DD0` также возвращает `array + (argument & 255)*460`, без проверки существования определения.

При сумме N=41 существуют ячейки 0..41. ID42 уже адресует память за массивом. Если создать 41 запись с большим пропуском ID и правильно пересчитать длины KWD, файл может пройти структурную проверку, но загрузчик запишет за границу массива. Для безопасной прямой записи требуется `ID <= сумма N` именно в реальной области подсчёта. Это ограничение не означает, что все ID между 1 и N обязаны иметь определения: незаполненные ячейки остаются сконструированными значениями по умолчанию.

Повторение Terrain ID повторно вызывает загрузчик той же ячейки. Это не универсальное правило «вся последняя запись побеждает»: загрузчик переносит отдельные поля по признакам присутствия, а часть ресурсов загружается условно.

## Семь каталогов: сортировка при вставке

| Каталог | Callback записи | Поиск ID | Runtime байт |
|---|---|---|---:|
| Rooms | `0x51EE60` | `0x50D0B0` | 1158 |
| Doors | `0x51FF30` | `0x50D650` | 181 |
| Traps | `0x520060` | `0x50D8C0` | 209 |
| Objects | `0x521650` | `0x50DB20` | 285 |
| KeeperSpells | `0x51FCD0` | `0x50DD60` | 122 |
| CreatureSpells | `0x51FE00` | `0x50DFA0` | 70 |
| Shots | `0x521810` | `0x50E1E0` | 118 |

Память выделяется на сумму N записей. Callback проверяет `loaded_count < capacity`, сдвигает записи с ID больше либо равным новому и загружает новую запись перед ними. При заполненной ёмкости callback ничего не добавляет, но возвращает успех.

Поиск начинается с `min(ID-1, loaded_count-1)`, идёт назад, возвращает совпадение и прекращается, встретив меньший ID. Аргумент используется как u8. При разных ненулевых ID пропуски допустимы: максимальный ID может превышать N. В вашем KeeperSpells 13 записей, максимальный ID14 — штатный случай. Упорядочивать файл по ID ради этого загрузчика не требуется. В обоих просмотренных Globals Shots и CreatureSpells уже записаны не по порядку; вставка их упорядочивает в памяти.

ID0 такой getter не возвращает: начальный индекс становится -1. Запись с ID0 также может сдвинуть другие определения дальше предельного стартового индекса поиска.

Дубликат является новой записью, а не обновлением существующей. Нельзя обещать общее «первый» или «последний побеждает». Например, после входа ID `[1,1,2]` поиск ID2 начинает со второй ячейки, видит там ID1 и возвращает null, хотя ID2 лежит в третьей. У двух записей ID5 поиск начинает с последней ячейки и находит более раннюю входную запись. Исправлять такие случаи автоматическим удалением/перенумерацией нельзя.

## Creatures: два разных ключа

Callback `0x51F240` выделяет/перемещает записи по 2199 байт. Для сравнения существующей записи он вызывает `0x494360`, а новый ключ берёт из входного CreatureId. Это отличается от простой сортировки по одному полю.

`0x494360` проверяет runtime-флаг `0x08000000` по +`0x686`. При установленном флаге возвращает +`0x5B3`, иначе +`0x770`. Пути из файла:

- `Flags`: raw+`0xEFC` → intermediate+`0x12EC` → runtime+`0x686`;
- `CloneCreatureId`: raw+`0xD3B` → intermediate+`0x112B` → runtime+`0x5B3`;
- `CreatureId`: raw+`0xF4B` → intermediate+`0x133B` → runtime+`0x770`.

Название флага `IS_UNIQUE` согласуется с данными: в ваших каталогах 13 таких записей ID32..44, например Unique Firefly/Alarm Fly имеет собственный ID32 и CloneCreatureId12.

Обычный getter `0x50D390` (виртуальный слот `0xC0`) сравнивает результат `0x494360`. Другой getter `0x50E3A0` (слот `0x1C8`) сравнивает собственный ID по +`0x770`. Оба начинают с `min(ID-1, count-1)` и прекращают поиск на меньшем ключе.

Порядок записей может менять результат. Контрольный пример: сначала unique с ID32/clone12, затем обычное существо ID13. Код оставит runtime ID `[32,13]`, потому что сравнит 12 с новым 13. Поиск собственного ID32 начнёт с ID13 и завершится неудачей. При обратном входном порядке runtime ID `[13,32]`, поиск32 успешен. Этот пример получен моделированием инструкций, без запуска изменённого файла в игре. Для Creatures сохранять исходный порядок и отдельно проверять результат каждой перестановки.

## Отдельная ветка обновления

Если DWORD `world+0xA3C7` ненулевой, рассмотренные callbacks ищут существующее определение и вызывают его loader без вставки/увеличения count. Для семейств с поиском null-проверки перед loader нет. В этом проходе не установлено, при каких внешних операциях включается режим; его нельзя автоматически приписывать любому Globals или любому повторному ID. Проектор моделирует только нормальную вставку.

## Неизвестные поля: что удалось и не удалось подтвердить

`unresolved-field-traces.json` сохраняет четыре точных пути:

| Каталог | Raw | Байт | Intermediate | Runtime | Значение в самостоятельном файле |
|---|---|---:|---|---|---|
| Terrain | `0x198` | 2 | `0x250` | `0x183` | 11 различных значений, включая 504/508 |
| Terrain | `0x224` | 4 | `0x2DC` | `0x1B5` | 0 либо 4628 |
| Traps | `0x204` | 2 | `0x2AC` | `0x98` | 0 либо `0xFFF6` |
| Objects | `0x34C` | 2 | `0x3CC` | `0x106` | 0 |

У Traps два baseline-поля по байту на деле переносятся одним словом. `0xFFF6` можно показать как 65526 или -10; это не доказывает смысл «генерация маны». Название ManaGen из шаблона остаётся гипотезой.

Поиск точных memory displacement в 8729 размеченных участках EXE не установил игровых потребителей этих четырёх полей. Кандидат `0x47BAFC` со смещением `0x183` оказался таблицей характеристик существ, а не Terrain. Поиск не покрывает все возможные алиасы указателей, блочные копии, неразмеченный код и другие EXE; неизвестные поля нельзя объявлять неиспользуемыми или обнулять.

## Проверка

`verify_catalogue_loading.py`: 177 граничных случаев и перестановок, включая разные ключи unique-существ, дубликаты, ID0, переполнение ёмкости и предел Terrain. Затем отдельно проверены девять семейств в самостоятельных каталогах редактора, AutoSaveGlobals и фактически указанном в описателе kop4Globals. Во всех трёх явных областях загруженные ID находятся штатными getters, выходов записи Terrain за расчётную границу нет. Это проверка статической модели размещения и поиска, не запуск новых карт в игре.

Пример проверки выбранной области без записи во входы:

```text
python native_catalogue_loading.py "полный путь к Globals.kld" --output "отдельный файл audit.json"
```

Не складывать самостоятельные каталоги и дублирующий их Globals в одну область без подтверждения такого порядка загрузки: искусственные дубликаты исказят результат.
