## Связь с вопросом об ошибках редактора

Отклонённые зацепки `Traps +0x204` не означают, что редактор записал высоту двери или параметры компьютерного игрока в ловушку. Совпало численное смещение в разных структурах памяти. Этап62 установил их типы: старое чтение `58ACC5` относится к Door Height, `4ED876` — к отдельной конфигурации компьютерного игрока. Сохранность WORD `Traps +0x204` подтверждена; его игровое назначение остаётся неизвестным.

Редактор может содержать ошибки. Однако для конкретного вывода «его запись сломала игру» нужны отдельно изменение байтов редактором и игровой потребитель этих байтов. Текущий этап показывает дополнительную причину не смешивать эти вопросы: игра сама может преобразовывать корректно сохранённые значения при активации.

## Выбор пресета отличается от его загрузки

Загрузчик принимает ID1..18 и хранит152 байта по `manager + 0x28 + ID*0x98`. Но активация выбирает источник иначе:

| Запрошенный режим | Действие `44ACE0` |
|---|---|
| 1,2,3,4,5,9,10,11 | Берёт соответствующий слот и применяет параметры согласно ветке режима |
| 13,14,15 | Берёт **слот9**, адрес `manager+0x580`; собственный слот режима здесь не применяется |
| 7,18 | После общей подготовительной части записывает номера текущего/ожидающего режима и возвращает1; границы и целевые параметры пресета не применяет |
| 6,8,12,16,17 | После копирования исходного слота возвращает0 |
| 0,19 | В проверенных доступных буферах возвращает0 после копирования152 байт |

Переадресация13..15 видна в `44AF5F`. Наличие записи с ID13 само по себе не доказывает использование её параметров этим путём. Проверены отдельные цепочки загрузки настоящих записей ID13/14/15 и цепочка загрузки настоящего ID9 с запросом режима13.

Копирование пресета выполняется **до проверки диапазона** номера режима. Сценарии0/19 имели специально доступную память; произвольные отрицательные или большие значения не объявляются безопасными.

## Особенность Lens в режимах13..15

В `44B312` и `44B318` один EAX записывается в обе границы `manager+D58` и `manager+D5C`. Он содержит `mid+0x84`, то есть исходное поле `LensMin` по raw offset `0x40`. Исходный `LensMax` по raw `0x44` не используется как верхняя граница этой ветки.

Затем выполняется обычное знаковое ограничение с исключённой верхней границей: `min(max(value,lower),signed32(upper-1))`. При равных границах1024 результатом становится **1023**. Этот результат подтверждён исполнением полной функции для всех трёх режимов, с сопоставлением всех байтов менеджера.

Для lower=`0x80000000` вычитание единицы превращает верхнюю границу в `0x7FFFFFFF`; утверждение «всегда lower−1» здесь неверно. Это исключение явно сохранено в схеме.

Доказаны инструкции и итоговое состояние при заданных внешних данных. Намеренность такого поведения и его видимое последствие не установлены. Называть это доказанной ошибкой редактора или причиной прежних графических артефактов нельзя. Независимый редактор должен сохранять raw `LensValue/Min/Max` раздельно, а не заменять их результатом активации.

## Флаг0x80 не делает неудачный вызов полностью бездействующим

Проверяется **предыдущее активное** поле `manager+D92`, а не флаг запрашиваемого пресета. Перед проверкой могут произойти:

1. Сброс global `759AE8` и вызов `571DA0`, зависящий от старых текущего/ожидающего режимов2/10/11.
2. Сохранение активного Zoom из D80 в DE0 для старых режимов3/4/5/9/13/14/15.
3. Запись времени/длительности и копирование16-байтных блоков перехода E52/E72.
4. Запись старого режима в DAC и младших16 бит аргумента nodeID в DEC.

Только затем `44AF3F` проверяет0x80 и может вернуть0, не применяя новый пресет. Поэтому `return0` не означает неизменности всей области состояния. Три сценария блокировки проверяют эти предварительные изменения.

Двухшаговый сценарий отдельно подтверждает: при предыдущем флаге0 первая активация пресета с0x80 завершается успешно, а следующий запрос блокируется. Native return0/1 сохраняется до выполнения сравнительного наблюдателя; регистр EAX наблюдателя не выдаётся за native return.

## Целевые значения и переход

Обычные границы XY берутся из поставщика размеров мира: минимум0, максимум `dimension<<12`. Минимум/максимум Z берутся из пресета. В обычной ветке целевые XY сохраняются из активной камеры, а Z берётся из `PositionZ`; это не прямое копирование всей raw Position.

В режимах3/4/5/9 используется сохранённый Zoom DE0 либо значение пресета при E3C bit0x40. Если старый режим принадлежал группе3/4/5/9/13/14/15, Zoom дополнительно вычисляется через отношение активного/целевого Lens с unsigned DIV и 32-битными переполнениями. Углы зависят от режима: например, режимы13..15 получают6 байт из **runtime** таблицы `75A311+mode*10`, а не из углов CD. Таблица в проверке задана явно; её наполнение реальной игрой не установлено этим этапом.

Для1/2/10 проверены ветки node kind0 Creature, kind2 Object и иной kind. ID сужается доWORD; ненулевой ID использует таблицу указателей без предварительной проверки таблицы валидности. Object Z = supplied terrain height + definition WORD FA; Creature Z = entity Z + definition WORD65C. Для Creature ID`0x2D` нижняя граница Lens делится со знаком с округлением к нулю, целевое значение — unsigned сдвигом вправо. Это exact-DX runtime offsets, не смещения CD-файла.

Режим11 проверен только для отсутствующего/не-kind6 узла: XY активной камеры, Z = supplied ground+256, углы activeYaw&2047/400/200, View lower/target0, **целевой Lens из mid84 (LensMin)**. Наблюдаются запросы событий `(9,now,1500)` и `(7,1500)`; длительность helper всегда3000, включая E3C bit0x40. Ветка kind6 с генератором случайных чисел не выполнена.

Группы режимов: `{1,2,10,11}`, `{3,4,5,9,13,14,15}`, `{7}`, `{18}`; остальные попадают в группу0. Подготовка выбирает500 при совпадении групп и2000 при различии. Выход из старого режима7 или E3C bit0x40 задаёт0, но режим11 позже заменяет её на3000. Единица времени не измерялась физически, поэтому эти числа не объявлены миллисекундами.

Полный `44BD70` при ненулевой длительности только записывает время начала DDC и `now+duration` в DD8. При0 он переносит целевые позицию/Zoom/углы/View/Lens в активные поля, устанавливает DA8=DD4 и DD8=0, вызывает reset/matrix providers и для валидного узла снимает bit0 entity BYTE F3. Для1/2/10 при ненулевой длительности текущий DA8 может оставаться прежним: ожидаемый DD4 и текущий DA8 — разные состояния.

## Проверка и границы результата

Сравниваются все3840 байт менеджера, включая весь банк пресетов,128 байт наблюдений, global759AE8, при наличии все1024 байта entity и2304 байта definition. Результаты всей памяти обусловлены этими поставщиками; их реальные побочные эффекты не объявлены проверенными.

Все семь полных native bodies повторно считаны из Ghidra после эмуляций и сопоставлены с исходным PE:44ACE0,44BD30,44BD70,572CD0,56F850,56F900,449A30. Таблицы переходов44BB8C..44BD2D сверены отдельно как initialized data. Подмена7 выполняемых функций не используется.

Три файла камеры имеют одинаковый SHA256: это39 разных исходных записей,117 с учётом копий. Для всех24 полей каждого из117 CD проверена точечная пересборка всего контейнера: **2808 правок только в памяти**, без изменения остальных байтов и предшествующей секции621 Variables. Все четыре исходных EXE совпадают с историческими SHA; игровых файлов исследование не меняло.
