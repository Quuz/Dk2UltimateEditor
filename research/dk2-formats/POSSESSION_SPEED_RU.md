## Где хранится

Запись type224 занимает 16 байт:

| Смещение записи | Физическое поле |
|---|---|
| +0 | DWORD типа224 |
| +4 | DWORD StatId |
| +8 | DWORD значения; загрузчик сохраняет low16 |
| +C | DWORD, не читаемый этим загрузчиком; сохранять |

В текущем `Data/editor/GlobalVariables.kwd`, SHA `d14b6a28694254dad722071267268d4f36c8535cd3a9c610f9ee0447fe9b941a`, запись StatId21 начинается по **2658h**, значение — **2660h**, исходные DWORD — `[224,21,200,10]`. Это смещения данного файла; редактор должен искать запись по типу/ID в контейнере, а не записывать по абсолютному адресу. Последний DWORD 10 здесь не является уровнем существа.

Оригинальная `51DC70` записывает WORD в `6F2863 + 2*StatId` с полным DWORD-индексом и без проверки границ. Getter `495080` работает иначе: берёт low8 аргумента, для индекса<32 читает **signed WORD** по `[6E4154]+313h+2*index`, иначе возвращает100. Обычно `[6E4154]=6F2550`, поэтому обе базы совпадают.

Граничные эмуляции подтвердили асимметрию: writer32 пишет WORD по6F28A3 за таблицей, getter32 возвращает100. Writer277 пишет по6F2A8D; getter277 сужает аргумент до21 и читает другую, нетронутую ячейку. Это forensic-проверки в ограниченном буфере, не рекомендуемые значения для нового содержимого. Неизвестные исходные записи нужно сохранять, не исправляя молча.

## Формула оригинальной `48ABB0`

Сначала выбирается базовая скорость: mode0 → definition DWORD5B4, mode1 → DWORD5B8, mode2 → DWORD5BC. Затем учитываются здоровье и Terrain. Последний процентный модификатор использует **StatId21 во всех трёх режимах**.

Пусть `B` — значение после этих ранних модификаторов, `P` — signed16 из ячейки21, `u32` — младшие32 бита:

```text
product = u32(B * (100 + P))
actor DWORD3E6 & 80h:      result = unsigned(product) // 100
иначе DWORD3EA & 08h:      result = unsigned(product) // 200
иначе:                    result = B
```

Бит80h действительно устанавливает оригинальная `48DEA0(1)`, вызываемая и в статически проверенном Shot process26. При обоих флагах побеждает первая ветка. Игровое имя второго флага в этом этапе не назначено: это половина всего множителя, а не только половина добавки.

| P, B=4096 | Вселение, flag80h |
|---|---:|
| 0 | 4096 |
| 100 | 8192 |
| 200 | 12288 |
| FFFFh, signed−1 | 4055 |
| 8000h, signed−32768 | 41611591 |

Последняя строка следует из 32-битного переполнения и **беззнакового** деления произведения. Плавающая точка и привычная «процентная» формула со знаковым результатом её не воспроизводят. Сохранять нужно полный исходный DWORD, даже если загрузчик использует только его младшие16 бит.

При P200 проверены ходьба4096→12288, бег8192→24576, Shuffle2048→6144. Отдельная загрузка StatId22=200 при21=0 не увеличила скорость в этом getter, включая режим бега. Это не доказательство отсутствия других потребителей StatId22.

## Что теперь известно про scalar98/113/114 и здоровье

Scalar98/113/114 загружаются в WORD6F28E0/6F28F2/6F28F4. В полном новом speed-path при type224/21=200 подмена всех трёх значений на0,6 или30000 не изменила результат12288. Следовательно, эти scalar-поля не управляют проверенным расчётом скорости. Это не доказательство, что они нигде не используются.

Полный образ существа в этих проверках сохраняет HP1000 при `48DEA0(1)`: setter ставит flag80h и обнуляет DWORD488/3EE, не прибавляя HP. Но здесь не исполнены полный процесс вселения через Shot26/действия игрока, другие параметры состояния и дальнейшие tick. **Формула бонуса здоровья и действие type224/StatId1 пока не объявляются найденными.** StatId1=100 в текущем файле и его отсутствие влияния на speed не доказывают ни бонус100%, ни неиспользуемость для здоровья.

## Проверки и воспроизведение

21 новый native-сценарий: сырой callback type224 → настоящий setter flag80h → полный getter скорости, включая оригинальный vslot88→48ED40 и lookup495080. Одна запись `[224,21,200,10]` взята неизменённой из текущего файла. Проверены границы signed16, старшие16 бит сырого значения, переполнение произведения, режимы движения, приоритет флагов и индексы writer/getter.

Стенд готовит уже созданного актёра из полного 1343-байтового снимка native factory этапа90. Это не повторное создание и не новый образ живого процесса. После каждого вызова сравниваются весь актёр с256 защитными байтами, таблицы, world/map/owner, исходная запись и остальные подготовленные данные. Новых полных образов не объявляется. Внешние GFX/sound/OS-probe providers сохранены в стенде, но вызовов не наблюдалось; код, vtable и игровые функции не подменялись.

125 полных диапазонов native-функций и6 блоков исходных данных сверены с PE; число включает ранее исследованные зависимости и статические ветви, это не покрытие125 функций исполнением. Среди557 ранее принимаемых Variables-контейнеров найдены32 type224-записи; выполнены128 точечных API-пересборок целых контейнеров с заменой только DWORD+8. Остальные поля, последний DWORD10, заголовки и соседние секции сохранены. Прежние24 отказа strict parser не ремонтировались и не объявляются повреждёнными.

API `patch_value_bits(raw,value)` сохраняет неизвестные биты и длину; `view(raw)` показывает фактические signed16 и адрес записи загрузчика; `speed_modifier` моделирует только последний модификатор, без здоровья/Terrain и игрового tick.

Воспроизведение: `prepare_possession_primary.py`, `ghidra_probe.py phase92-primary-queries.json`, `emulate_possession_speed.py`, `build_possession_speed.py`, `build_format_package.py`, `audit_possession_speed.py`.
