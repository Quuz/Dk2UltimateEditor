# Неизвестное Objects34C: проверка оставшихся границ инструкций

Этап100. Исследован предоставленный старый EXE SHA-256 `93e826a142f677ef5120699feddb0572799d93399167ef1d05ec4b48a8b2a342`. Папка13 не удостоверяет розничную версию1.3.

**Закрыты шесть оставшихся неиндексированных кандидатов из нового anchored-набора этапа70. Ни один не оказался настоящей инструкцией, читающей неизвестное Objects+34C.** Это ограниченный отрицательный результат; поле не объявляется неиспользуемым.

Физический путь неизвестного слова остаётся прежним: raw WORD34C → intermediate WORD3CC → definition WORD106. Значение и остальные неизвестные байты нужно сохранять. Новая схема — `unknown-instruction-boundary-review.json`, компонент `unknown_instruction_boundary_review`.

Все байты сопоставлены с PE и диапазонами Ghidra. Это дополнение к уже отвергнутому на этапе70 адресу42F0F1; тот прежний результат не засчитывается повторно.

Сам по себе поиск от байтов displacement полезен для обнаружения пропущенного кода, но может начинать декодирование внутри другой инструкции. В частности, удаление префикса66 превращает WORD в кажущийся DWORD. Для настоящего WORD104 следующий байт106 уже лежит за пределами чтения.

## Пропущенные ветви switch

Ghidra первоначально не включила switch arms функции4979B0 в body. Перед переходом497A1E код сравнивает EAX с4 и уходит при большем значении. По оригинальной таблице497E58 восстановлены все пять адресов и317 дополнительных инструкций. Среди них находится настоящее чтение497C61.

Поэтому первая неуспешная проверка принадлежности инструкции не была признаком отсутствия кода: она выявила неполноту metadata. Восстановленные байты сохраняются в машинной схеме, а вся таблица отдельно сверена с программой Ghidra и PE. Это статическая проверка, не пять исполненных игровых ветвей.

## Настоящее соседнее чтение107

По4A9005 действительно стоит `MOV EAX,DWORD[ESI+107]`; оно начинается после ложного кандидата4A9004. Эта операция численно затрагивает байт107, но происхождение структуры имеет значение.

Входной ECX сохраняется вESI по4A8C1B, затем в stack local по4A8C22. Перед интересующими ветвямиESI восстанавливается по4A8F51. Проверка графа647 состояний показала, что этот reload доминирует чтение4A9005. Оба входящих условных перехода —4A8FB6 и4A8FDD; между reload и ними ESI не перезаписывается. Decompiler связывает используемый `param_1` с исходным ECX.

Следовательно, здесь читается член исходного экземпляра, с которым функция выполняет позиционные/скоростные операции, а не новое поле из полученного определения Objects. Доказательство явно предполагает фиксированный stack frame, обычное сохранение nonvolatile-регистров и отсутствие изменения данного local через alias. Оно не является рекурсивной проверкой всех callees или поведения при повреждённом стеке.

Простой регистровый анализатор сам не смог восстановить указатель после stack reload. Этот предел записан в схеме, а локальная spill/reload-проверка выполнена отдельно. Запрос PCode по имени `param_1` подтверждает только происхождение этой переменной; сам по себе он не доказывает, что любой регистр около адреса содержит её.

## Проверки и оставшиеся вопросы

Сверены шесть полных code extents старого EXE и одна20-байтовая switch-таблица;317 восстановленных инструкций проверены отдельно. Проверены прежние SHA84 связанных исходных файлов и четырёх EXE. Новых native-эмуляций, raw-пересборок или запусков игры здесь нет; прежние проверки не засчитаны повторно.

В пакет добавлен79-й компонент, прежние78 машинных схем сохранены побайтово. Источники и параллельный редактор не изменены. Оценка готовности всей цели остаётся около75%: закрытие списка ложных кандидатов не раскрывает игровое назначение нового свойства.

Остальные wide/byte/adjusted/indexed/indirect кандидаты, другие профили и бинарники не исключены. Objects34C, Traps204, Doors236, CreaturePriority/Jump, Terrain198/224 и scalar113/114 сохраняют статус неизвестных. Следующий поиск должен исходить из реального источника указателя или нового способа обращения, а не повторять эти шесть совпадений.
