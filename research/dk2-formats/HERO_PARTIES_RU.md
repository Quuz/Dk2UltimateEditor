# Things C9: отряды героев, этап32

Дополнение этап75 — `WANDER_STATE_RU.md`:всего782 реальныхC9(payload555),5768 занятых слотов и6744 пустых. ByteWanderRadius29(decimal,1Dhex) равен0 во всех слотах. Это новый подсчёт корпуса,не доказательство игрового эффекта и не разрешение очищать остальные байты пустых слотов.

Подтверждено по предоставленным EXE. Машинная спецификация — `hero-party-semantics.json`, API — `native_hero_parties.py`, воспроизводимая проверка — `phase32-validation.json`. Исходные игровые файлы не изменены. Смещения ниже шестнадцатеричные, относительно payload после8-байтовой оболочки `u32 C9,u32 payloadBytes`.

## Современная запись555 байт

| Смещение | Размер | Содержание |
|---|---:|---|
| 00 | 32 | Raw имя; обработка строки загрузчиком описана отдельно |
| 20 | 2 | TriggerId |
| 22 | 1 | PartyId |
| 23 | 4 | Прежний X23, назначение не установлено |
| 27 | 4 | Прежний X27, назначение не установлено |
| 2B | 512 | 16 слотов по32 байта, каждый — payload Good C7 без оболочки |

**Счётчика участников в X23/X27 не найдено.** Game parser570210 и editor converter42F9E0 не переносят эти8 байт. Они создают631-байтовый intermediate:19 DWORD признаков присутствия, затем555-байтовый буфер. Признаки всех16 слотов получают1, включая пустые. Все512 байт участников копируются дословно. Имя проходит `strncpy32`, после чего последний,32-й байт принудительно обнуляется; после первого NUL действует обычное заполнение нулями.

Два DWORD23/27 остаются нулевыми в intermediate, хотя физические байты файла могут быть ненулевыми. Их нужно сохранять в редакторе, а не переименовывать в счётчик или автоматически обнулять.

| 300 | WORD00/byte02 | 8×32 с0C | Начинается с10C, то есть268-го байта |
| 555 | WORD20/byte22 | 16×32 с2B | Первые32 байта |

Для старых записей оставшиеся8 канонических слотов нулевые. Старые промежутки заголовка не переносятся.

В ветках268/300 исходный код использует поиск NUL и копирование без ограничения длины. API даёт точную проекцию только при предоставленной ограниченной строке с NUL и длиной до31 символа. Для268 требуется явный `legacy_tail_cstring`: результат нельзя однозначно получить из файла. В native-fixtures строка вне прочитанного входа задана явно; это свойство проверено в обоих EXE. Для300 строка без NUL внутри32 байт отвергается инструментом, исходная запись остаётся сохранённой raw.

Любая другая объявленная длина направляет native parser в чтение555 байт: проверено в том числе556. Независимый парсер должен соблюдать границы оболочки и сообщать о неизвестном варианте, сохраняя его содержимое. Общий `dk2_formats.py` уже сохраняет такие оболочки raw; расширение новых legacy записей не требует подменять их фиктивными555 байтами.

## Хранение в игре

Callback5212A0 вызывает world checksum5108C0 для всех631 байт intermediate, затем50FA70. В runtime:

```text
slot = world + 4030h + unsigned8(PartyId) * 520
slot[0..1] = TriggerId
slot[2] = PartyId
slot[8..519] = все16 записей участников
slot[3..7] остаются прежними
```

Имя и X23/X27 не хранятся этим helper в runtime-слоте. При этом **нормализованное имя участвует в предшествующей контрольной сумме**, как и все байты слотов, даже пустых; X23/X27 в неё поступают уже заменёнными нулями. «Не используется для хранения отряда» не означает «не влияет ни на что».

Запись напрямую адресуется по PartyId. Более поздняя запись того же ID заменит TriggerId/ID/512 байт участников. Границы24 в50FA70 нет:24 и255 также умножаются на520. Это подтверждено только в выделенной памяти эмулятора. Оригинальный редактор считает и перечисляет24 слота0..23; его getter48DE00 возвращает null за этим диапазоном. Не принимать отсутствие проверки game helper за разрешение создавать произвольные ID.

При последующем spawn путь519F90 проходит все16 слотов и пропускает только `CreatureId=0`. Он переносит **PartyId из byte1E самого участника** в instance417. Game world-store не исправляет его по заголовку. Поэтому при ручной правке заголовок и PartyId участников могут разойтись. Полный spawn, координаты появления, бой и все trigger actions этим этапом не эмулировались.

## Путь Editor Pro отличается от одиночного C7

Callback491A40 выбирает все непустые слоты, пропуская `CreatureId=0`. `4211B0` добавляет их в первые свободные позиции модели, поэтому отверстия между участниками уплотняются. Нулевые по CreatureId слоты могут содержать другие байты; обычное raw-сохранение не должно их терять.

После создания модели участника:

- PartyId берётся **из заголовка отряда**, заменяя member1E.
- Уровень копируется байтом:0 здесь остаётся0, в отличие от одиночного C7.
- В современной ветке major!=1 золото/здоровье проходят low8, затем min100. Major1 имеет отдельную legacy конверсию, исключённую из числового API.
- WanderRadius, target player и objective копируются байтами. AP DWORD сужается до byte setter41CF40.
- Leader/Follower не очищаются. Если оба отсутствуют, первый добавленный участник получает Leader, последующие — Follower. Если хоть один уже установлен, флаги сохраняются, включая оба бита сразу и нескольких лидеров.
- Objective0 при загрузке остаётся0; AP не заменяется на3. Позднее serializer4952F0 меняет objective0 на19, сохраняя byte AP.

Финализатор одиночного Good41CF20 и его сброс ReturnToHeroLair для старой версии здесь не вызываются. Правила C7 из этапа31 нельзя автоматически применять к участникам C9.

Raw XYZ участников этот цикл не присваивает модели: значения позиции определяются отдельным конструктором. API `editor_member_fields` описывает перечисленные поля после создания и добавления, не обещает полную реконструкцию модели. Unique/clone lookup и MFC constructor выделены отдельно и полностью не эмулировались.

Имя модели отряда callback форматирует как `Hero Party %u`, используя headerID+1, поверх исходного имени. Финальное добавление через48DE20 имеет особую обработку IDFF — выбор свободного ID; все последующие последствия этой операции для модели не проверены. Проекции участников описывают момент до неё.

## Почему имя и X23/X27 бывают похожи на мусор

Писатель4947C0 в цикле C9 заполняет только TriggerId20, Id22 и16 сериализованных слотов с2B. **Имя00..1F и восемь байт23..2A не назначаются** и сохраняют начальное содержимое рабочего буфера при проверенных контрактах helper функций. Null участник сериализуется в32 нулевых байта.

Статический CFG проход от входа писателя до первого C9 write/skip охватил593 состояния инструкций: прямые записи через ESP и PUSH не затрагивают эти интервалы. Отдельно учтены границы date helper,32-байтового Good serializer и условие, что file callback читает буфер без изменения. Это локальный анализ с явными контрактами, а не универсальная проверка всех косвенных алиасов.

Шесть прогонов **полного Things writer** с рабочим буфером00/A5/FF, пустыми и всеми16 заполненными участниками подтвердили ожидаемые555 байт целиком. Настоящие party count/get/member get, definition lookup и полный Good serializer выполняются; счётчики других семейств, дата, виртуальные XY/trigger и I/O заданы fixtures. Значит, для совместимого редактора не нужно генерировать «правильные» случайные значения X23/X27 или native-имени: по умолчанию сохранять исходные байты, а новые поля считать явно неизвестными.

## Корпус и проверка

В109 Things файлах найдены782 отряда, все555-байтовые, с5768 непустыми участниками. Все header PartyId находятся в0..23 и совпадают с PartyId непустых участников. Один отряд имеет отверстие в слотах; пустых слотов с другими ненулевыми байтами в этом корпусе нет. У767 записей неизвестные8 байт заголовка ненулевые; встречаются69 разных raw32 значений имени. Это согласуется с writer, но само по себе не служило доказательством назначения полей.

50 native-прогонов:16 полных parsers двух EXE,4 полных game callbacks/world-store,24 editor member fragments и6 полных writers. REPE CMPSB сравнивает все631 байт parser callback,520 байт runtime-слота,96 байт контролируемой модели участника и555 байт writer payload с независимым ожидаемым буфером. Это побайтное сравнение, не совпадение хешей. Фрагменты участников начинаются после создания и заканчиваются после native add; полный MFC callback с UI не исполнялся.

517 граничных проверок,1184 точечных пересборки и8 добавлений записей разных размеров выполнены в памяти двух настоящих Things. N и длина секции при добавлении согласованы. Проверены942 инструкции;46 полных повторных assembly не изменились. Дополнительно46 диапазонов **реальной памяти Ghidra-программ побайтно совпали с PE исходных EXE**. Сохранились SHA-25617 исходных файлов и2 EXE.
