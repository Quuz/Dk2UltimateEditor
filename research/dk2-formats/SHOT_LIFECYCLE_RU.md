# Shots: первый tick, завершение и отрицательный Data1

Этап 148, 31 октября 2026. Проверен предоставленный `DKII-DX.exe`, SHA-256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a`.

`DamageType = 5 (AT_START)` выполняется один раз в первом обновлении снаряда. `DamageType = 6 (AT_END)` выполняется в отдельном завершающем обработчике при дополнительном условии World. Оба режима используют оригинальную `4AC5A0`, которая передаёт в метод изменения HP отрицание `Data1`. В проверенных сценах значение `-80` поэтому прибавило целям 80 HP.

В 5 551 исходной записи Shots из 82 контейнеров встречаются только режимы 0, 1, 2 и 7. Режимы 5 и 6 выполнены на диагностических копиях записей. Их поддержка в этом EXE подтверждена; штатное заклинание с этими режимами не найдено.

## Данные для редактора

Размер записи Shots — 239 байт, порядок байтов little-endian.

| Поле | Смещение в записи | Хранение | Назначение в проверенных режимах |
|---|---|---|---|
| Data1 | `0x98` | DWORD, API `u32` | Параметр, который обработчик отрицает перед запросом изменения HP |
| Data2 | `0x9C` | DWORD, API `u32` | Целочисленный размер области в клетках |
| Flags | `0xA8` | DWORD | В частности, бит `0x4` включает уменьшение HP снаряда на единицу за проверенный tick |
| Health | `0xBC` | WORD | Начальное HP снаряда |
| DamageType | `0xC5` | BYTE | Режим обычного урона |
| ProcessType | `0xC7` | BYTE | Отдельный обработчик процесса; во всех новых сценариях задан NONE = 0 |

`Data1` и `Data2` совместно используются двумя системами диспетчеризации. В редакторе нужно учитывать одновременно DamageType и ProcessType. Менять глобальный физический тип Data1 на `i32` нельзя: у других процессов это могут быть ID, количество или иные параметры. Для записи диагностического `-80` текущим API используется `Data1 = 0xFFFFFFB0`.

Область режимов 5/6 — заполненный полуоткрытый квадрат `[cx-R, cx+R) × [cy-R, cy+R)`, где R берётся из целого instance Data2. Здесь не требуется умножение на 4096. При R = 0 в проверенной сцене запросов изменения HP нет. Геометрия общей `4AC5A0` была установлена на этапе 131; новый этап выполняет её из целых функций жизненного цикла.

## Когда выполняется AT_START

В начале `4AB180` увеличивается счётчик instance DWORD `+0x12D`. При нулевом DWORD `+0x149` выполняется ветка первого обновления: проверяется режим 5, вызывается `4AC5A0`, выполняется процесс события `0x40`, после чего `+0x149` получает 1. Второе обновление не повторяет эту ветку.

Одна фабрика `4B7CD0` не нанесла урон. Первый tick при Data1 = 80 уменьшил HP двух подготовленных целей с 1000 до 920, второй сохранил 920. Вариант с последним аргументом фабрики 1 также выполнил урон первого tick; общее назначение этого аргумента здесь не устанавливается.

Явный вызов завершающего обработчика для режима 5 не нанёс урон ни до первого tick, ни после него. При подготовленном World `+0x723B = 1` урон первого tick по-прежнему выполнился.

## Когда выполняется AT_END

`4AAF70` вызывает World vslot `0x4C`, оригинальная реализация `509850` возвращает DWORD World `+0x723B`. Только нулевой результат вместе с DamageType = 6 допускает вызов `4AC5A0`. Состояния 0, 1 и 2 выставлялись оригинальным setter `509860`: 1 и 2 подавили урон, а завершающая очистка продолжилась.

Завершающий обработчик смог нанести урон при HP снаряда 32 ещё до первого tick. Значит, внутри этой функции предварительное обнуление HP не является условием урона. После неё DWORD состояния `+0x16` стал 2.

Отдельная связка выполняет оригинальный HP setter с -31, затем полный tick. HP снаряда становится 0; tick запрашивает удаление через настоящий vslot `0x20` / `4B2AD0`, но HP целей остаётся 1000 и состояние `+0x16` остаётся 0. Только последующий явный вызов `4AAF70` наносит 80 урона и переводит состояние в 2. Поэтому в реализации нужно разделять запрос удаления и завершающий callback.

Значение World `+0x723B` пока описывается как условие подавления этого урона. Названия вроде «загрузка», «выгрузка» или «конец игры» не подтверждены. Обычный планировщик World, который выбирает момент вызова callback, и фактическое освобождение памяти пула ещё не выполнены в этой композиции.

## Проверенные результаты

| Сценарий | HP двух целей после выполнения |
|---|---|
| Режим 5, только фабрика | 1000 / 1000 |
| Режим 5, первый tick, Data1 = 80 | 920 / 920 |
| Режим 5, второй tick | 920 / 920 |
| Режим 6, один или два tick без завершения | 1000 / 1000 |
| Режим 6, завершение, World gate = 0 | 920 / 920 |
| Режим 6, завершение, World gate = 1 или 2 | 1000 / 1000 |
| Режим 5 или 6, соответствующее срабатывание, Data1 = -80 | 1080 / 1080 |
| Режим 5, Data1 = 0 | 1000 / 1000; запросы изменения HP с нулём присутствуют |
| Контроль режима 1, два полных tick | 840 / 840 |

Это подготовленные допустимые вражеские цели: владелец создателя 7, владельцы целей 8. Отрицательный параметр не отменяет исходные фильтры целей и ограничения метода HP. Крайние значения, переполнение, INT_MIN и все пределы лечения этим набором не проверены.

## Доказательства и воспроизведение

Приняты 22 сценария выполнения оригинальных инструкций. Шесть независимых контролей Ghidra сравнили 354 области памяти, всего 812 784 байта, с результатами Unicorn. Сверены байты 120 диапазонов функций и четырёх блоков таблиц; покрыты все 5 020 уникальных исполненных адресов инструкций исходного PE.

164 диагностические пересборки в 82 контейнерах проверяют Data1, Data2, DamageType и ProcessType. Обратные правки восстанавливают исходные записи, decode → rebuild сохраняет данные, остальные байты контейнеров не меняются. SHA-256 всех 310 исходных файлов и семи путей EXE сохранены. Прежние 126 компонентов спецификации остаются побайтно прежними.

Машинная спецификация — `shot-lifecycle-semantics.json`, актуальные значения — `editor-format-package.json → effective_shot_parameters`. Исторические компоненты и физическая разметка не переписываются.

Запускать из каталога исследования имеющимся Python окружения `ghidra-mcp-runtime`:

python crosscheck_shot_lifecycle.py

Контекст World, карты, списков целей и пула подготовлен явно; конвертеры, загрузчики, фабрика, tick и завершающий обработчик оригинальные. Внешние ресурсные и звуковые запросы обслуживаются описанными адаптерами; реальные звук, GPU и полёт в живой игре не проверены. Ранние неполные стенды без нужных графических/звуковых слотов исключены из принятых сценариев. Их остановки не свидетельствуют о падении игры.

Новые назначения непрозрачных полей на этом этапе не объявляются. Проверки CreatureFlags `0x800` и `0x1000` не установили их смысл. Общая цель по 15 семействам остаётся открытой, оценка готовности — около 75%.
