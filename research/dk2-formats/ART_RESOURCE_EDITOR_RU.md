# ArtResource: подтверждённая ошибка смены типа в оригинальном редакторе

Этап 130, 29 октября 2026. **В предоставленном Editor Pro смена типа ArtResource может заносить в сохраняемые метаданные прежнее содержимое стека.** Это подтверждено инструкциями, наблюдением за чтениями/записями, выполнением полного writer Rooms и независимым CPU Ghidra. Новая схема `art-resource-editor-semantics.json`, компонент `art_resource_editor_semantics`. Оригинальные EXE, игровые данные и параллельный редактор не изменялись.

Нативный диалог276 «Modify Art Resource» получает типы0–8 из таблицы `50C0F8`; вторая таблица `513198` побайтно совпадает. Message map связывает combo1658 с `433CF0`, а кнопку OK12431 — с `4349F0`. Для Procedural Mesh поле1660 подписывается **ID**. При открытии getter `41C080` читает DWORD `resource_object+48h`, при сохранении setter `41C090` записывает его, если тип7. Это `ArtResource+44h`, то есть уже установленный селектор процедуры из этапа129. Оба метода поддерживают полныйu32; подпись ID не доказывает полный набор допустимых игровых значений или диапазон проверки окна.

Ветка OK статически вызывает `41BBB0` для смены типа. Декомпиляция и инструкции показывают следующий порядок:

1. Старое имя сохраняется в настоящем CString.
2. В локальном84-байтовом буфере записывается только байт типа по смещению80.
3. `REP STOSD` обнуляет84байта **объекта ресурса**.
4. `REP MOVSD` копирует в объект21DWORD **из локального буфера**, остальные83байта которого эта функция не инициализировала.
5. `41BC50` восстанавливает имя и пересчитывает отдельный кэш суффикса `#`.

Таким образом, обнуление объекта не защищает данные: следующим действием в него копируется другой, неподготовленный буфер. В принятых CPU-прогонах наблюдатель фиксирует все21чтение источника и ровно одну запись в этот локальный буфер — байт типа в `41BBE6`. Подмены исходных функций или инструкций нет.

При одинаковой подготовке объекта и разных шаблонах прежнего стека переход0→7 или6→7 даёт:

| Шаблон стека | DWORD `ArtResource+48h` | DWORD `ArtResource+4Ch` |
|---|---:|---:|
| `00` | `00000000` | `00000000` |
| `5A` | `5A5A5A5A` | `5A5A5A5A` |
| `A5` | `A5A5A5A5` | `A5A5A5A5` |

Это неизвестные DWORD после селектора процедуры, а не их новые игровые значения по умолчанию. **Их смысл по-прежнему не установлен.** Ошибка объясняет способ появления странных чисел, но не доказывает, что каждое ненулевое значение в исходном корпусе возникло именно так. Обнулять исторические значения нельзя.

Для обычного неизменённого типа7→7 `41BBB0` пропускает переинициализацию. Подготовленные `55667788` и `99AABBCC` сохраняются при разных стеках, изменении только ID и последующей записи оригинальным writer. Это существенное различие между редактированием поля и созданием варианта другого типа.

Есть и тонкость сравнения: запрошенный байт типа расширяется как signed, существующий — как unsigned. Поэтому диагностические128→128 и255→255 всё равно запускают копирование. Штатный список окна предлагает0–8; живой сценарий окна с128/255 не проверялся. Эти проверки не превращают неизвестные типы в недопустимые данные файла.

Для проверки сохранения выполнены четыре подготовленных варианта одной записи Treasury, RoomID1. Изменяется известный **CompleteResource rawC8h → объект модели16Ch / raw-байты170h**. Настоящие `42DF90→49FC30` выделяют и регистрируют модель, затем выполняются `41BBB0→41C240(1)→41C090(4)→4A7AC0`. Все1352байта модели сверяются до/после с ожидаемым изменением ресурса; все1055байт каждой выходной записи проверены и контейнеры повторно разобраны/собраны.

В полных переходах0→7 один opaqueDWORD стал `17000000`, другой0 — наблюдённое прежнее содержимое нативного стека этой сцены. Writer перенёс их в файл. При7→7 сохранились заданные два DWORD. Это четыре диагностические композиции на базе исходной записи, а не четыре неизменённые исходные записи. Ранее установленный неинициализируемый байт Room36F при прогнозе выходной записи берётся из фактического состояния стека перед writer; тождество всего файла источнику не заявляется.

Отдельно подтверждены соседние методы. Конструктор `41BB40` обнуляет весь84-байтовый ресурс и кэш. `41C240(1)` устанавливает младший бит flags (маска1), а **`41C240(0)` стирает все84байта**, включая имя, тип и union; отдельный кэш при этом остаётся прежним. Это явная операция очистки, а не правило чтения любого сохранённого ресурса типа0. Прежняя цепочка этапа127 сохраняет произвольные84байта type0 при загрузке/записи без этой операции.
