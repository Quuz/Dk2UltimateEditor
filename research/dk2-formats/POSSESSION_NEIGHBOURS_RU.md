Обновление этапа98: полный шаг4D5A40/4D4760 теперь выполнен в32 сценариях с подготовленной картой и пустым массивом сил; четыре дополнительно применяют координаты к существу. См. `NAVIGATION_STEP_RU.md`. Полныйtick и реальные силы остаются открыты; ограничения ниже относятся к исходному этапу.

Этап95, предоставленный `DKII-DX.exe`, SHA-256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a`.

**Найден настоящий источник второго флага скорости:** при вселении игра проверяет линию по карте до других существ в списке владельца. Если проверка проходит, устанавливается `actorDWORD3EA & 08h`. Это тот флаг, для которого ранее была подтверждена половина общего множителя скорости. При текущем параметре200 получается **×1,5** для такого существа; само вселённое существо получает **×3**.

Оригинальная композиция выполнена в34 сценариях: raw type224 → настоящий setter вселения источника → обход списка `4BFD00` → проверка линии `4512F0` → полный getter скорости цели `48ABB0`. В четырёх сценариях перед ней выполнена полная загрузка сырой записи Doors. Схема — `possession-neighbour-semantics.json`, компонент `possession_neighbour_semantics`.

## Как выставляется и снимается эффект

`4BFD00` получает владельца в ECX и указатель на существо-источник в аргументе. Начало списка — `ownerWORD6`, следующий участник — `entityWORD10`, указатели разрешаются через таблицу tag.

- Если источник вселён (`DWORD3E6 & 80h`), функция пропускает его самого и для каждого другого участника выставляет либо очищает бит08 по результату проверки линии.
- Если источник уже без флага вселения, функция очищает бит08 у всех перечисленных участников, включая источник.
- Пустой список не меняет никого. Существо вне переданного списка не обрабатывается. Внутри самой функции нет повторной проверки владельца или типа каждого участника; корректность списка — её входной контракт.

Нативные вызовы есть в общем tick `488930` и в setter снятия вселения `48DEA0(0)`. В tick при установленном флаге вселения и `currentTick > actorDWORD3EE` вызывается обновление, затем `3EE=currentTick+20`. Это20 единиц игрового счётчика, а не установленное этим анализом число секунд. Полный tick и полный setter снятия вселения в новой композиции не исполнялись: в проверке очистки исходный флаг уже подготовлен сброшенным.

## Что проверяется на карте

`4512F0` обходит сетку между XY двух существ; Z не читает. Это целочисленная проверка с обработкой границ и углов клеток. Исполняется оригинальная функция, упрощённая замена алгоритма не вводилась.

В проверенных условиях:

| Карта между существами | Бит08 / скорость при базе4096, P200 |
|---|---:|
| Открытый проход | установлен /6144 |
| Проверяемая клетка с nav-битом08 | снят /4096 |
| Дверь без definition-бита40, отмеченная в nav | снят /4096 |
| Та же дверь с definition-битом40 | установлен /6144 |
| Одна XY-клетка, даже с nav-битом08 | установлен /6144 |

При одной клетке функция возвращает успех до проверки nav и дверей. В проверенном многоклеточном пути препятствие в исходной клетке не мешало; препятствие в конечной клетке мешало. Горизонтальный, вертикальный, обратный и диагональный пути проверены отдельно. Изменение Z цели не изменило результат.

Двери проверяются через `4511A0 → 4528E0 → 4D1A20` и настоящий World lookup `508FC0`. Старший полубайт runtime nav-клетки разрешает поиск Door-типа4 в списке клетки; сам по себе этот полубайт без двери не блокирует путь. Если такого признака нет, подготовленная дверь в списке не проверяется этой веткой. Это устройство runtime nav, **не назначение соответствующих битов сырой KLD-клетки**.

В `4BFD00` нет сравнения с радиусом: вычисленные квадраты разностей XY остаются в локальных переменных без дальнейшего использования. Открытый путь от(1,5;1,5) до(30,5;30,5) дал эффект. Это не доказательство отсутствия ограничений выше по цепочке или во всех игровых ситуациях.

## Где лежит процент скорости

Используется та же запись `GlobalVariables`: type224, StatId21, DWORD значения по+8. В текущем файле `[224,21,200,10]`. Загрузчик сохраняет младшие16бит; getter читает signed16. Сохранять редактор должен все32бита значения и последний DWORD, даже если этот потребитель их не использует.

Для скорости после ранних поправок здоровья и Terrain:

```text
product = low32(base * (100 + signed16(P)))
флаг вселения:            unsigned(product) / 100
иначе соседний флаг08:    unsigned(product) / 200
иначе:                   base
```

Деление целочисленное. При обоих флагах побеждает вселение.

| P, база4096 | Другое существо с битом08 |
|---|---:|
| 0 | 2048 — ×0,5 |
| 100 | 4096 — ×1 |
| 200 | 6144 — ×1,5 |

Таким образом, этот путь делит пополам **весь результат**, а не только добавку. Run8192 дал12288, Shuffle2048 дал3072: все три режима используют StatId21. Скалярные98/113/114 со значениями0,6,30000 не изменили эти новые результаты; их глобальное назначение этим не объявляется найденным или отсутствующим.

## Связь с Doors.kwd и безопасная правка

Подтверждена полная цепочка:

```text
raw Door DWORD228, bit40
 → initializer56A920 + converter56AA40: midDWORD29C
 → loader4A7100: definitionDWORD8B
 → проверка линии
 → бит08 у цели
 → множитель скорости
```

В базовом перечислении bit40 называется `IS_BARRICADE`. Здесь независимо проверено конкретное следствие этого бита для проверки линии. Это не новый самостоятельный флаг «бонус вселения»: у него есть и другие применения, поэтому переименовывать существующее поле только по этому эффекту не следует.

Четыре новые raw-композиции проверяют бит снятым/установленным в записи из нулевых616байт и в первой записи текущего `Doors.kwd`. Выполнены настоящие initializer, converter и loader; сравниваются все616raw,732intermediate,181definition и64 защитных байта после каждого буфера. Явный loader-gate1 исключает визуальную, звуковую и checksum-ветки; их поведение здесь не проверялось.

API `native_possession_neighbours.patch_door_bit40(raw, enabled)` меняет только bit40 по+228, сохраняя остальные31бит флагов и все другие байты. На82 исходных Door-контейнерах/656записях проверены1312 пересборок целого файла. Заголовки, порядок, неизвестные данные, соседние записи и секции сохранены; исходники не перезаписывались. Правка процента type224 использует уже проверенный API этапа92.
