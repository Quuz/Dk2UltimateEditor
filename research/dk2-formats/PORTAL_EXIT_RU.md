# Появление из портала: начальная точка и смещение выхода

Для предоставленного DX SHA `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a` теперь подтверждён игровой потребитель первой XYZ-тройки Creatures. **X/Y по raw `E94/E98` изменяют позицию после анимации портального появления. Начальную точку создания эта тройка не выбирает.** Raw Z по `E9C` в этом обработчике читается, но перед перемещением заменяется высотой пола.

Машинная спецификация — `portal-exit-semantics.json`, компонент пакета — `portal_exit_semantics`. Для правок добавлен `native_portal_offsets.py`; прежние 69 компонентов сохраняются побайтово.

## Путь, найденный в оригинальном коде

`4DC8F0` ищет в списке комнат владельца комнату типа 3 и вызывает `4DC9A0`; второй найденный caller — автоматический обработчик `4DBF90`. Эти обёртки исследованы статически; в эмуляции выполняется сама `4DC9A0` с заданным ID существа.

`4DC9A0` требует бит `400h` в DWORD владельца по `+76`, затем передаёт настоящей factory `4B78D0 → 4B7900 → 4872A0` позицию:

```text
X = (room BYTE+2D << 12) + 1800h
Y = (room BYTE+2E << 12) + 1800h
requested Z = 0
```

Это координаты опорной клетки комнаты плюс 1.5 клетки по обеим осям. Дальше применяется обычное размещение существа и проверка пола. В стенде с опорой (5,6) и центральным полом 0 существо появляется в `(6.5, 7.5, 0)` клетки. Полные 1343-байтовые экземпляры при нулевой XYZ-тройке и тройке `(4096,−4096,7FFFFFFFh)` одинаковы: тройка на этом этапе не использована.

После создания уменьшается совпавшая запись запаса существ владельца (`5064B0`), отмечается первое появление типа (`4C04A0`), включается action `31h` и запрашивается AI-состояние `C1h/193`. Для комнаты типа `19h` есть другая ветка, состояние `116h`; её выполнение не проверялось.

В состоянии 193 таблица, заполненная оригинальной `47BBE0`, содержит callback `459C20`, категория 7. Подтверждён вызов через оригинальный AI dispatcher `476FC0`, а не только прямой вызов известного адреса.

## Когда и как применяется XYZ

`496D00` считает действие активным, если его ID отличается от 0 и `15h/21`. Пока установлено action49, callback возвращает 1 и оставляет положение прежним. Сценарии ожидания с нулевой и ненулевой тройкой дали одинаковые полные образы существа; через настоящий dispatcher положение и состояние также сохранились.

После завершения действия `459C20`:

1. Обнуляет WORD существа `+95/+97/+99`.
2. Копирует текущую XYZ-позицию, прибавляет DWORD definition `+6EC/+6F0/+6F4` с обычным 32-битным переполнением.
3. По полученным XY находит клетку и вызывает `4545C0`.
4. Заменяет Z результатом этого helper и перемещает существо через `4B5560`, включая списки клеток.
5. Записывает итоговую XYZ в `+F6/+FA/+FE` и переходит в состояние 1 через настоящую `48AD30/476D30`.

В этом потребителе нет вращения XY-смещения на значение `WORD F4`; компоненты прибавляются непосредственно по мировым осям. Одна клетка равна **4096 единицам**. Отрицательные значения хранятся как обычный signed32 в тех же четырёх физических байтах.

| Смещение в стенде | Результат после выхода |
|---|---|
| X = 4096 | X с 6.5 до 7.5 клетки; сущность перенесена в список новой клетки |
| Y = −4096 | Y с 7.5 до 6.5 клетки |
| X = 512, Y = −256 | X +0.125, Y −0.0625 клетки |
| Только Z = `7FFFFFFFh` | Полный экземпляр совпадает с вариантом Z=0 |

Высота результата зависит от новой клетки. В стенде центр портала даёт 0, соседние клетки — 4096. У звука `E0` есть отдельный gate: он выполняется только при совпадении владельца существа с `World vslot264 → WORD+7243`; проверены оба исхода.

## Подтверждение завершения анимации

Оригинальная `4950C0` заполняет все 81×29 байт таблицы animation-action; таблицы категорий и состояний также заполняются оригинальными `4798F0/47BBE0`. Каждая полная таблица сравнивается с независимой проекцией инструкций, игровые callbacks не подменяются.

В двух сценариях выполняется настоящий animation tick `496AA0`: при отсутствии графического объекта в `actor+DC` он очищает action49. Затем прямой callback либо настоящий AI dispatcher выполняет выход. Для X=4096 вариант с native tick и вариант с прямым вызовом оригинального reset-helper `4966A0(actor+38D)` дали одинаковые полные 1343 байта. Остальные done-сценарии используют этот reset-helper, чтобы отдельно проверить арифметику и перемещение.

Это подтверждает путь завершения при null GFX. Длительность настоящей отображаемой анимации, её кадры, физический tick и полный цикл живого процесса здесь не воспроизведены. В completed-сценариях статическая нулевая тройка getter `494650` подготовлена как уже инициализированная (`6E4144=1`, `6E4148..4153=0`), как в этапе85. Отдельный диагностический запуск первой регистрации через `atexit` сохранён, в успешные проверки не включён.

## Какие байты менять в редакторе

Все смещения ниже относятся к началу записи существа, не ко всему KWD:

| Компонента | Raw DWORD | Runtime DWORD | Назначение в проверенном пути |
|---|---|---|---|
| X | `E94` | `6EC` | Смещение X после анимации появления |
| Y | `E98` | `6F0` | Смещение Y после анимации появления |
| Z | `E9C` | `6F4` | Сохранять; итоговый Z здесь заменяется полом |

Raw → intermediate `1284` → runtime `6EC` уже доказано полной нативной цепочкой этапа85. Этап91 проверяет новый реальный потребитель с подготовленной runtime definition; единый новый запуск raw Creatures → definition → portal spawn не выполнялся.

Практическое имя свойства для нашего редактора: «Смещение выхода после анимации портала», X/Y в единицах 1/4096 клетки. Это не абсолютная координата карты и не выбор портала. Z нельзя обнулять автоматически: у тройки есть другие потребители, их правило высоты отдельно не установлено. В этом callback не найдено новой проверки границ перед position→tile; произвольное смещение не гарантирует попадание внутрь карты.

Текущий исходный Creatures содержит, например, Vampire ID8: `(77,5301,0)`, Rogue ID24: `(−3999,56,0)`, Imp ID1: `(0,0,0)`. Эти байты и SHA файла сохраняются в машинной схеме; это данные данной установки, не универсальные значения любой версии.

```python
from native_portal_offsets import DX, view, patch_signed
print(view(raw_creature_record, DX))
changed_record = patch_signed(raw_creature_record, 'x', 4096, DX)
```

API принимает только изученные размеры записи 5449/5537 и точный DX SHA для интерпретации. `patch_bits` сохраняет произвольные unsigned32-биты; `patch_signed` принимает signed32. Остальные байты, расширение записи и длина сохраняются. Проверены 3734 представления записей, 738 точечных пересборок целых контейнеров из 82 источников и 8 отказов некорректным входам. Это проверки нового API; они не пересчитывают прежние 5904 проверки этапа85 как новые.

Этап91: 14 сценариев, 84 выполнения оригинального кода, 14 полных образов существа. Код и vtable игры не заменялись; GFX/sound — явно подготовленные внешние providers, range-checked OS probe поставлен, но не вызывался. Исходные игровые файлы и EXE не изменены.
