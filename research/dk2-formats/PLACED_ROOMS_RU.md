# Things CC: свойства существующих комнат

Этап39, 26 октября 2026. CC — дополнительная запись для уже существующей клетки/комнаты. Исследованный callback игры сам комнату не создаёт. Поле baseline RoomType содержит **TerrainId**, а не RoomId каталога Rooms: например, Portal имеет TerrainId12 и RoomId3; Dungeon Heart — TerrainId14 и RoomId5. Соответствие проверено в самостоятельных Terrain.kwd и Rooms.kwd.

## Запись и преобразование

Envelope8: `tag:u32=204 (CC)`, `payloadBytes:u32=20`. Далее payload:

| Смещение | Байт | Назначение |
|---|---:|---|
| `00/04` | 4+4 | X/Y клетки, DWORD bit patterns |
| `08` | 4 | Неизвестный Z; game placement использует0 |
| `0C` | 2 | Неизвестные flags; converter делает OR в intermediate |
| `0E` | 1 | Direction; правила зависят от типа |
| `0F` | 1 | Неизвестный байт; converter не копирует |
| `10` | 2 | InitialHealth, unsigned WORD; правила зависят от типа |
| `12` | 1 | TerrainId selector, baseline RoomType |
| `13` | 1 | PlayerId; game здесь только проверяет неноль |

Парсеры `5708A0`/`430FA0` для длины, отличной от20, сначала обнуляют20-байтовый буфер, затем читают объявленную длину. Верхнего ограничения нет; oversized path не исполнялся. Диагностический API разрешает только0..20 и дополняет нулями, сохраняя физическую длину исходной записи для patch.

Intermediate44: шесть presence DWORD0..14; XYZ18..20, flagsWORD24, directionBYTE26, healthWORD28, terrainBYTE2A, playerBYTE2B. BYTE27 остаётся от инициализации; raw0F не переносится. Оба полных parser обнуляют intermediate. Standalone converter `42FC20` делает OR flags и оставляет BYTE27 из seed.

## Применение в игре

`521420` при PlayerId0 возвращает1 сразу, до position и checksum. Иначе вычисляет центр X/Y Q12, Z0, вызывает проверку позиции world virtual200. После ненулевого результата получает tile через1D4, передаёт intermediate44 checksum helper, проверяет `tileWORD2 & 0FFF` и разрешает существующий room entity через `4559B0`/таблицу6EE540.

Обрабатываются только три селектора:

| TerrainId | Действие |
|---:|---|
| 12 Portal | При health!=100 вычисляет delta здоровья и вызывает4E5300; health100 пропускает вызов |
| 14 Dungeon Heart | Передаёт полный healthWORD в4DB700, который создаёт/обновляет объекты сердца |
| 37 Hero Gate3×1 | Direction0/2/4/6 записывают orientationDWORD9B=0/1/2/3, затем вызывается refresh4EF6C0 |

Для других значений Direction ворот3×1 старый orientation сохраняется, refresh всё равно вызывается. Названия NORTH/EAST/SOUTH/WEST остались baseline-подписями; независимо подтверждены значения и их числовое преобразование, не мировая ориентация севера.

Селекторы33/34/40 и прочие в этом callback ничего не применяют. Это не утверждение об отсутствии самих комнат в игре: их создание и другие свойства берутся из других путей, включая клетки карты. Selector не сравнивается с фактическим типом найденной комнаты. Raw PlayerId не назначает нового владельца; он служит только проверкой ненулевого значения в этом callback.

Для портала используется current room healthDWORD35. Вычисления учитывают переполнение32 бит: `p=signed32(low32(current*(100-rawHealthWORD)))`; затем signed multiply константой−1374389535, верхняя половина64-битного произведения, арифметический сдвиг5 и поправка к нулю. При обычных значениях это отрицательное усечённое процентное уменьшение. Значения health>100 могут давать положительную delta. Проверяется аргумент health helper; полное конечное здоровье, death/rebuild и cap-ветви helper не моделировались.

## Что делает редактор

Callback `492030` сначала требует совпадения raw TerrainId с байтом terrain plane950 по X/Y и ширине990. При несовпадении возвращает1 без применения. Далее находит модель игрока по raw PlayerId через488850.

- Portal12 и Hero Portal40: настоящий4226B0 добавляет/находит20-байтовую запись с XY,Z0,flags0,direction0,health100,типом и ID модели игрока. При наличии health major1 сохраняет100; другие версии копируют **low8(rawHealthWORD) в WORD**, без clamp100. Например,300→44,65535→255.
- Heart14: X/Y сохраняются в player2C/30, полный healthWORD — в player34; major1 не меняет это правило.
- Gate33/37: настоящий422C20 добавляет/находит запись с health100; исходное health игнорируется. Callback копирует полный DirectionBYTE и принудительно назначает model PlayerId=1.
- Selector34 в проверенном callback не имеет применяющей ветви.

Новые portal/gate add routines не назначают локальный BYTE0F. Это не гарантированное нулевое padding. При проверке editor callback исключён ровно этот один байт свежесозданной записи; проверены все256 байт player model и остальные19 байт каждой записи. Исполнялись реальные terrain/player lookup, add/find/resolve с заранее выделенными массивами; heap growth/GUI не проверялись.

## Сохранение и риски потери данных

Полный writer4947C0 в конце проходит player models:

- Главную запись Heart пишет только при playerID>=3. Serializer4225A0 выводит XY,Z0,flags0,direction0,полный healthWORD,terrain14,playerID. **BYTE0F не назначается**: в контролируемых прогонах полного writer остаётся seed00/A5/FF.
- Portal arrays пишет как20 исходных модельных байт. Если healthWORD==0, **сначала меняет модель на100**, затем пишет. Остальные поля, включая Z/flags/opaque0F, передаёт как есть.
- Gate arrays пишет как20 байт без такого исправления здоровья0.

Таким образом, нельзя описывать сохранение всех CC одной нормализацией Z/flags или здоровья. Наш codec сохраняет envelope и полный исходный payload; native editor projections доступны отдельно и применяются только по явному выбору совместимости.

## Набор данных и проверка

В110 Things файлов, включая AutoSaveThings, найдено858 CC payload20: Heart230, Portal195, Gate2×2 252, Gate3×1 167, selector34 —6, Hero Portal8. Все координаты в пределах парных карт; у всех858 raw selector совпал с terrain клетки. PlayerId0 отсутствует. Значения health, отличные от100, встречаются у9 Heart: пять0, два1, два50. Порталов с health0 в исходном наборе нет — мутация подтверждена синтетическими native fixtures.

Raw Z/flags у всех0. **BYTE0F ненулевой у586 из858 записей**, встречаются12 значений. Его происхождение не доказано; это наблюдение исключает безусловное обнуление поля.266 записей имеют тип без применяющей ветви данного game callback; это не обоснование удалять их из карты.

`phase39-validation.json`:136 эмуляций —18 parser,3 converter,67 полных game callback,35 полных editor callback,3 heart serializer,10 полных Things writer.419 API/boundary проверок,15444 точечных изменения в памяти с точным сравнением всего контейнера,110 parse→pack без изменения.3049 инструкций,26 повторных disassembly/26 live Ghidra ranges совпали с PE. Исходные17 основных данных и два EXE сохранили хеши. Полного gameplay/визуализации комнат с изменёнными данными не было.

Машинная схема — `placed-room-semantics.json`, компонент50 `placed_room_semantics`. Код — `native_placed_rooms.py`; воспроизводимые проверки — `emulate_placed_rooms.py` и `audit_placed_rooms.py`. Неизвестными остаются назначение rawZ/flags/BYTE0F и поведение других путей игры. Этот этап уточняет ограничения конкретных callbacks и writer, а не объявляет всю систему комнат расшифрованной.
