# KeeperSpells: массив определений, дубликаты и режим обновления, этап 83

Продолжение этапа 84 — `KEEPER_UI_ORDER_RU.md`: граница предыдущего этапа о последствиях DB в интерфейсе расширена. Полная raw→array→UI→Session композиция подтвердила пропуск CreateGold при совпадении DB9 в двух Qz-картах,поведение вкладки и выбранный ID в очереди. 28 новых сценариев учитываются отдельно от41 этапа83. Реальное окно/мышь и исполнение действия миром остаются вне проверки;C8 не получило назначения.

В точном `DKII-DX.exe` выполнена новая композиция: настоящий конструктор определения, raw-конвертер и загрузчик массива `51FCD0`, затем оригинальные методы поиска и обхода. Проверен 41 сценарий: 29 загрузок и 12 наборов вызовов методов массива. Внутри них выполнены 33 пары raw-init/converter и 38 вызовов callback загрузки. Прежние отдельные проверки этапов 44/72 не считаются новыми сценариями.

Игровое назначение DWORD `C8` **не установлено**. Новый результат уточняет, как определения собираются в памяти, выбираются при дубликатах и обновляются. Машинная схема — `keeper-array-semantics.json`, встроенная в `keeper-pipeline-semantics.json.phase83_runtime_array`. Итоги проверки — `phase83-validation.json`; общий пакет сохраняет 67 компонентов.

## Файл, промежуточная запись и массив игры

Запись `KeeperSpells` занимает 406 байт, её native-промежуточное представление — 526, определение игры — 122. В проверенной композиции `56B990` инициализирует intermediate, `56BAB0` преобразует полный raw, а `51FCD0` вызывает настоящий scalar-loader `4F7CE0`. Начальная ёмкость массива выделена стендом; потоковый парсер, создание всего World и heap allocator здесь не исполнялись.

| Поле World | Назначение в этой цепочке |
|---|---|
| DWORD `1604` | Указатель на массив определений |
| DWORD `1608` | Ёмкость |
| DWORD `160C` | Число принятых определений |
| DWORD `1610` | Сумма runtime-checksum определений |
| DWORD `A3C7` | Ненулевое значение выбирает обновление по ID вместо вставки |

ID находится в BYTE raw `EE` и BYTE definition `75`. Все смещения в документе шестнадцатеричные.

## Обычная вставка

При `count < capacity` загрузчик идёт от конца массива и сдвигает вправо полные 122-байтные определения, пока предыдущий ID больше либо равен новому. Затем загружает определение в получившееся место и увеличивает count. Поэтому последовательность входных ID `[7,1,3]` даёт runtime `[1,3,7]`. Это порядок массива игры; физический порядок записей файла остаётся самостоятельным свойством.

Равные ID не объединяются: новая запись вставляется **перед** равными. При этом последующий getter `50DD60` не реализует универсальное правило «брать последнюю запись». Как ранее установлено, поиск начинает с `min(ID−1,count−1)` и идёт назад.

В новых полных проверках:

- После вставок ID 3 с разными C8 перед существующим ID 7 массив содержит два ID 3. Getter выбирает первое поступившее значение `FE0C0000`, хотя более новое `FE0C0001` физически находится перед ним.
- Для двух новых ID 1 перед старым ID 1 getter начинает с нулевого элемента и выбирает более новое значение `FE0C0001`.
- Вставка физического ID 0 разрешена callback, однако getter по ID 0 возвращает NULL. Эти факты не оправдывают автоматическую перенумерацию файлов.

Если ёмкость исчерпана, callback возвращает **1**, пропуская scalar-loader и вставку. Массив, count и сумма не меняются. При capacity=1 и входе `[7,1,3]` принимается только 7; два следующих вызова тоже возвращают 1. Поэтому успех этого callback не доказывает, что все записи приняты. Для собственного редактора это основание проверять размеры и количества, сохраняя исходные данные и явно сообщая о противоречиях.

## Частичное представление и начальные байты

Внутри обычной вставки нет вызова конструктора для нового места. Scalar-loader накладывает поля на байты, уже находившиеся в этом месте массива. При сдвиге туда могла остаться копия соседнего определения. Поле с отсутствующим presence сохраняет прежние байты места.

Отдельные контролируемые intermediate с присутствующими только ID и C8 показали это на всех 122 байтах. При снятом presence C8 новый ID 3 унаследовал `12340001` из прежнего места ID 7. **Обычный конвертер полной 406-байтной записи устанавливает все 30 presence-флагов**; частичный опыт не означает, что такая наследственность возникает при каждом обычном KWD.

Настоящие `4F7C70/504D60` обнуляют definition `00..35` и `3A..79`, но не DWORD checksum `36`. В опытах с конструктором этот DWORD сохранял начальные байты буфера. Это описание инструкций, а не гарантия его значения в реальной выделенной памяти.

## Обновление по ID и отсутствие проверки NULL

При ненулевом World `A3C7` callback вызывает оригинальный World `v110=50DD60`, затем scalar-loader для найденного адреса. Count, capacity и агрегат не изменяются.

Между getter и scalar-loader **нет проверки NULL**. В трёх специально подготовленных случаях отсутствующего ID, включая ID 0, loader записал рассчитанные поля определения в контролируемую область низких адресов: в частности checksum по `36` и C8 по `3A`. Callback завершился с 1.

Это проверка пути машинного кода в эмуляторе. Живая игра не запускалась и настоящий краш не вызывался. Не установлено, какие комбинации режима обновления, checksum-gate и отсутствующих ID достижимы через обычную загрузку или редактор. Нельзя автоматически приписывать этот результат ошибке сохранения редактора либо объяснять им любой наблюдавшийся краш.

## Суммы

При `DWORD 6FCDCF == 0` scalar-loader складывает все 526 unsigned-байт intermediate в checksum определения `36`. При другом значении сохраняется прежний DWORD. Обычная вставка прибавляет итоговый checksum в World `1610` по модулю 2³². Ветка обновления возвращается раньше этого прибавления. Ранее для этого была статическая схема `catalogue-checksums.json`; теперь ветви проверены в композиции с массивом.

Это runtime-суммы. Они не заменяют поля количества/размеров в raw-заголовке и не означают произвольный CRC или криптографический хеш. DWORD C8 сохраняется целиком.

## Методы обхода и служебный байт DB

Подтверждены исходные World-vslots:

| Слот | Метод | Контракт |
|---|---|---|
| `FC` | `50DC80` | ID первого физического runtime-элемента либо 0 |
| `100` | `50DCA0` | Следующий ID с переходом с конца на начало |
| `104` | `50DD00` | Предыдущий ID с переходом с начала в конец |
| `108` | `50DDD0` | ID по полному DWORD-индексу, вне диапазона 0 |
| `10C` | `50DE50` | Проверка ID; в новом этапе только статический контекст |
| `110` | `50DD60` | Адрес определения по ID; полные прежние и новые составные проверки |
| `120` | `50DE00` | ID первой строки, у которой BYTE definition `6C` равен полному DWORD-аргументу |

Пять методов, возвращающих ID, имеют значимый **AL**; верхние биты EAX могут остаться от указателя или арифметики. Нельзя безусловно трактовать весь EAX как возвращённый ID. Аргументы next/previous обрезаются до BYTE, индекс остаётся DWORD. В `v120` байт поля расширяется до unsigned DWORD и сравнивается со всем аргументом: `2A` и `0100002A` не эквивалентны.

Цепочка служебного поля: raw BYTE `DB` → intermediate BYTE `153` → definition BYTE `6C`. Его базовое название `OrderInEditor` сохранено; новое доказательство устанавливает поиск byte→ID, а не придумывает игровую приоритетность.

В 82 файлах, содержащих 1066 записей KeeperSpell, нет физических ID 0, дубликатов ID или неупорядоченных списков ID. Однако два файла имеют повтор служебного порядка 9:

- `maps/Battle for the Sun Qz2Globals.kld`;
- `maps/Battle for the Sun QzGlobals.kld`.

В обоих порядок 9 задан для **Raise Dead, ID 9**, и **Create Gold, ID 13**; порядок 10 отсутствует. Две реальные неизменённые записи первого файла прошли native-конвертацию и вставку. Настоящий `v120(9)` вернул ID 9, а `v120(10)` — 0. Это неоднозначность конкретного lookup по служебному порядку, не дубликат ID. Какая видимая команда интерфейса использует этот вызов, данным этапом не установлено. Исправлять эти файлы автоматически нельзя.

## Новый поиск C8 и границы

Новый индекс берёт обращения к самому World-массиву `1604`, которые прежний поиск только по возвратам getter не охватывал. В DX найдено 18 совпадений: методы обхода/поиска, обнуление, выделение, удаление, вставка и четыре операции LEA в другом контексте встроенных resource-map. Один лишь одинаковый displacement не устанавливает тип объекта.

Отдельно в старом точном EXE получены 18 пока нетипизированных кандидатов из локальных PE-байтов. Новый этап не выдаёт их за старые native-проверки. Headless-сервер сейчас открыл только DX; команды открытия других программ требуют GUI. Это ограничение сохранено в доказательствах, исследование DX продолжено без перезапуска.

Игра копирует C8 при загрузке и сдвиге определения и сохраняет его при отсутствии presence. Это всё ещё хранение, а не установленное игровое назначение. Поиск ограничен литеральным `1604` и линейным декодированием; он не доказывает глобальную неиспользуемость C8.

Все исходные инструкции и World-vtable сохранены. Каждый из 41 запусков сравнивает полный World, весь массив заданной ёмкости, 256 соседних байт, raw/intermediate, низкоадресный guard, globals, результаты и sound-counter. Дополнительно считываются первые 128 байт массива через XMM; это не выдаётся за полный дамп массива. 20 диапазонов функций и один диапазон vtable повторно считаны после всех запусков и совпали с исходным PE.

Для 82 исходных файлов выполнены 246 точечных DB-пересборок и 82 явные перестановки полных записей в памяти. За пределами выбранного изменения все байты, неизвестные области, заголовки и остальные секции совпали. Файлы и четыре EXE сохранили хеши. Реальные ресурсы/звук, heap-выделение массива, игровой интерфейс, cast/tick и renderer остаются за границами этого этапа. Общая цель и неизвестное назначение C8 не закрыты.

Воспроизведение: `scan_keeper_array_roots.py`, `native_keeper_array.py`, `emulate_keeper_array.py`, `prepare_keeper_array_primary.py`, `build_keeper_array.py`, `build_format_package.py`, `audit_keeper_array.py`. Конкретные native-входы и результаты — `phase83-keeper-array-emulations.json` и перечисленные там файлы `ghidra/phase83-emulation-keeper-array-*.json`.
