# Выбор комнаты при блуждании существа: этап 145

Для точного предоставленного `DKII-DX.exe` подтверждена дополнительная ветвь
состояния 87: выбор цели внутри комнат владельца. Это дополняет
`WANDER_TARGET_PATH_RU.md`, где список комнат был пуст.

## Подтверждённый порядок

Функция `480A00` расходует `RNG(8)` из общего `World+15A0`. При результате 0
она рассматривает список комнат владельца: голова — `Player WORD+36`, следующая
комната — `Room WORD+8`, разрешаемый через таблицу `6EE540`.

Первый проход считает комнаты следующих ID:

| ID | Исходное имя Rooms.kwd |
|---|---|
| 1, 2, 4 | Treasury, Lair, Hatchery |
| 6, 7 | Library, Training Room |
| 9, 10 | Guard Room, Work Shop |
| 11, 12 | Prison, Torture Chamber |
| 13, 14 | Temple, Graveyard |
| 15, 16, 26 | Casino, Combat Pit, Crypt |

Проверены все 26 исходных ID. Список основан на runtime-байте комнаты `+18`;
файловый RoomId — байт `+392`. Происхождение ID через загрузчик и создание
комнат подтверждено раньше, в этапах 138/139. Здесь узлы комнат подготовлены
явно: это не новый запуск полного загрузчика/фабрики комнат.

**Выбор между комнатами не является случайным в этой функции.** Во втором
проходе счётчик начинается с полного числа подходящих комнат и уменьшается
на каждой из них. Проба клетки начинается, когда счётчик достигает нуля:
то есть с последней подходящей комнаты по порядку списка.

Если проба не удалась, счётчик остаётся нулевым. Поэтому далее пробуются и
следующие узлы из первоначально исключённых типов. Ранее пропущенные комнаты
повторно не рассматриваются. Если успеха нет, начинается прежний поиск по кольцу.
Это точное поведение исследованного кода; назначение такого алгоритма автором
и поведение полного жизненного цикла комнат отсюда не выводятся.

## Воспроизводимые примеры

При существе в клетке `(10,10)` и аргументе радиуса `1`:

| Список комнат | Результат |
|---|---|
| Treasury с клеткой `(3,3)`, затем Lair с `(20,20)` | Выбран Lair `(20,20)` |
| Те же комнаты в обратном порядке | Выбран Treasury `(3,3)` |
| Доступный Treasury, затем пустой Lair | Treasury не пробуется; переход к кольцу |
| То же, затем Portal ID3 с `(24,24)` | Portal даёт цель, хотя исключён первым фильтром |
| То же, затем пустой Heart ID5 и Bridge ID8 с `(24,24)` | Пробуются оба следующих узла; выбран Bridge |

Таким образом, радиус аргумента функции не ограничивает расстояние до комнаты
в этой ветви. Это не устанавливает смысл файлового `WanderRadius`.

## Выбор клетки и дальнейший путь

Оригинальная `4E8430` начинает с координат комнаты `BYTE+2D/+2E` и проходит
цепочку клеток: `WORD+4` клетки содержит следующие X/Y, `(0,0)` завершает
список. Считаются клетки, для которых обе `454110` и `454230` возвращают 0.
Затем один `RNG(count)` выбирает клетку при повторном проходе. Три возможных
результата для трёх клеток воспроизведены разными исходными seed.

Выход — центр клетки в Q12, `Z=0`. Внешняя функция также проверяет отсутствие
блокирующего объекта через настоящую `453600`. В текущих сценах объектные
цепочки пусты; ветвь отказа из-за такого объекта ещё не исполнена.

Три дополнительных исполнения состояния 87 включают настоящую инициализацию
AI/NAV, выбор комнаты, случайную поправку внутри клетки и запрос пути.
Два открытых сценария переходят в состояние 6 с продолжением 87; полностью
заблокированный NAV отклоняет путь, сохраняя 87. Координаты самого существа
при этом не меняются: проверено принятие пути, не физическое перемещение.

## Доказательства и ограничения

- 38 новых сценариев: 35 отдельных выборов цели и 3 полных callback состояния 87.
- Все 26 исходных типов комнат, порядок/отказ/последующие исключённые типы.
- 6 независимых исполнений Ghidra с полным сравнением подготовленной памяти.
- Сверены дополнительные полные функции и таблицы с исходным EXE;
  прежнее покрытие этапа 144 проверено по хешам и байтам.
- 26 точечных пересборок `RoomId` на копиях исходных записей, с обратной правкой
  и проверкой всех остальных байтов контейнера. Диагностические ID с высоким
  битом не предлагаются для использования игрой или изменения ссылок.
- Исходные игровые файлы и EXE не менялись.

В успешной ветви комнаты значения instance `BYTE+418` 0 и 255 дают одинаковые
цель, RNG, запрос пути и конечную память, кроме самого байта. Во всех 38 принятых
сценариях чтения этого байта нет. Его игровые единицы и назначение остаются
неизвестными; глобальная неиспользуемость не доказана.

Первоначальная проверка заблокированного NAV имела отсутствующую запись
Terrain-cache и чтение `NULL+17B` из отображённой нулевой страницы. Этот контекст
исключён. Финальные 38 сценариев содержат явную ненулевую floor-definition
и пропускают на нулевой странице только настоящие обращения `FS:[0]`.
Это исправление тестового окружения, не обнаружение сбоя самой игры.

Комнаты, их списки и Terrain-definition подготовлены в памяти; обычный World
планировщик, изменения списков при слиянии, специальные режимы клеток и весь
жизненный цикл движения не исследованы этим набором. Общая готовность цели
остаётся около 75%.

Машинная спецификация: `room-wander-semantics.json`. Запуски:
`emulate_room_wander.py`, `crosscheck_room_wander.py`;
итоговая проверка: `audit_room_wander.py`.
