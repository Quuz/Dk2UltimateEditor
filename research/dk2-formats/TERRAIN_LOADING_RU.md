Обновление этапа99: Terrain rawDWORD190→definition17B→навигационный байт теперь проверен20 native-композициями,включая8raw-loader цепочек. См. `NAVIGATION_MAP_RU.md`. Продолжение этап74 — `TERRAIN_CACHE_RU.md`:44 native-композиции уточняют ordinal enumeration,глобальный кэш и выбор определения для света. Getter возвращает прямой слот;перечисление — отдельная операция,пропускающая слот0. Полный allocator/parser этим этапом не исполнялся. Unknown198/224 остаются открытыми.

Этап58, 27 октября2026. Исследован предоставленный `DKII-DX.exe`, SHA-256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a`. Проверены настоящие инструкции загрузчика в Ghidra EmulatorHelper. Назначения Terrain+`0x198` и+`0x224` в игровом процессе остаются неизвестными.

## Подтверждённый путь двух полей

| Файл | Промежуточная структура | Флаг присутствия | Игровое определение |
|---|---|---|---|
| WORD+`0x198` | WORD+`0x250` | DWORD+`0x30` | WORD+`0x183` |
| DWORD+`0x224` | DWORD+`0x2DC` | DWORD+`0x98` | DWORD+`0x1B5` |

Полная цепочка: parser`56F090` → initializer`56EB60` → converter`56ED20` → callback`51EB50` → loader`4F66E0` → getter`508DD0`. Все биты обоих значений проходят без нормализации. Проверены нули, старшие биты, `FFFF` и `FFFFFFFF`. Масштаб `/4096`, установленный ранее для модели редактора, в игровом loader отсутствует. Это подтверждает хранение, но ещё не определяет игровую единицу измерения или знаковость потребителя.

В восьми отдельных полных вызовах loader проверены флаги присутствия0/1/2/FFFFFFFF: ноль сохраняет прежнее значение, любое проверенное ненулевое значение заменяет его. Это отличается от короткой записи: при stride548 parser обнуляет552-байтный сырой буфер, читает548 байт и converter помечает отсутствующий хвост+224 присутствующим нулём. Поэтому хвостовое поле заменяется нулём.

## ID, счётчики и повторные записи

Определение хранится в слоте `array + 460 × TerrainId`. Getter маскирует свой DWORD-аргумент до младшего байта и возвращает адрес слота. Он не проверяет число загруженных записей и не проверяет ID внутри слота. Проверены0,1,3,7,22,255,256,511,FFFFFFFF, включая незаполненные слоты. В испытаниях таблица заранее выделена на256 слотов; это не означает, что реальный allocator всегда выделяет столько.

Header callback добавляет N к world+15A8. Обычный callback увеличивает world+15AC на каждую запись, включая повторный ID. Последняя запись с одинаковым ID заменяет определение в том же слоте, но контрольные суммы обеих загрузок уже добавлены в world+15B0. При update mode(world+A3C7≠0) определение меняется, счётчик загрузок и общий аккумулятор остаются прежними.

При обычной загрузке флаг80 выбирает ID воды(world+9BAE),100 — лавы(9BAF). Последняя запись с соответствующим флагом выигрывает. Если позднее тот же ID перезаписан без флага, старый выбор не очищается. Два отдельных прогона подтвердили случай: ID7 с80, ID3 со100, затем ID7 без обоих флагов; итоговые выборы7/3 сохраняются. В update mode callback возвращает управление до выбора воды/лавы: прежние ID201/202 в испытании остались неизменны, хотя определения получили другие флаги.

## Что означает контрольная сумма

При global6FCDCF=0 DWORD+84 определения равен сумме **736 байт промежуточной структуры**, включая флаги присутствия и преобразованные поля. Это не сумма552 байт записи. При ненулевом global прежний DWORD+84 сохраняется.

Два полных прогона получили одинаковую сумму при разных значениях:

| Вариант | WORD raw198 | DWORD raw224 |
|---|---:|---:|
| A | `01FC` | `01000000` |
| B | `02FB` | `00010000` |

В обоих случаях сумма байтов WORD равна253, DWORD —1. Итоговые промежуточные структуры и игровые определения различаются, а checksum и аккумулятор world совпадают. Для проверки совместимого редактора нужно сравнивать все байты; совпадение суммы не подтверждает совпадение содержимого.

Полный constructor4F6570 с13 настоящими resource initializer504D60 также проверен на отдельном буфере. Он обнуляет оба неизвестных поля, но не DWORD84; в1CB очищает два младших бита, сохраняя остальные. Начальное заполнениеA5 — условие испытания, а не утверждение о реальном состоянии памяти allocator.

## Проверки и границы

32 прогона:24 полные parser→callback→loader цепочки и8 полных частичных загрузок. Каждый дополнительно выполняет constructor и9getter вызовов, всего288lookup. Побайтово сравниваются256×460 байт определений, весь world размеромA3CC,736 байт intermediate,16 байт состояния адаптеров,460 байт constructor и входной поток.11 полных функций после эмуляций повторно прочитаны из Ghidra и сверены с PE. Среди них регистрация callback проверена статически; не все11 функций выполняются в каждой цепочке.

Файловое чтение заменено ограниченным буферным адаптером: до REP проверяются начало/конец потока и размер≤552. Звуковой provider возвращает тестовые handles; ветка дополнительного вызова для ID22 проверена. Графический provider равенnull, ресурсные дескрипторы пусты, специальные ветки flags1000/2000 исключены. Настоящий renderer, звук, запуск игры и полный GUI редактора не проверялись.

В82 исходных файлах3306 записей проверены точная пересборка и6612 отдельных изменений unknown198/224. Для каждого изменения собранный файл сопоставлен с независимой заменой только выбранных2/4 байт. Исходные файлы и четыре EXE сохранены неизменными.

`terrain-catalogue-validation.json` вложен в существующий компонент `terrain_lighting_semantics` как `phase58_complete_loading`; пакет остаётся из67 компонентов. API `native_terrain_catalogue.py` предоставляет исследовательские проекции загрузки и `patch_unknown` для явной замены неизвестного поля без изменения остальных байтов.
