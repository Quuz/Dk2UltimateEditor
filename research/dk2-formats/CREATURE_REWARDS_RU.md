# Храм: успешная награда существом — этап 90

Для DX SHA-256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a` выполнены оригинальные конструктор, factory, initializer существа и храмовый обработчик. Подтверждены создание, назначение уровня, позиция, владелец и включение в список обитателей комнаты. Машинная спецификация: `creature-reward-semantics.json`; компонент пакета: `creature_reward_semantics`. Ранее опубликованные 68 компонентов сохранены побайтово.

## Что происходит с наградой

`4F1780`, ветка типа 1, извлекает ID существа из младшего BYTE значения награды и запрошенный уровень из BYTE по битам 16–23. Владелец берётся из WORD комнаты по `+1D`. После успешного создания игра вызывает `48B120` ровно `requestedLevel−1` раз, если уровень больше 1, затем `48AD30(6A)` запрашивает переход AI.

В проверенном стенде с живым существом и положительным HP:

| Запрошенный BYTE уровня | Результат |
|---|---|
| 0, 1 | 1 |
| 3 | 3 |
| 10, 11, 255 | 10 |

Ограничение 10 находится в оригинальной `48B120`. Это не правило нормализации сохранённого DWORD: исходные биты файла надо сохранять. Значения `00030008` и `FE03AB08` дали одинаковые полные экземпляры существа ID 8 третьего уровня. Из этих примеров нельзя выводить семантику произвольных битов в других видах награды.

В новой композиции сырой 16-байтовый рецепт type43 «Creature16 → Creature8», значение 8, проходит `51DB30 → 50F7E0`; оригинальные `4F1600/4F1660` обрабатывают жертву третьего уровня и получают значение `00030008`; затем выполняются награда, создание, повышение уровня и вход в комнату. Все 1343 байта полученного существа совпали с прямым runtime-сценарием. Усреднение, BYTE-переполнение суммы уровней и сложение уровня со старым DWORD описаны отдельно в `SACRIFICE_RU.md` и этим результатом не заменяются.

Точка награды выбирается `4E4D90` внутри комнаты; высоту предоставляет `World vslot1D4 → 4545C0`. Клетка (5,6) в стенде даёт XYZ `5800h/6800h/1000h`. Переданная мета-точка `9800h/A800h/3000h` не стала позицией появления. Это храмовый путь; он не доказывает порядок первого выхода из портала.

## Вход в храм и заполненная комната

Оригинальные `4798F0` и `47BBE0` действительно инициализируют таблицы категорий и состояний AI перед наградой. После выполнения сравниваются все 2048 байт таблицы категорий и 7025 байт таблицы состояний с независимыми проекциями инструкций. Таблица состояний изначально заполнена A5; исходные байты категорий совпадают с PE. Обработчики и vtable не заменяются.

`476D30` вызывает обработчик входа категории 12 — `47B8C0`. Он разрешает низшие 12 бит WORD клетки по `+2` в комнату, проверяет принятие существа (`4E7F80`) и вызывает `4E5A70`. Для храма вместимость проверяется через `4E53B0`: `used WORD+6B + CreatureDefinition BYTE+672 <= capacity WORD+67`. При успехе существо добавляется в список комнаты WORD `+0A`, получает tag комнаты в WORD `+3B9`, а счётчики `+6B/+6D` увеличиваются на требуемую вместимость.

При вместимости 100 и расходе 1 подтверждены состояние `6A`, tag комнаты 200, голова списка 100 и оба счётчика 1. При вместимости 0 награда **всё равно создаётся**, но состояние остаётся 1, tag комнаты — 0, список и счётчики комнаты не меняются. История жертв в обоих случаях уже очищена. Поэтому факт вызова `48AD30(6A)` нельзя выдавать за безусловно установленное состояние.

## Экземпляр и создание

Реальный конструктор `CCreature` — `4B5E10`, vtable — `66D524`, размер экземпляра — 1343 (`53Fh`) байта. Близкие `4B5CE0` и `4B5D80` не являются этим конструктором. В `4B5A10` статически подтверждены 448 экземпляров с таким шагом: выделение `92E44h`, четырёхбайтовый заголовок и исходный vector-constructor `635EC0` с constructor `4B5E10`. Полное выделение всех 448 экземпляров в этом этапе не эмулировалось.

Стенд выполняет настоящий конструктор одного неиспользуемого экземпляра; его tag 100 регистрирует оригинальная `507850`. Далее `4B78D0 → 4B7900 → 4872A0` извлекают этот экземпляр из свободного списка. Глобальный manager `6E504C` соответствует `World+8`; WORD manager `+1C` хранит голову свободного списка, DWORD `+1E` — число активных существ. Внутри factory новый tag и блок Object pool не выделяются. Подтверждены изменения списка свободных, списка существ мира, владельца, карты и статистики по ID; Object pool и 256 защитных байт после экземпляра сохраняются.

У владельца дополнительно вызывается `4BE330`: DWORD-флаг `+76 |= 200h`, DWORD `+B4F = текущий tick`, DWORD `+B53 = tick + global6F2611 * global6F2590` с обычной 32-битной арифметикой. `4BE180` читает оставшееся время как `end−currentTick`. Более широкое игровое назначение этого таймера пока не названо. `491900/4919C0` расходуют две выборки World PRNG и выбирают значения полей существа `+4ED/+4EF`, учитывая уже имеющиеся значения существ владельца.

Коэффициенты HP читаются как packed WORD по `Variables+E1+2*level`, то есть по нечётным адресам. Коэффициент 150 для уровня 2 действительно дал HP 1500 при базовом HP 1000; коэффициенты 100 сохранили HP 1000. Ранний диагностический стенд заполнял выровненные WORD значением 100, что по нечётному адресу читалось как `6400h`. Этот диагностический результат сохранён отдельно и не является ошибкой игры.

## Проверки и границы

11 самостоятельных сценариев, 66 выполнений оригинальных функций, 11 полных образов по 1343 байта: один factory-сценарий и 10 храмовых. Для каждого образа объединяются шесть детерминированных повторов с одинаковыми входами; это не атомарный снимок живого процесса. Во всех успешных повторах проходят сравнения ожидаемых областей памяти и защитных байтов. 89 полных диапазонов функций и шесть блоков исходных данных сверяются с предоставленным PE; это не утверждение о покрытии всех их ветвей.

Внешние providers явно отделены: GFX A0 — null с пятью аргументами, GFX 90 — null с шестью, sound — фиксированный результат с четырьмя; поставлен range-checked provider системного `IsBadReadPtr`, но в проходящих сценариях этапа 90 он не вызывался. Игровые функции, vtable и обработчики AI не заменяются.

Сырые Creatures → runtime definition в этом этапе не скомпонованы с созданием: definition и коэффициенты подготовлены явно. Полный spell-sacrifice event → callback → Creature также пока не выполнен одной цепочкой. Не проверены дальнейшие tick, выход из храма, реальная графика/речь, полный пул, повторное использование умершего экземпляра и отказ при 448 активных существах. Сохранность точечной правки 44 сырых рецептов подтверждена прежними 1188 проверками этапа 88; здесь они не пересчитаны как новые.

Воспроизведение: `prepare_creature_reward_primary.py`, `ghidra_probe.py phase90-primary-queries.json`, `emulate_creature_factory.py`, `emulate_sacrifice_creatures.py`, `build_creature_rewards.py`, `build_format_package.py`, `audit_creature_rewards.py`. Скрипты эмуляции повторно используют результат только при точном совпадении входов и ожиданий.

Общая цель остаётся открыта: первое появление из портала, потребители бонусов вселения, Objects `34C`, Traps `204`, Doors `236`, Terrain `198/224`, Creature Priority/Jump и другие существенные неизвестные не объявляются расшифрованными.
