# Creatures+0xEE4: Ability Creep Percentage

25 октября2026, этап24. Поле, оставленное в baseline как `Unkee4`, связано с native-подписью **Ability Creep Percentage**. Подтверждены игровые потребители, связь с ростом по уровням и потеря старших битов в Editor Pro.

## Где находится поле

| Представление | Offset | Байт |
|---|---|---|

| Intermediate игры | `0x12D4` |4 |

Это целочисленный процент. Делителя4096 в переносе или использовании этого поля нет. Игра сохраняет все32 бита в converter `0x568E30` и loader `0x492320`. Variables type77, StatId26 через `0x494A70` также записывает все32 бита без деления на TPS или сужения до байта.

## Что оно делает в игре

Найдено11 встроенных участков расчёта в8 функциях: `0x45B140`, `0x45B500`, `0x45B800`, `0x45BAD0`, `0x45BDF0`, `0x45C690`, `0x45CB00`, `0x48EE90`.

Они пересчитывают **взвешенный квадрат XY-расстояния** перед дальнейшими проверками выбора цели/видимости. Это не прямое присваивание скорости перемещения. В семи функциях коэффициент берётся у проверяемого кандидата; `0x48EE90` использует состояние собственного существа, затем проверяет его по радиусу других существ.

Расчёт включается, когда instance flags `+0x3E6` содержит `0x1000`. Собственная диагностика игры `0x490240` прямо называет этот бит `Creeping`. Поэтому название состояния установлено по EXE, независимо от сторонних шаблонов.

Базовая метрика строится из координат в масштабе4096 на тайл:

```text
dx = signed32(targetX - sourceX)
dy = signed32(targetY - sourceY)
D = low32((dx*dx >>12) + (dy*dy >>12))
```

Отдельный квадрат вычисляется через signed64 IMUL и SHRD. Знаковая32-битная разность координат и последующее сужение сохраняются; проекция не заменяет это вычислением float-расстояния.

При Creeping:

```text
level ==1: P = runtimePercentage
level !=1: P = trunc_to_zero(signed32(low32(levelCoefficient * runtimePercentage)) /100)
weightedD = unsigned32(low32(D * P)) //100
```

`levelCoefficient` читается как signed WORD. В последнем делении используется **беззнаковый** результат уже обрезанного32-битного произведения. При обычных положительных значениях это процент от **квадрата** расстояния. При переполнении или отрицательных входных битах нельзя заменять формулу произвольной signed-арифметикой или вещественным умножением.

Примеры при `D=409600`:

- На уровне1, поле50 →`weightedD=204800`.
- На уровне2, поле50 и коэффициент105 →сначала `P=52`, затем `weightedD=212992`.
- Поле0 при активном Creeping →нулевая метрика.
- Без Creeping входная метрика остаётся прежней.

Дальнейший числовой тест радиуса в `0x48EE90` использует строгое `<`: `signed32(weightedD) < signed32(low32(radiusTiles²*4096))`. Равенство отвергается. Другие ветви учитывают также класс существа, текущую ближайшую цель, состояние, владельцев и результат LOS. Полученная формула не заменяет весь алгоритм видимости и не означает буквальные «50% скрытности».

## Рост по уровням и управление состоянием

Уровень — instance byte `+0x403`. Только значение1 пропускает таблицу; остальные значения используют WORD по `[DAT_006E4154 +0x2A3 +2*level]`. Ограничение уровня1..10 в этих фрагментах не установлено; корректность произвольного индекса во всём движке не заявляется.

В обычной инициализации инструкция `0x509A96` устанавливает `DAT_006E4154=0x6F2550`. Native-handler Variables type65 `0x51DC40` для StatId26 записывает тот же адрес таблицы:

```text
0x6F261D +2*(26*9+level)+2 == 0x6F2550+0x2A3+2*level
```

На диске запись type65 содержит4 DWORD: Type, StatId, ValueRaw, CreatureLevel. В таблицу сохраняются low16 ValueRaw, а данный потребитель читает их как signed16. Здесь используется сам коэффициент, а не прибавление100 к его значению.

В предоставленном `GlobalVariables.kwd`: level2=105,3=110,4=115,5..10=120. Среди105 успешно разобранных файлов карт с Variables не найдено записей type65/StatId26. Это не заменяет анализ порядка загрузки конкретного descriptor и всех его ссылок.

Обработчик `0x517310` при ненулевой ссылке player `+0x134` меняет только Creeping-бит существа: `flags=(flags &0xFFFFEFFF)|((actionValue &1)<<12)`. При отсутствии ссылки флаги остаются прежними. Другие биты сохраняются. Полная маршрутизация всех команд здесь не исследована.

В first-person input отдельно виден выбор speed mode2 при Creeping. Функция скорости `0x48ABB0` для mode2 берёт runtime `+0x5BC`, связанный с raw `+0xD37` и native-подписью **Shuffle Speed (Tiles Per Second)**. `+0xEE4` в просмотренном helper скорости не используется. Модификаторы здоровья, Terrain и possession продолжают учитываться другими ветвями.

## Editor Pro обрезает DWORD до байта

Native STRINGTABLE ID`0xF85C` содержит `Ability Creep Percentage`. Путь к панели и обратно подтверждён:

1. Converter читает raw DWORD `+0xEE4` в editor intermediate `+0x12E4`, устанавливая presence `+0x208`.
2. Callback `0x4A01B0` при установленном presence сохраняет только AL в model byte `+0x1740`.
3. Панель переносит этот байт в `+0x1880`; property case`0xF85C` показывает unsigned byte числом.
4. Update-case после `__ftol` сохраняет low8 целого результата. Полный float-парсер и все проверки GUI здесь не эмулируются.
5. Writer `0x4A7F00` выполняет `XOR ECX,ECX; MOV CL,[model+0x1740]; MOV [record+0xEE4],ECX`.

Итог обычной цепочки чтения присутствующего поля и записи: **`savedDWORD = originalDWORD &255`**, даже без обновления этого конкретного свойства в GUI.

| Вход | Игра после converter/loader | Callback → writer Editor Pro |
|---|---|---|
|50 |50 |50 |
|255 |255 |255 |
|256 |256 |0 |
|300 |300 |44 |
|32000 |32000 |0 |
|`FFFFFFFF` |`FFFFFFFF` |255 |

Это отличается от ранее разобранного условного update-case Torture Time To Convert: здесь сужение начинается уже в callback загрузки модели. Если presence не установлен, callback оставляет предыдущий байт модели; типичный converter полного raw-поля presence устанавливает.

Для вашего редактора хранить все4 исходных байта. Числовое свойство можно показывать с native-подписью и отдельно предлагать явную совместимость с байтовой моделью Editor Pro. Само название Percentage не устанавливает ограничение0..100.
