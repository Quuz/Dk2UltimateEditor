# Terrain и Traps: доход маны, предел в секунду и содержание

25 октября2026, этап23. По инструкциям `DKII-DX.exe` установлены игровые потребители ещё трёх WORD. Это дополняет физические схемы файлов; их ширина и исходные байты сохраняются.

## Поля и представление

| Файл/поле | Raw | Intermediate | Runtime определения | Подтверждённое использование |
|---|---|---|---|---|
| Terrain.ManaGain | `0x19C`,2 байта | `0x254` | `0x187` | Знаковая добавка к доходу игрока `+0x10E2` |
| Terrain.MaxManaGain | `0x19E`,2 байта | `0x256` | `0x189` | Знаковая добавка к пределу дохода **за секунду**, player `+0x10DE` |
| Traps.ManaUsage | `0x202`,2 байта | `0x2AA` | `0x96` | Знаковое содержание ловушки: player `+0x10D6`, одновременно вычитание из `+0x10E2` |

Во всех этих потребителях используется `MOVSX` из WORD: `7FFF`→32767, `8000`→−32768, `FFFF`→−1. Исходные `u16` в baseline-схемах сохранены для аудита и хранения битового представления; игровой числовой вид — `s16`.

Назначение подтверждают собственные диагностические строки игры в `0x4BCF10`: `MaxManaGainPerSecond`, `ManaGainPerSecond`, `BasicManaPerSecond`, `MaxMana`, `CurrentMana`. Поле запаса `MaxMana` находится в player `+0x10EA` и участвует в отдельном ограничении текущего баланса. Поэтому Terrain.MaxManaGain нельзя показывать в редакторе как увеличение вместимости запаса маны.

## Смена владельца клетки

`0x4559D0` читает Terrain через глобальный массив `0x6DA4A8` и ID клетки `node+0xA`. В слове `node+8` младшие12 бит содержат индекс владельца; верхние4 бита сохраняются.

При переходе в ветку изменения владельца:

- Если старый владелец ненулевой, оба знаковых параметра Terrain вычитаются из его `+0x10E2/+0x10DE`.
- Оба значения прибавляются новому владельцу, включая индекс0.
- Дополнительно вызывается `0x4BE070`; при числовом режиме4 есть другие побочные вызовы. API этого этапа возвращает только дельты полей маны.

Если владелец совпал, обычная ветка ничего не прибавляет. Однако при ненулевом владельце и установленном бите`0x80` world byte `+0x7239` оба значения прибавляются снова. Это условие присутствует в коде; назначение режима включения флага здесь не устанавливается.

Есть тонкость формального диапазона: сравнение выполняется между старым индексом12 бит и **low16** запрошенного значения, а запись владельца использует только low12. Поэтому запрос `0x1001` при старом владельце1 проходит ветку изменения, хотя записанный индекс остаётся1. Эмуляция проверяет это отдельно. Это описание native-инструкций, не рекомендация разрешать такие индексы в UI.

## Смена типа Terrain и отдельные правила комнат

`0x455B90` при разных старом/новом ID:

1. Если ни один Terrain не имеет ROOM `0x10`, владелец ненулевой и world `+0x7239` не имеет бита`0x40`, обработчик вычитает старый ManaGain и прибавляет новый. Для старого ID0 вычитание пропущено.
2. Если хотя бы один Terrain имеет ROOM, новый ID17 или26 даёт фиксированное`+1`; иначе старый ID17/26 даёт`−1`. Проверки ненулевого владельца и world bit40 в этой ветке нет.
3. Ветка нового специального ID имеет приоритет: переход17→26 здесь даёт`+1`.
4. Если ID одинаковы, изменений нет. При разных ID новый ID записывается в клетку даже в ветках, пропустивших изменение дохода.

**Этот обработчик не пересчитывает player `+0x10DE`.** Его эффект отличается от смены владельца. Это не доказывает, что другие вызовы или дальнейшая перестройка состояния не обновляют предел дохода. Полные цепочки всех вызывающих функций не восстановлены.

## Как ограничивается и начисляется доход

Обозначения:

- `E` — player `+0x10E2`, накопленный доход с уже внесёнными изменениями содержания;
- `B` — `+0x10E6`, BasicManaPerSecond;
- `L` — `+0x10DE`, MaxManaGainPerSecond;
- `C` — результат `0x4C17A0`, сумма расходов с условиями для существ, ловушек и способностей;
- `O` — `+0x10EE`, OneShotManaGain.

Функция `0x4C1770` возвращает:

```text
gross = min_signed32(s32(E + B + C + O), L)
```

В рабочей ветке `0x4C10E0` сначала обнуляются оба OneShot DWORD, затем:

```text
gross = min_signed32(s32(E + B + C_before), L)
delta = s32(gross - C_after)
if delta > 0: delta = s32(delta * ManaIncreaseRate)
```

Helper вызывается дважды. Проекция принимает два результата отдельно и не предполагает, что они всегда одинаковы. Полное вычисление условных расходов и всех вложенных вызовов не эмулируется.

Пример: `E=−10`, `B=100`, оба `C=30`, `L=80`. Gross получается80, после расходов остаётся50. При ManaIncreaseRate2 положительная добавка становится100. Ограничение дохода применяется до вычитания расходов и до множителя. Отрицательная добавка на ManaIncreaseRate не умножается.

Далее есть отдельная ветка числового режима global DWORD `0x75AD4B==3`: setting WORD `0x75AEA7==2` удваивает delta, setting0 выполняет последовательность low32 удвоения, знаковой поправки и `SAR2`. При переполнении это нельзя заменять обычным делением исходной delta на2. Названия режимов по этим двум числам не назначаются.

К текущему балансу `+0x82` прибавляется конечная signed delta с32-битным переполнением. При отрицательной delta код ограничивает только отрицательный результат до0; при неотрицательной — только превышение `MaxMana`. Проекция сохраняет это поведение даже для крайних значений.

Входной таймер проверяет беззнаковое `now >= low32(last_tick + ticks_per_second)`. При равенстве начисление уже разрешено. На обычном пути завершения `last_tick` записывается равным now; ранние выходы и предупреждения остаются за пределами проекции.

## Содержание ловушек

`0x4C1B60` читает определение через `instance+0xF7`, затем signed WORD `definition+0x96`:

```text
player.MaintainTrapManaPerSecond += usage
player.ManaGainPerSecond        -= usage
```

`0x4C1B90` выполняет обратные операции. Поэтому raw`FFFF` в этих обработчиках означает отрицательное содержание и повышает доход при добавлении учёта. Это результат изолированного native-вызова; пригодность такого изменения в полном игровом цикле не проверена.

Учёт вызывается с условиями. `0x4A7CE0` добавляет его только после успешного предыдущего helper и при сброшенном instance `+0x10C` bit`0x20`. `0x4A7B20` снимает его под своим внешним условием и тем же bit-clear. `0x4A96D0` сбрасывает этот бит и добавляет учёт в обеих ветках TriggerType. В `0x4A96A0` remove/add стоят вокруг других helper привязки; их полный смысл здесь не назначается.

Соседний raw`+0x204`/runtime`+0x98` в этих обработчиках не читается. Нельзя переносить на него установленный смысл ManaUsage.

В80 файлах карт проверены3224 Terrain и1261 Traps. Отрицательных значений трёх полей нет. Для Terrain пары gain/ceiling распределены так:

| Gain | Ceiling | Записей |
|---|---|---|
|0 |0 |2981 |
|1 |0 |123 |
|1 |32000 |38 |
|17 |0 |2 |
|100 |100 |61 |
|100 |32000 |19 |

Нулевой вклад клетки в ceiling не означает нулевой общий предел игрока: его формируют и другие источники. В отдельном Terrain.kwd у Claimed Path значения1/0, у Claimed Vault100/100.

`phase23-validation.json`:279 граничных проверок,62 успешные native-эмуляции,1764 точечные пересборки контейнеров в памяти. Состав эмуляций:12 смен владельца,12 смен Terrain,9 gross-income,13 начислений,10 add/remove содержания и6 таймеров. Исходные тела смены Terrain и учёта содержания не менялись; смена владельца использует stub внешнего helper, режим4 отключён. Начисление исполняет исходный арифметический фрагмент с двумя явными результатами cost-helper. Полные обработчики возвращаются в readout-trampoline; арифметический фрагмент передаёт результат через отдельный выходной adapter. Все изменения памяти относятся только к EmulatorHelper.

Пять повторных полных assembly-выгрузок совпали побайтово с доэмуляционными. Сверены23 цитаты и282 инструкции.17 входных файлов и2 EXE сохранили SHA-256. Изменённая игра не запускалась.

Продолжение поиска неизвестных полей: `scan_adjusted_pointers.py` проверил8729 mapped spans и22572 короткие трассы сдвига указателей, получив38 кандидатов пересечения. Это не полноценный межпроцедурный анализ и не доказательство отсутствия потребителей. Назначения Terrain+`0x198/+0x224`, Traps+`0x204` и игровой эффект Objects+`0x34C` остаются неустановленными.

Артефакты для редактора: `mana-semantics.json`, `native_mana_semantics.py`, компонент34 в `editor-format-package.json`. API рассчитывает только описанные ветви и не заменяет состояние всей игры.
