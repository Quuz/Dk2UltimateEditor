## Последние27 байт

В266-байтной записи диапазон `0xEF..0x109` занимает27 байт. Полные converters игры56A560 и Editor Pro42A0D0 его не переносят. При разных хвостах проверенный320-байтный префикс intermediate совпадает. Byte13F остаётся прежним, Flags DWORD124 объединяется с входным через OR.

Writer размещает record по `[frameESP+0x4C]`. Последнее назначенное поле — AlternativeShot BYTEEE, `[frameESP+0x13A]`; следующие27 байт `[frameESP+0x13B..0x155]` остаются прежним содержимым стека. Затем file-write получает все266 байт. Прогоны с заполнением стека00/A5/FF и меняющимся шаблоном подтвердили каждый байт хвоста, включая две последовательные записи.

Вывод относится к именам в пределах32 байт. Реальный helper4AB3B0 копирует всю длину CString: аргумент32 только дополняет короткую строку нулями. Полный writer-прогон с длиной240 подтвердил перезапись первого байта хвоста: имя копируется после scalar/resource assignments. Принятие такого имени GUI не проверялось.

Это устанавливает механизм появления произвольных данных у данного writer. Происхождение каждого исторического хвоста не доказано. **Наш редактор сохраняет все27 исходных байт**, а не обнуляет их.

## Flags DWORDD4

Converter сохраняет32 бита. Model callback4A2260, участок4A2466..4A2474, при presence DWORD4C вызывает decoder41D760. Восемь битов распределяются по model DWORD:

| Бит | Model offset |
|---:|---:|
|01 |184 |
|02 |188 |
|04 |18C |
|08 |190 |
|20 |194 |
|40 |198 |
|80 |19C |
|100 |1A0 |

Encoder41D6F0 считает каждый DWORD логическим ненулевым значением и возвращает только **маску1EF**. Writer пишет DWORD результата. Presence0 оставляет модель прежней; проверены также отрицательные ненулевые DWORD модели.

Игровой смысл остальных битов из нормализации не следует. При правке checkbox наш редактор меняет выбранный бит исходного DWORD; автоматическое применение mask1EF удалило бы неизвестные биты. API `native_spell_writer.patch_flags` сохраняет остальные биты и хвост. Baseline-названия флагов здесь не переименованы.

## N/S/D и пустые слоты

Writer берёт N из context DWORD59C и перечисляет pointer array598:

```text
N @ header+20 = число физических слотов
S @ header+8  =56+266*N
D @ header+52 =266*N
```

Null-pointer пропускается без корректировки этих величин. Полные прогоны `[1,0,2]`, `[0,2]`, `[0]` дали меньше payload-записей, чем объявлено в заголовке. `[2,1]` подтвердил физический порядок. Это требование к целостности native-массива, а не особый допустимый формат. Наш сборщик считает реально сериализованные записи.

Writer с N0 выполнялся, но загрузка такого каталога игрой не проверялась: раннее деление D/N описано в `CATALOGUE_LOADER_LIMITS.md`.
