| Каталог | Запись на диске | Runtime | Converter | Loader | Поиск определения по ID |

| CreatureSpells | 266 | 70 (`0x46`) | `0x56A560` | `0x4F7860` | `0x50DFA0` |

Оба ID — u8. Поиск использует ID записи, а не просто индекс массива. Размер runtime не определяет длину записи файла. Полные границы полей уже находятся в FIELD_LAYOUTS.md; пути переноса — scalar-storage-paths.json.

## AlternativeShot — проверка пригодности цели

Уточнение этапа42: rawE8 Alternative Shot ID иE9 Alternative Room ID имеют подтверждённые native-подписи и model/UI/writer paths, но не игровой replacement rule. Они отличаются от rawEE AlternativeShot predicate. Full loader4F7860 переносит их только косвенно в checksum346, без semantic definition fields. Crossed partial presence, lookup−1/unchecked commit и размер intermediate346 — `SPELL_ALTERNATIVES_RU.md`,63 native cases.320 этапа41 — проверенный prefix, не полный размер.

Raw `+0xEE` → runtime `+0x45`. Диспетчер `0x49A7B0` выбирает одну из шести записей таблицы по адресу `0x6E4AC8`, stride 17. Таблица заполняется `0x49A6C0`. Значения >=6 безопасно отклоняются с возвратом 0; произвольного доступа за таблицу здесь нет.

| Значение | Название OpenKeeper | Callback | Проверенное условие |
|---:|---|---|---|
| 0 | NONE | null | Диспетчер возвращает 0 |
| 1 | HASTE | `0x49A830` | Таймер существа +0x459 равен 0 |
| 2 | HEAL | `0x49A840` | Текущее HP строго меньше половины максимального HP с учётом уровня |
| 3 | ARMOUR | `0x49A8C0` | Категория из 0x478050 равна 0x16 и таймер +0x443 равен 0 |
| 4 | INVULNERABLE | `0x49A8F0` | Та же категория 0x16 и таймер +0x445 равен 0 |
| 5 | INVISIBLE | `0x49A920` | Та же категория 0x16 и таймер +0x44F равен 0 |

Эти callbacks возвращают пригодность цели. Они сами не применяют бафф и не выбирают альтернативный ShotId. У HEAL сравнение строгое: ровно половина HP не проходит. Максимальное HP берётся из определения существа +0x692 и, для уровня выше 1, масштабируется соответствующей таблицей уровня. Категория 0x16 сохранена числом: её полное название здесь не восстановлено.

Два соседних поля имеют другую судьбу:

| Поле | Raw | Intermediate | Результат |
|---|---|---|---|
| AlternativeShotId | +0xE8, u8 | +0x138 | Converter читает, просмотренный runtime loader не переносит |
| AlternativeRoomId | +0xE9, u8 | +0x139 | Converter читает, просмотренный runtime loader не переносит |

В самостоятельном каталоге эти поля ненулевые у ID12 Dark Elf Arrow и ID24 Elf Archer Arrow: `(36,4)`. В двух Globals ненулевая пара осталась у ID45 Wizard Freeze: `(68,0)`. Это не доказательство их использования в игре. Редактор обязан сохранить данные; утверждение ограничено проверенным путём загрузки.

## Неизвестный хвост CreatureSpells

Уточнение этапа41: полный writer4A9730 не назначает эти27 байт при bounded имени и выводит прежнее содержимое стека. Оба full converters проверены с разными хвостами. Найдены также model flags mask1EF и native null-slot count mismatch; подробности и61 native case — `SPELL_WRITER_RU.md`. Для всех исторических файлов происхождение хвоста не установлено; требование сохранять raw остаётся.

Последние 27 байт по raw `+0xEF..+0x109` просмотренный converter не читает. При этом хвост **ненулевой у всех 41/72/72 записей** проверенных наборов. Внутри каждого набора наблюдаются повторяющиеся raw-буферы; у Globals видны и фрагменты текста. Назначение этих байтов не установлено. Их нельзя восстанавливать как 27 нулей на основании названия unused в стороннем парсере.

Аналогично KeeperSpells `+0xE0`, 2 байта, не читается просмотренным converter и сохраняется raw. KeeperSpells.Xc8 по `+0xC8` реально переносится в runtime +0x3A, но потребитель и смысл пока не установлены; новые названия ему не присвоены.

## CastRule и TargetRule KeeperSpells

CastRule: raw `+0xEF` → runtime `+0x76`, таблица `0x6FCDD8`, 6 записей по 17 байт. Инициализатор `0x5174A0`, диспетчер `0x5176B0`.

| Значение | Название OpenKeeper | Callback |
|---:|---|---|
| 0 | NONE | null |
| 1 | OWN_LAND | `0x517B80` |
| 2 | OWN_AND_NEUTRAL_LAND | `0x517CB0` |
| 3 | ENEMY_LAND | `0x517DE0` |
| 4 | ANY_LAND | `0x517F10` |
| 5 | ANYWHERE | `0x517F60` |

Названия не описывают все условия. OWN_LAND вызывает `0x4BF3D0`: для собственного владельца возвращает разрешение, а для другого использует байт союза. Отдельно исключается специальный/нейтральный игрок и проверяются препятствия/комнаты. Это не простое сравнение owner==caster. ANYWHERE непосредственно возвращает 1 из данного callback; остальные проверки применения остаются в вызывающем коде.

TargetRule: raw `+0xDA` → runtime `+0x77`, таблица `0x6FCE40`, 7 записей по 18 байт. Инициализатор `0x517580`, диспетчер `0x517730`. Дополнительный байт +17 возвращается helper0x5177B0 и отделяет режимы с целью-сущностью.

| Значение | Название OpenKeeper | Callback | Цель-сущность |
|---:|---|---|---|
| 0 | NONE | null | нет |
| 1 | OWN_CREATURES | `0x517800` | да |
| 2 | ENEMY_CREATURES | `0x517930` | да |
| 3 | ALL_CREATURES | `0x517990` | да |
| 4 | LAND | `0x5179D0` | нет |
| 5 | ALL | `0x517F60` | нет |
| 6 | POSESSION | `0x517AB0` | да |

OWN_CREATURES учитывает дополнительные состояния, включая плен/владение комнатой; бит4 аргумента вызова меняет ветвление проверки. ENEMY_CREATURES также может перенаправляться в проверку OWN_CREATURES при этом бите. Для ALL_CREATURES проверяется существующий слот сущности, тип 0 и исключённый владелец. У POSESSION есть дополнительные запреты состояний/таймеров, а также отдельная ветка объекта типа 2 с подтипом 9. Полные имена всех состояний и аргументных флагов здесь не заявлены.

CastRule>=6 и TargetRule>=7 возвращают 0. В codec это диагностируется как отклонение операции, а не как доказанный краш. Значение 0 является определённой записью с null-callback.

## Обычный и улучшенный Shot

В KeeperSpells хранятся два набора:

| Набор | ShotId | Data1 | Data2 |
|---|---|---|---|
| Обычный | raw+0xF0 → runtime+0x42 | +0xD0 → +0x43 | +0xD4 → +0x47 |
| Улучшенный | raw+0x113 → runtime+0x4B | +0x114 → +0x4C | +0x118 → +0x50 |

Пути `0x4BBF90` и `0x4BC290` выбирают набор для проверки ненулевого ID, lookup и Data1/Data2 по DWORD состояния игрока+0x0D. Однако перед вызовом фабрики они перечитывают обычный ShotId из definition42/rawF0. Поэтому смысл Data1/Data2 нужно проверять через фактически созданный Shot; нельзя универсально назвать их уроном/стоимостью. Подробности и120 native cases — `KEEPER_CAST_RU.md`. В коде есть также проверки конкретных SpellId: 4 участвует в расчёте стоимости создания рабочего, 5 — в дополнительном ограничении призыва, 14 — в проверке отдельного флага игрока. Само добавление новой записи с похожими параметрами не копирует ветки, привязанные к этим ID.

## Важное различие ResearchTime и стоимости исследования

RechargeTime в обоих каталогах умножается на TPS в **32 битах**, затем логически сдвигается на 12: `(rawU32*TPS mod2^32)>>12`.

ResearchTime и BonusRTime KeeperSpells обрабатываются иначе: инструкции `0x4F7D86 IMUL DX,CX`, `0x4F7D8A SHR DX,0xC` и аналогичная пара для AX доказывают **16-битное** произведение до сдвига. Результат `(rawU16*low16(TPS) mod65536)>>12` находится в пределах 0..15. Например, при явно выбранном для расчёта TPS20 исходные 500 и 1500 дают 2 и 7. Это арифметический пример, не вывод о текущем TPS игры.

Реальный проверенный путь завершения исследования использует другой источник:

1. Variables type17 содержит category, DefinitionId и ResearchPointsRaw.
2. `0x51DB00 → 0x506FF0` складывает эти три слова в 12-байтовые записи CResearchOrder.
3. `0x507040` сравнивает накопленные очки с третьим словом выбранной записи; `0x507060` использует тот же порог для процента.
4. Игрок вызывает эти функции из `0x4C2DC0` и `0x4C31D0`. В просмотренном пути +0x20F игрока — накопленные очки, +0x213 — выбранный номер записи, с нумерацией от 1.

В вашем GlobalVariables.kwd 29 записей ResearchOrder; первые записи заклинаний категории 4 задают по 1000 очков. В самостоятельном KeeperSpells.kwd у соответствующих определений ResearchTime=500. Подмена порога исследования значением из KeeperSpells была бы ошибкой. Все возможные другие потребители runtime-полей +0x5E/+0x60 здесь не исключены; доказано именно устройство loader и данного пути завершения.
