# Doors: настоящий файловый reader и мировой каталог

Этап160, 1 ноября2026. Компонент `native_door_reader_semantics`, схема `native-door-reader-semantics.json`.

Выполнена оригинальная цепочка **файловый reader56AC80 → настоящие MyFile/Disc → raw converter → World callback51FF30 → определение двери → lookup50D650**. Это закрывает ранее оставленный разрыв между изолированным загрузчиком определения и вставкой в мировой каталог. Значение `Unknown236` по-прежнему не установлено.

Проверены21 сценарий:20 завершаются обычным возвратом, один намеренно вызывает деление на ноль на некорректном заголовке. Из-за отдельного двухпроходного сценария reader имеет22 входа/21 нормальный возврат. Одиннадцать полных независимых Ghidra-контролей совпали; сценарий с исключением не посчитан успешным Ghidra-контролем.

Все адреса и смещения далее шестнадцатеричные; размеры и количества десятичные, если не указано иное.

## Что reader извлекает из файла

| Байты файла | Значение |
|---|---|
| `00..0B` | Внешний12-байтовый префикс; данный reader входит после него |
| `0C` | Проверяемый header tag141 (`8Dhex`) |
| `14` | DWORD количества записей `N` |
| `30` | Проверяемый data tag142 (`8Ehex`) |
| `34` | DWORD размера данных `D` |
| `38` | Начало записей Doors |

Reader читает фиксированные36 байт заголовка с позиции12, затем8 байт data header. Для исходного `Doors.kwd`: размер4984, `N=8`, `D=4928`, запись616 байт. После добавления диагностической девятой записи: размер5600, `N=9`, `D=5544`.

При активном обработчике данных он вычисляет **unsigned `floor(D/N)`**, после чего выполняет ровно `N` чтений этого размера. Остаток `D%N` не поглощается: при диагностическом `D=4929` восемь записей читаются, один байт остаётся в потоке.

Если вычисленный stride отличается от616, перед каждым чтением очищаются616 байт raw-буфера; converter всё равно обрабатывает616 байт. Проверен случай600: недостающий хвост заполняется нулями. Это не основание сохранять новые файлы с произвольным stride: совместимый редактор использует каноническую структуру616 и строгие проверки длины.

## Раздельные проходы заголовков и данных

Оригинальная `51DF90` регистрирует header callback `51FF10`, а `51E0A0` — data callback `51FF30`. Эти внешние функции регистрации прочитаны и сверены статически, но целиком не исполнялись.

Для исходного файла дополнительно выполнена последовательность с теми же callback:

1. Настоящий reader с header callback и нулевым data callback: считает ёмкость и пропускает payload настоящим MyFile.
2. Настоящая перемотка MyFile на позицию12.
3. Настоящий reader с data callback и нулевым header callback: загружает определения.

Итоговые все байты массива определений совпадают с комбинированной диагностикой и с чтением записей исходного файла в обратном порядке. Сам массив памяти и World подготовлены явно; оригинальные конструкторы слотов выполняются, полное выделение World-каталога через внешний bootstrap здесь не доказано.

## Как формируется мировой каталог

| Поле World | Смысл в подтверждённой цепочке |
|---|---|
| `15D4` DWORD | Указатель массива определений по181 байту |
| `15D8` DWORD | Ёмкость; header callback прибавляет `N`, но память не выделяет |
| `15DC` DWORD | Фактически вставленное количество |
| `15E0` DWORD | Накопленная runtime checksum |
| `A3C7` DWORD | Ненулевой режим обновления существующих определений |

В обычной вставке `51FF30` сортирует определения по unsigned BYTE ID: raw `DoorId244` → MID `2B8` → definition `AD`. При поиске позиции старые записи с ID, **равным** новому, тоже сдвигаются. Новая запись оказывается перед прежними равными. Сдвигаются все181 байт определения, включая неизвестные поля.

Порядок входа `[4,1,3,2]` даёт `[1,2,3,4]`. Исходные уникальные ID1..8 и обратный порядок8..1 дают побайтово одинаковый итоговый массив. **Физический порядок записей в файле всё равно нужно сохранять**: runtime-сортировка не разрешает молча менять импортированный файл.

При `count>=capacity` callback возвращает1, не загружая очередную запись. В диагностике с четырьмя входными записями и ёмкостью2 в каталоге остаются только первые две по поступлению, затем отсортированные. Reader при этом возвращает успех. Число callback и число реально загруженных определений — разные величины.

При ненулевом `World+A3C7` callback вызывает настоящий lookup по ID и обновляет существующее определение. Количество, ёмкость и суммарная `World+15E0` не меняются. Проверены существующие ID1/3; обновление отсутствующего ID не исполнялось.

## Lookup и дубликаты

Настоящая `50D650`, слот World vtable `138`, использует такой алгоритм:

```text
id = requestedDWORD & 255
i = min(id - 1, count - 1)
пока i >= 0:
    если row[i].ID == id: вернуть &row[i]
    если row[i].ID < id: вернуть NULL
    i -= 1
вернуть NULL
```

Поэтому общего правила «первый» или «последний дубликат» нет:

- При четырёх записях и дубликатах ID1 начальная позиция0 выбирает новый экземпляр.
- При четырёх записях и дубликатах ID4 начальная позиция3 выбирает старый экземпляр.
- ID0 можно вставить, но lookup0 немедленно возвращает NULL.
- Запрос `101hex` находит ID1: старшие биты аргумента отбрасываются.
- При каталоге ID1/3 запрос2 возвращает NULL.

Для создаваемых редактором новых определений следует обеспечивать уникальные ненулевые ID. При открытии существующего файла дубликаты/нулевые ID необходимо показывать как исходные данные и сохранять без скрытого исправления; поведение выше относится именно к этому getter.

## Подтверждённые дефекты reader

**Обрезанный хвост принимается как успех.** В подготовленном файле из двух616-байтовых записей последние60 байт удалены. Последнее чтение запрашивает616, получает556. Настоящий MyFile сообщает неполное чтение результатом0, но reader проверяет только `<0` и продолжает.

На ветви обычного stride616 raw-буфер перед чтением не очищается. Хвост последней записи остаётся от предыдущей: intended ID2 и `Unknown236=1101hex` становятся ID1 и `1100hex`. Итоговый каталог `[1,1]`, lookup2=NULL, reader возвращает1. Это воспроизведённое поведение **данного reader**, не утверждение о повреждении предоставленного исходного файла или о прохождении всех внешних проверок в живой игре. Внешний dispatcher и открытие файла не исполнялись.

**Нулевой `N` при активном data callback вызывает DIV0.** Инструкция `56ADAE: DIV ECX` выполняется до следующей проверки количества. Диагностические `N=0,D=0` дают ожидаемое CPU-исключение с ECX0 и без нормального возврата. При нулевом data callback тот же пустой payload пропускается и reader возвращает1. Проверка внешним загрузчиком и обработка такого исключения всей игрой остаются за границей результата.

Неверные header/data tags reader отклоняет возвратом0. Эти дефекты не следует переносить в новый редактор: проверять полные длины/границы записей до изменения или игрового экспорта; не считать native-успех доказательством целости файла.

## Checksum и Unknown236

При `global6FCDCF==0` checksum определения по `87` равна сумме всех732 беззнаковых байтов MID. При вставке её прибавляют к `World+15E0` с переполнением DWORD. Это runtime-накопитель, **не поле заголовка KWD**: его нельзя записывать вместо `S/N/D`.

Ненулевой глобальный gate оставляет предыдущий checksum определения. Конструктор `4A7040` это место не назначает; в диагностике там остаётся исходный заполнительA5. World затем складывает эти значения. Это ограничение конкретного подготовленного состояния, не формула правильного checksum файла.

`Unknown236` сохраняет все16 бит в полной файловой цепочке, в добавленной девятой записи и при сдвиге определений. Полная пара исходный файл / изменение только последнего `Unknown236=BEEFhex` отличается только:

- двумя байтами исходного payload и raw-буфера;
- двумя байтами MID `2AA` и definition `99`;
- checksum определения и суммой World.

Сравнены22 области/53348 байт; за пределами перечисленных различий память совпадает, включая IO и lookup. Чтения неизвестного слова при копировании целой181-байтовой записи являются переносом данных; игровое назначение этим не установлено. Прежние семь зацепок через общий `F7` не объявляются новыми потребителями двери. Поле остаётся `Unknown236:u16`.

## Пересборка и границы доказательств

В82 исходных контейнерах с656 Doors проверены164 новые точные операции в памяти:

- Добавление копии с новым ID и `Unknown236=BEEFhex`: увеличиваются только длины `S/D` на616 и `N` на1, добавляется ровно616 байт.
- Обратный порядок записей: заголовок остаётся прежним, сохраняются все байты самих записей.

Прочие секции, порядок вне выбранной перестановки, суффиксы и неизвестные поля побайтово сохранены. Проверен публичный decode→rebuild. Реальные игровые файлы не записывались.
