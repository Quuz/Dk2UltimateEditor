## Файл и загрузка

Запись Variables type43 занимает 16 байт, все смещения — от её начала:

| Смещение | Размер | Содержание |
|---:|---:|---|
| 0 | 4 | DWORD 43 |
| 4, 6, 8 | по 2 | BYTE типа жертвы, BYTE ID |
| A | 1 | Тип награды |
| B | 1 | Номер речи |
| C | 4 | Биты значения награды |

`51DB30` пропускает пары с нулевым типом, сохраняя порядок остальных. Неактивный ID при этом не читается как ингредиент, но остаётся физическим байтом файла и сохраняется нашим API. Подготовленный runtime-рецепт имеет 34 байта: три шестибайтовые записи `type:u32,id:u8,level:u8`, DWORD количества по +12h, три DWORD награды по +16h.

`50F7E0` добавляет его в World по `+2E70 + 34*count`; BYTE count хранится по +731B. Лимит — 128 записей. При заполненном массиве append возвращает 0 без записи, однако внешний callback всё равно возвращает 1. Поэтому успешный возврат callback не гарантирует, что 129-й рецепт принят. Все 44 текущих рецепта отдельно прошли исходный загрузчик в одном native-сценарии.

## История и сопоставление

`4F1600` ведёт общую для видов жертв историю из трёх записей в экземпляре комнаты. Entries начинаются по +49h, шаг 6; last/next/count — BYTE по +5Bh/+5Ch/+5Dh. Новая жертва записывается в next, затем last=next, next уменьшается по модулю 3. Count насыщается на 3; четвёртая жертва вытесняет самую старую.

`4F1660` сопоставляет рецепт с **последними N жертвами в хронологическом порядке**, сравнивая тип и ID. Уровень не участвует в проверке ингредиента. Более старая история вне N игнорируется: рецепт из одного ингредиента может сработать после трёх жертв. При несовпадении output награды и история не меняются. Пустой рецепт совпадает с любой историей, в том числе пустой.

Первый подходящий рецепт в порядке файла выигрывает. Это подтверждено полным `5133A0`: перестановка конкурирующих однокомпонентного и двухкомпонентного рецептов меняет итоговую награду с 5 на 40 маны. Игра не выбирает автоматически наиболее длинный рецепт. Следовательно, нельзя сортировать рецепты или превращать ингредиенты в неупорядоченное множество при сохранении.

Порядок отдельной записи и результат целой таблицы — разные вещи: автор файла может явно перечислить перестановки. Отчёт корпуса содержит `permutation_groups`, чтобы отличать такую таблицу от одного рецепта, принимающего ингредиенты в любом порядке. Наличие всех перестановок в исследуемом файле не предполагается.

Для жертвы-существа статический caller `472930` передаёт тип1, Creature ID и его уровень; для объекта `49F600` — тип2, Object ID и уровень0; полный проверенный `5133A0` — тип3, Spell ID и уровень0. Первоначальная зацепка 4728E0 была лишь ближайшим предыдущим прямым call-target; настоящий вход содержащей функции — 472930. Полные входы существа/объекта здесь не исполнялись.

## Уровень награды и ошибочный рецепт

При награде type1 matcher суммирует уровни только жертв типа1 в BYTE с переполнением по 256, затем делит сумму на число таких жертв с округлением вниз. Результат сдвигается на 16 и **прибавляется** к исходному DWORD значения награды по модулю 2³². Это не побитовое OR. При обычных уровнях 1–10 сумма трёх уровней не переполняется; проверены также физические граничные значения.

Пример: уровни 2 и 7 дают средний уровень 4. Сохранять нужно исходное значение награды в файле; рассчитанный matcher-результат — другое, runtime-значение.

Если полностью совпавший рецепт обещает награду type1, но не содержит ни одной жертвы типа1, исходная `4F1749: IDIV ESI` делит на ноль. Два воспроизводимых случая: рецепт только из объекта и пустой рецепт. Эмулятор сообщает `Divide by 0`; это не наблюдение живого краша игры. В текущих 44 рецептах такого условия не найдено.

## Выдача награды

`4F1780` сначала выбирает позицию в комнате через `4E4D90`, затем очищает всю историю: last=FF, next=0, count=0. Сами байты трёх entries не затираются. Более старые жертвы, не вошедшие в короткий рецепт, тоже теряются. Очистка происходит до ветки награды, включая нераспознанный тип и будущий отказ factory.

Диспетчер содержит только четыре отдельные ветки:

| Тип | Исходный путь | Граница подтверждения |
|---:|---|---|
| 1 | Creature factory `4B78D0`; owner комнаты, low8 ID; цикл повышения уровня из low8(value>>16) | Статический путь, успешное создание не исполнялось |
| 2 | Object factory `4B7A90`; owner из global WORD6F2548, low8 ID | Статический путь, успешное создание не исполнялось |
| 3 | Получение owner через `4E52F0`, затем `4BA420` | Статическая ветка золота, выдача не исполнялась |
| 4 | `4E52F0` → `4C19C0`, плюс счётчик owner+10EE | Полная native-цепочка, включая границы и переполнение |

Типы 0, 5–9 и 255 прошли полный обработчик: отдельной награды нет, история очищается. Затем возможны общие эффект комнаты и речь. Это ограничение конкретного DX dispatcher, а не универсальное утверждение об именах всех enum или других версиях.

Мана использует signed32 запрос и младшие 32 бита суммы. Для отрицательного запроса отрицательный итог ограничивается нулём; для неотрицательного запроса итог ограничивается signed owner+10EA. Счётчик +10EE увеличивается на **запрошенную величину**, а не фактическую прибавку: 90 маны при лимите100 и награде30 дают100 маны и +30 в счётчик. Проверены также отрицательные значения, signed overflow и signed отрицательный лимит. Эти крайние значения не объявляются допустимыми настройками GUI.

Проверенная композиция использует оригинальную World vtable и двухклеточный конечный список комнаты. PRNG, получение карты/комнаты, выбор позиции, matcher, mana helper и notification gate — исходные. У owner+19A=1 сообщения завершаются через настоящий ранний gate; room-definition effect+421=0. Живая речь, визуальный эффект и успешные creature/object/gold factories не проверены. Позиция награды выбирается по комнате, а не просто копируется из позиции жертвы, переданной caller.

## Корпус, пакет и воспроизведение

Все 44 текущих рецепта прошли 1188 точечных пересборок: девять физических полей, по три граничных значения каждого. Проверено изменение только выбранных байтов всего контейнера и повторное чтение. Выявленных конфликтов suffix-приоритета, пустых рецептов, неподдерживаемых reward types и деления на ноль в этих 44 записях нет.

Расширенный поиск затронул 580 вложенных map Variables и исходный GlobalVariables: 557 файлов прошли strict parse→pack; 24 входа строгий parser отверг. Это отдельный набор от исторической проверки 737 файлов верхнего каталога. Отказы и SHA сохранены; их причины полностью не разобраны, файлы не объявляются повреждёнными. Среди принятых map Variables рецептов type43 не найдено. Исходные данные не изменялись, четыре EXE сверены по SHA.

Проверены 16 полных диапазонов функций и две таблицы: оригинальная World vtable и четыре адреса switch. 14 функций входили в native-сценарии; сверка всей функции не означает исполнения каждой её ветки. Одна первоначальная диагностика отличалась лишь ожидаемым текстом ошибки деления и сохранена отдельно; в 59 успешных/ожидаемых сценариев она повторно не засчитывается.

В пакете появился 68-й компонент `sacrifice_semantics`; прежние 67 компонентов сохранены по SHA. Итог — `phase88-validation.json`, primary bytes — `phase88-sacrifice-primary-manifest.json`. Для воспроизведения: `prepare_sacrifice_queries.py`, `prepare_sacrifice_context.py`, `prepare_sacrifice_executor_queries.py` и соответствующие `ghidra_probe.py ...queries.json`; затем `emulate_sacrifice_matching.py`, `emulate_sacrifice_dispatch.py`, `prepare_sacrifice_primary.py`/его queries, `export_temple_recipes.py`, `build_sacrifice_semantics.py`, `finish_sacrifice_phase.py`, `build_format_package.py`, `audit_sacrifice_semantics.py`. Подготовка primary выполняется до появления всех 16 функций, затем ещё раз для оставшихся диапазонов и таблиц.

Цель целиком не завершена: успешные factory-награды, другие версии и остальные существенные неизвестные форматов остаются открытыми. Исследование Terrain-индексных зацепок предыдущего прохода сохранено отдельно и не объявлено завершённым этим этапом.
