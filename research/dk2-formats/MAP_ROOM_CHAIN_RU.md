# Map: оригинальное создание комнаты, декорации и навигация

Этап 138, 30 октября 2026. Профиль — предоставленный `DKII-DX.exe`, SHA-256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a`. Игровые данные, EXE и параллельный редактор не изменялись.

Полный Map callback `51EC60` теперь исполнен с исходными инструкциями: он создаёт комнату из свободного слота, присоединяет соседние клетки, вызывает фабрики и удаление декораций, обновляет клеточные маски и действительно перестраивает навигацию. Это расширяет этап137, где активная комната и её клетки были подготовлены заранее, а NAV4 позволял setter вернуть управление без перестроения.

## Граница входа из файла

Физическая клетка KLD по-прежнему состоит из четырёх байтов: TerrainID, PlayerID, NativeMapFlags и неизвестного четвёртого байта. Использована установленная проекция `native_map_cells.intermediate_cell`: три DWORD presence=1, BYTE+C TerrainID, BYTE+D PlayerID, BYTE+E flags, BYTE+F=0.

**Полный native reader KLD этим этапом не исполнен.** Проекцию raw→MapMID делает host-код, опираясь на отдельное историческое доказательство parser из этапа28. Новый native путь начинается на входе целого callback:

```text
51EC60 cdecl(x, y, MapMID*, World*)
  → Terrain / Room lookup
  → 44FC40: размещение Terrain
  → 4C5C30 / 4ED1A0 / 4ED320: создание или присоединение комнаты
  → 450770: привязка клетки
  → декорации, маски клеток, навигация
  → финальный бит подложки из MapMID.flags
```

Callback читает PlayerID через подготовленный массив World+84 со stride `0x1125`; выбран PlayerID2 с фактическим тегом владельца2. Это не доказательство проверки произвольных неверных PlayerID.

Для Terrain с флагом `0x10` callback находит RoomDefinition по совпадению TerrainID (`50B550`). Загружены исходные Room Temple13/CombatPit16 и Terrain Temple22/Ground3; размещается только Temple13. Graphics-аргумент загрузчиков равен NULL, остальные raw-значения исходных записей сохранены.

## Создание и присоединение клеток

Выполнены настоящие конструкторы `4E3790` двух 169-байтовых Room slots; они получили теги1000/1001. Входной свободный список разрешает выделить один слот1000. Подготовлены связанные фигуры, поэтому новый слот активируется один раз (`4EC490` → `4E3800`), а следующие клетки присоединяются (`4EC650`). Полное выделение массива672комнат через `4EC000`/CRT не выполнялось; несвязанные комнаты, их слияние и разделение остаются отдельной задачей.

Независимые проверки установили для выбранных фигур:

- ровно одну активную комнату, тип13 и владельца2;
- RoomTag1000 у всех размещённых клеток;
- связный список клеток комнаты, совпадающий с набором входных координат;
- число клеток и накопленное здоровье комнаты: `10000 × число клеток`;
- маски BYTE+C из восьми соседей по правилу этапа137.

Квадрат3×3 даёт центральную маску `FF`; без одной диагональной клетки — `FD`. Прямоугольник2×3 не содержит клетки с `FF`. Обратный порядок размещения квадрата сохраняет итоговое соседство; внутренние списки, теги и прочие байты не объявляются независимыми от порядка загрузки.

## Декорации и корректный allocator

Для фабрик загружены шесть исходных Objects: 72,73,97,98,111,132. В выбранных сценах остаются декорации Object111: обычно четыре, в фигуре без диагонали — пять. Код размещения вызывает настоящее создание и очистку декораций при расширении комнаты.

Пул Object инициализирован оригинальной `554AD0`. Предоставлена память для16384полезных байт,24байт двух внешних sentinel и64байт защитного хвоста. Исполняются allocate `554B30` и free `554BD0`. У каждой живой декорации проверены native vtable, тег, регистрация, владелец и указатель на Player. Списки used/free покрывают все16384байта без дыр и наложений; счётчик used совпадает с World+76. Один живой Object занимает408байт allocation, его объектная часть —393байта.

Ранний exploration fixture имел только достаточные для создания sentinels. При проверке освобождения обнаружилось отсутствие полного free-list initializer; эти снимки исключены из принятого покрытия. Принятые11сцен используют `554AD0`, проверяют разбиение всей арены и допускают обращения к нулевой странице только через `FS:[0]` для SEH. Этот результат относится к удалению декораций и не доказывает окончательное удаление жертвы-Creature.

## Перестроение навигации

Исполнены оригинальные setup `4CE690`, `4CE740`, `4C8F30`, `4CEF20`. Заданы реальные размеры5×5, stride5, исходный bitmap из нулей и1454байта рабочего буфера — размер для50элементов по формуле исходного setup. Защитные64байта не изменились.

`4CEF20` строит начальную сетку один раз в каждой сцене. В полном квадрате3×3 центральная клетка после вычисления маски `FF` меняет NAV0→4, вызывая ещё одно полное `4CE770`. Это уже не ветвь «старый байт равен новому» и не ранний возврат из-за нулевых размеров. Итоговый bitmap содержит4только в центре; остальные24байта —0. Для неполных фигур дополнительного вызова нет.

Полные выходные mesh/work-буферы совпали на двух CPU. Значения всех внутренних байтов navmesh, оптимальность путей и сама геометрическая спецификация сетки этим сравнением не расшифрованы. Название кода4 по одному этому пути не присваивается.

## Флаги и накопленная сумма

Перед размещением callback вызывает `5108C0`, прибавляя к World+`0x72E7` **signed8 каждого из16байт MapMID** по модулю2³². Это не raw-сумма четырёхбайтовой клетки и не поле заголовка KLD. Для Terrain22/Player2/flags0 вклад равен27: три presence-единицы плюс22+2.

Четыре парных опыта повторяют одинаковый квадрат, меняя только flags на2,1,80h,FFh. Все подготовленные области памяти сравнены целиком. Допустимые отличия оказались ровно такими:

| Область | Отличие |
|---|---|
| Входной MapMID | Изменённый flags |
| World+72E7 | Накопленный signed8 вклад flags |
| Runtime cell WORD8 | Бит1000 устанавливается только при flags&2 |

Все прочие подготовленные байты совпали, включая декорации и навигацию. Это ограниченный результат для выбранного храмового пути, а не доказательство глобальной неиспользуемости других bits. Четвёртый raw-байт KLD остаётся opaque.
