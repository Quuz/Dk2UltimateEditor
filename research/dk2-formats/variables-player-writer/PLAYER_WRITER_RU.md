# Variables: первая player-scoped ветка `4937C0`

14 ноября 2026. Профиль `DK2 Editor pro.exe`, SHA-256 `989c45df779bccfc9a9e509b2ad0224a9bd269629f74792adc0320fa4b99fb09`. Это ограниченный аудит только первой по порядку исполнения player-scoped ветки оригинального сериализатора Variables. Файлы: `audit_player_writer.py`, `player-writer-results.json`.

## Что исполнено в оригинальных инструкциях

`4937C0` вызывает счётчик `48CA00` (`0x4937D0`), пишет заголовок и сразу вызывает `4943C0` (`0x49386D`). Именно `4943C0` — первая ветка, зависящая от игроков; в phase199 она возвращалась сразу, потому что `Map+0xA68 = 0`.

- Массив игроков: указатель `Map+0xA64`, количество `Map+0xA68`. Аксессор `488830`: при `index < count` возвращает `*(Map[+0xA64] + index*4)`, иначе 0.
- Отбор: беззнаковый байт `player[+0x1C] >= 3` (строгое `2 < byte`).
- Счётчик `48CF50(player+0x4C)` читает контейнер `{+0x50 данные, +0x54 количество}` и считает элементы, у которых DWORD value по `+0x50[i*8+4]` не ноль.
- `4943C0` идёт по тому же контейнеру и на каждый ненулевой value пишет ровно 16 байт:

| Смещение | Значение | PC записи |
|---:|---|---|
| +0 | DWORD-константа `1`; это первое поле/тип записи | `0x4943CD` |
| +4 | DWORD key = беззнаковый младший байт `player[+0x50][i*8+0]` | `0x49441C` |
| +8 | DWORD value = `player[+0x50][i*8+4]` | `0x49442B` |
| +12 | DWORD kind = беззнаковый `player[+0x1C]` | `0x4943FD` |

Все 16 байт этой записи назначаются оригинальным кодом; необъявленных байт в ней нет. Вызов выхода — `0x494434` (`CALL [EDX+0x38]`). Смысл типа `1` за пределами «первое поле записи исходного writer» здесь не назначается.

## Сцены и результат

| Сцена | Игроки | Объявлено | Записано | Новые записи |
|---|---:|---:|---:|---|
| baseline | 0 | 196 | 196 | — |
| one-accepted | 1, kind 3, один элемент | 197 | 197 | `01000000 94000000 44332211 03000000` |
| two-order | 1, kind 3, два элемента | 198 | 198 | `(1,0x11,0xAABBCCDD,3)`, затем `(1,0x22,0x01020304,3)` |
| kind2-boundary | 1, kind 2 | 196 | 196 | —; аксессор вызван, внутренний цикл пропущен |

Ожидаемые записи выведены только из входов. Наблюдённые 16-байтные записи совпали побайтно, включая порядок двух элементов. Новые player-записи сверены с независимым ожиданием из входов. Полный список (193 скалярные + Type74 + Type241 + Type242 + новые) также сравнивается; скалярные хвосты для этого сравнения берутся из наблюдённого writer-entry scratch и проверяют воспроизведение; хвост выходного буфера — `0xA5`, `META` — `(3+count, OUTPUT+size, 0)`.

PC-доказательства: `0x4937D0` (вызов счётчика), `0x49386D` (вызов `4943C0`), `0x4943E8` (аксессор `488830` на игрока), `0x48CA36` (вызов `48CF50`), `0x48CF71` (инкремент счётчика), `0x494434` (запись 16 байт). В baseline `0x4943E8 = 0`; в kind2 `0x4943E8 = 1`, но `0x494434 = 0` и `0x48CF50 = 0`.

## Fixtures и ограничения

Добавлены только данные: `Map+0xA64/+0xA68`, объект игрока `0x177A0000` (нули, кроме `+0x1C` и `+0x4C/+0x50/+0x54`), массив 8-байтных `{key,value}` по `0x177B0000`, массив указателей `0x17790000`. Остальные pool/availability-контейнеры игрока явно нулевые. Наследуемые CFile sink, HeapAlloc/HeapFree, lstrlen, interlocked, critical-section, clock/TLS/error IAT adapters, Terrain #6 и default-initializer — фикстуры опубликованного стенда, а не новые подмены. Регистры на входе каждого вызова: EAX/EBX/ECX/EDX/ESI/EDI = 0 кроме объявленного ECX, ESP=EBP=0x7FFF0000, EFLAGS=2, FPCW=0x37F.

Не проверялись и не интерпретировались: pool/availability-группы `1+(kind<<16)`..`5+...`, GUI-достижимость, полное сохранение, игровые потребители, реальная запись файла. Не исполнялись также пропуск нулевого value в `+0x4C` и индекс аксессора больше нуля (во всех сценах ровно один игрок), поэтому порядок между игроками не проверен. `Type77 count 110 = 0`. Types 29/113/114/186 не получают новых значений; SDT/Crypt не затрагивались. Хвосты `+8..+15` скалярных записей — воспроизведение унаследованного стекового scratch (`0xA5A5A5A5`), а не новое утверждение о формате.
