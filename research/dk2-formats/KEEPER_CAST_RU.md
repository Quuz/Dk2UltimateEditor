**Подтверждено важное уточнение:** обе функции выбирают обычные или улучшенные параметры по состоянию заклинания игрока, но перед созданием Shot снова читают **обычный ShotId**. Улучшенный ShotId участвует в проверке ненулевого значения и поиске определения; улучшенные Data1/Data2 передаются созданному Shot. ## Какие поля участвуют

Все raw-смещения — от начала406-байтовой записи KeeperSpells. Runtime definition —122 байта.

| Поле | Raw | Definition | Ширина |
|---|---:|---:|---:|
| Обычный ShotId |F0|42|BYTE|
| Обычный Data1 |D0|43|DWORD|
| Обычный Data2 |D4|47|DWORD|
| Улучшенный ShotId |113|4B|BYTE|
| Улучшенный Data1 |114|4C|DWORD|
| Улучшенный Data2 |118|50|DWORD|
| TargetRule |DA|77|BYTE|
| Неизвестное C8 |C8|3A|DWORD|

При player spell-state DWORD+0D==0 выбираются обычные поля, при любом ненулевом DWORD — улучшенные. Выбранный ShotId должен быть ненулевым; с этим ID вызывается world virtual1B0 для поиска определения Shot.

Однако путь A в4BC160 читает AL из `[definition+42]` и передаёт его в4B7CD0 в4BC19E. Путь B повторяет это в4BC401/4BC40E. Это повторное чтение обычного ID после выбора улучшенных полей. Нативная фабрика4B7CD0 использует первый аргумент для проверки существования через virtual1AC, сохраняет младший BYTE в Shot entity+124 и передаёт его initializer4AAC90. Тело фабрики просмотрено и сверено с PE; внутри тестов путей A/B она заменена перехватчиком.

Пример подтверждённого маршрута: обычный ID20, улучшенный40, состояние улучшено. Поиск выбранного определения получает **40**, вызов фабрики получает **20**, а Data1/Data2 берутся из улучшенных полей. Это различие непосредственно записывается стендом, а не выводится только из декомпилятора.

Если улучшенный ID равен0, улучшенный путь останавливается **до** поиска и фабрики даже при ненулевом обычном ID. Обратный искусственный пример — обычный0, улучшенный40 — передаёт фабрике0. В12 тестах стендовая фабрика принимает этот аргумент; это **не доказательство**, что настоящая игра создаст Shot0: реальная фабрика проверяет существование ID и может отказать.

## Поля созданного Shot и последующие действия

После успешного возврата фабрики обе функции присваивают:

| Поле Shot instance | Источник |
|---|---|
| DWORD13D |Выбранный обычный/улучшенный Data1|
| DWORD141 |Выбранный обычный/улучшенный Data2|
| WORD147 |Младшие16 бит аргумента цели|
| DWORD14D |1 при TargetRule1/2/3/6; при остальных значениях прежние байты сохраняются|

Data1/Data2 здесь прослежены как32-битные значения. Их общий смысл нельзя универсально назвать уроном или стоимостью: он зависит от реально созданного типа Shot и его обработчика.

Оба пути копируют XYZ цели. Путь A дополнительно прибавляет2000hex/8192 к Z при **обычном ID21**; в пути B такого присваивания нет. Условие зависит от перечитанного обычного ID, а не улучшенного. Названия A/B привязаны к адресам, а не к предположению об универсальных командах интерфейса.

На успешных стендовых ветвях реальный код wrapper вызывает функцию изменения маны с−1234, добавляет1234 к player DWORD10F2, записывает время в DWORD5 и9 состояния заклинания и вызывает sound virtual20. Проверены остановки по отсутствию заклинания, отказу проверки маны, отказу проверки цели и отказу фабрики. Маска аргументных флагов01 позволяет пройти отказ проверки достаточности маны; реальная логика списания внутри mana helper не исполнялась.

**Обе функции возвращают EAX=0 и после успешных побочных действий.** Поэтому этот возврат нельзя использовать как признак «ничего не применилось». В тестах он фиксируется до выполнения кода сравнения выходных буферов.

## Что означает проверка C8

В96 основных испытаниях менялся только definition DWORD3A между0,1,7FFFFFFF,80000000,FE0C0000 иFFFFFFFF. Для каждого из16 сочетаний пути, улучшения и пары ID выходы Shot/player/state и события совпали при всех шести значениях. Определение сохраняло своё входное содержимое без записи из wrapper.

Это подтверждает отсутствие влияния C8 **в исполненном коде этих wrappers с указанными подстановками**. Проверки цели, фабрика и другие реальные helpers могли бы иметь собственные зависимости; их полное отсутствие этим не доказывается. Назначение C8 остаётся неизвестным, поле сохраняется как raw bits.

Воспроизводимый ограниченный CFG-поиск указателей:45 кандидатов getter/vcall110,838 состояний,9 дальнейших передач указателя и ни одного установленного чтения C8 в рассмотренных фрагментах. Virtual110 без типа объекта не гарантирует Keeper definition. Ограничения ветвления, неизвестных вызовов и stack aliases сохраняются в отчёте `phase53-keeper-cfg-alias-leads.json`. Результат поиска не является доказательством глобального неиспользования поля.

Ресурсы Keeper-панели RC3258 не дали новой подписи C8; видимый Recharge Time соответствует отдельному rawCC. Отдельно найденные старые getter/loader-кандидаты сохранены как leads, не как завершённая расшифровка старой версии.

## Корпус и применение в независимом редакторе

В82 каталогах/1066 записях у247 обычный и улучшенный ID различаются; у84 оба различающихся ID ненулевые. В этих84 входят82 копии пары2/60 и две пользовательские пары183/182 и184/24. Повторяющиеся каталоги не считаются независимыми игровыми реализациями. Встречаемость пары не доказывает успешное применение конкретного заклинания в игре.

Сохранять оба ID и четыре Data-поля нужно независимо. Не следует автоматически переносить улучшенный ID в обычный: это изменит данные карты. В UI собственного редактора можно показать диагностическое примечание о подтверждённом маршруте конкретного DX. Это отдельная подсказка, а не изменение физической структуры файла.

`native_keeper_cast.selection_view(raw, upgrade_bits, route)` возвращает выбранный ID поиска, аргумент ID для фабрики, выбранные Data1/Data2 и наблюдаемые условия. Она не прогнозирует успешное применение: настоящие availability/target/mana/factory проверки могут отказать.
