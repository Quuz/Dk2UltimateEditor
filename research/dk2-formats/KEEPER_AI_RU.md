# KeeperSpells: флаги, выбор боевых заклинаний и неизвестный C8

Этап26,26 октября2026. Новая схема `keeper-ai-semantics.json` — компонент37 общего пакета. Числовой API: `native_keeper_ai.py`; доказательства — сохранённые инструкции предоставленных EXE и ресурсы Editor Pro. Исходные игровые файлы не изменены.

## DWORD флагов: игра сохраняет больше, чем родной редактор

Raw `KeeperSpells+0xDC` — полный DWORD в записи406 байт. Game converter `0x56BAB0` выполняет OR с intermediate+`0x154`; при исходном нуле это сохраняет все32 бита. Loader `0x4F7CE0`, при ненулевом presence+`0x74`, копирует DWORD в runtime+`0x54` без маски.

Editor Pro converter `0x42B720` также делает OR в intermediate+`0x154`. Его initializer `0x42B600` обнуляет область, включающую это поле. Однако callback `0x4A25E0` передаёт DWORD декодеру `0x420270`, который извлекает только четыре бита в отдельные BOOL DWORD модели:

| Маска | Native-подпись | Модель | Панель | Control ID |
|---|---|---|---|---:|
| `0x02` | Create Worker | `0x204` | `0xB4` |1796 |
| `0x04` | Attacking | `0x208` | `0xB8` |1797 |
| `0x08` | Defensive | `0x20C` | `0xBC` |1798 |
| `0x10` | Don't Cast On Creatures | `0x210` | `0xC0` |1799 |

Конструктор `0x450A10` выбирает диалог258. Fill`0x451CC0`, DDX`0x450F80` и commit`0x451FD0` связывают эти поля с четырьмя checkbox. Названия и control ID повторно прочитаны непосредственно из PE-ресурса, а не только из сохранённого JSON.

Writer`0x4A99B0` вызывает encoder`0x420230`, который строит новый DWORD только из этих четырёх BOOL. Его результат сохраняется на ESP+`0x12C`; начало raw-буфера ESP+`0x50` даёт смещение`0xDC`. Поэтому native-проекция загрузка модели → запись:

```text
saved_flags = raw_flags & 0x1E
```

Изменять checkbox для потери остальных битов не требуется. Например, `0xFFFFFFFF` превращается в`0x1E`, а одиночный bit0 — в0. Это поведение Editor Pro, а не правило сохранения нового редактора: неизвестные биты следует сохранять, пока пользователь явно не меняет их.

Игровое назначение Create Worker здесь отдельно не расшифровывается; ниже установлены конкретные потребители трёх остальных масок в одном боевом алгоритме.

## Какие заклинания рассматривает боевой ИИ

Функция`0x503060` обходит список существ, проверяет native-категорию`0x16` и проходит дополнительные проверки состояния, владельца, комнаты/CTA и параметров ИИ. После этого выбирается одна из двух веток. Вызов random с bound4, при результате меньше `(AI DWORD+0x4B2 >>26)&7`, ведёт в защитную ветку; иначе — в атакующую. Более ранний random-gate требует результат bound4 не меньше `(AI DWORD+0x4B6)&7`.

В обеих ветках целочисленный счётчик `i` идёт от1 до количества определений, полученного через world vtable+`0x114`. Для каждого `i` проверяются:

1. Player helper`0x4BAFA0(i)` возвращает3.
2. Helper`0x4BE390(i)` возвращает0 — нет задержки повторного применения.
3. Lookup по world vtable+`0x110` возвращает определение для`i`.
4. В защитной ветке требуется `flags &0x08`, в атакующей — `flags &0x04`.
5. **В обеих ветках обязательно `!(flags &0x10)`**.

Бит0x02 сам по себе не подходит ни одной ветке. Другие старшие биты не блокируют показанные битовые проверки. Это не полный диспетчер всех способов применения KeeperSpells: специальный путь CTA и последующие проверки остаются отдельными.

Перебор `1..count` и поиск по ID нельзя подменять перебором всех фактических ID. Этот код сам по себе не доказывает посещение разреженного ID выше count. В сохранённом выбранном ID остаётся младший byte счётчика.

## Mana Cost влияет на случайную проверку

Raw ManaCost `+0x11C` переносится в runtime+`0x58`. Здесь код читает его как unsigned DWORD. Фрагменты используют unsigned MUL с константой`0xD1CC931B`, затем старшую половину сдвигают на11:

```text
q = (uint64(costBits) * 0xD1CC931B) >> 43
bound_defensive = q + 1
bound_attacking = q + 2
```

Это **деление на2499**, не2500. Аудит доказывает эквивалентность `q=floor(costBits/2499)` на всём диапазоне u32 через оценку ошибки reciprocal, а не только на нескольких примерах. Например, cost2498 даёт q0,2499 — q1,4998 — q2. Значение со старшим битом также трактуется unsigned именно этим потребителем; это не предписание разрешать отрицательную стоимость в UI.

Затем берётся трёхбитный параметр `P=(AI DWORD+0x4B6 >>23)&7`:

```text
threshold = unsigned32(4 - P)
passed = unsignedRandomResult >= threshold
```

При P=5..7 вычитание переполняется и порог оказывается около`0xFFFFFFFF`; он не ограничивается нулём. API называет аргумент `power` для передачи этих трёх битов, не присваивая ему отдельной native-подписи параметра личности.

Random helper`0x5558D0` при ненулевом bound обновляет seed:

```text
seed = low32(seed * 0x19660D + 0x3C6EF35F)
result = ROR32(seed,13) % bound
```

Следовательно, результат в`0..bound−1`. Равномерность распределения не утверждается. В этой функции ИИ передаёт seed-поле world+`0x15A0`; native-прогоны выбора используют явно заданные результаты вместо PRNG, чтобы независимо проверить каждую ветку.

## Защитная и атакующая ветки сохраняют кандидата по-разному

Защитная ветка записывает `selectedId=low8(i)` **до** random-проверки. Первый успех заканчивает поиск. Если все random-проверки провалились, остаётся **последнее подходящее защитное заклинание**. Ноль получается, когда вообще не было подходящего кандидата.

Атакующая ветка записывает ID только **после** успеха random-проверки и сразу выходит. При всех провалах ID остаётся0.

Например, два определения с flags`0x0C`, cost0, P0 и результатами random0/0 дают selectedId2 в защитной ветке и0 в атакующей. Native-прогоны подтвердили именно различие порядка присваивания, а не гипотезу по названиям флагов.

Выбранный ID ещё не означает выполненное заклинание. Далее идут поиск цели по расстоянию, проверки здоровья/состояния, пригодности цели и собственно применения. Защитный путь, например, требует здоровье строго ниже половины level-adjusted максимума и отсутствие instance bit`0x200000`. API `select_spell` заканчивается до поиска цели и не моделирует полный ИИ.

## Что удалось уточнить для неизвестного +0xC8

Поле остаётся **семантически неизвестным**. Его путь: raw DWORD`0xC8` → intermediate`0x140` → game runtime`0x3A`. Родной Editor Pro callback рассматривает DWORD как unsigned и делит на4096 в model double`0x178`. Writer умножает это значение на4096, преобразует helper`0x4ACDA8` и пишет DWORD обратно в rawC8.

В проверенной основной панели KeeperSpells Recharge Time идёт из **model`0x180`**, то есть соседнего raw`0xCC`, в panel double`0x78` и обратно. Model178 в этом fill не копируется. Похожая функция fill`0x4439A0` действительно читает178, но принадлежит другому каталогу: её getter использует count+`0x59C`, а Keeper использует+`0x564`. Этот ложный след отклонён; назначать C8 подпись Recharge Time нельзя.

В80 файлах карт1040 записей KeeperSpells. C8=0 в960 записях; у80 записей Sight Of Evil/Sight-of-Evil — `0xFE0C0000`. Обнулять поле или считать его непереносимым мусором оснований нет. Игровой потребитель runtime3A пока не установлен.

## Корпус, сохранность и воспроизведение

Распределение flags по1040 записям:0 —71,0x04 —246,0x08 —84,0x10 —481,0x12 —82,0x14 —76. Все значения укладываются в1E, поэтому на этом корпусе native-проекция не теряет биты. Среди примеров: Heal0x08 подходит защитной маске, Tremor0x14 отсекается битом0x10 из атакующей выборки, Turncoat встречается как0 и0x04. Это свойства записей; наличие заклинания в реальном бою дополнительно зависит от всех остальных условий.

`phase26-validation.json`:329 граничных проверок и273 точечные пересборки контейнеров в памяти. Подтверждена полная сохранность соседних полей, включая неизвестный C8, заголовков и других секций.

48 успешных native-прогонов:32 двух selection loops,8 game converter/loader pipeline,8 editor decoder→encoder. Для loop fixtures подменены helpers доступности/задержки, lookup/count и источник random. Исполняются исходные условия, арифметика стоимости, порядок обхода и присваивания ID. Полные caller gates, target search, GUI и запись ресурсов не запускались; x87-путь C8 подтверждён инструкциями, без native-эмуляции.

13 первичных цитат и347 инструкций проверены по выгрузкам; четыре checkbox повторно извлечены из PE. После эмуляции5 полных assembly выгрузок сохранили инструкции.17 исходных файлов и2 EXE сохранили SHA-256. Артефакты: `build_keeper_ai.py`, `native_keeper_ai.py`, `emulate_keeper_ai.py`, `audit_keeper_ai.py`, `keeper-ai-semantics.json`.
