## Что удалось установить

- Полный native-сборщик флагов Editor Pro поддерживает **17 бит**, в том числе0x4 и0x4000, которых нет в прежнем enum. Игровое назначение этих двух битов пока не установлено.
- Native-сохранение флагов оставляет только маску **0x0003FFBF**; бит0x40 и биты18…31 этим путём не сохраняются. В собственном редакторе это должно быть отдельной диагностикой, а не автоматическим обнулением.
- В Line Of Sight поле **TriggerData+0x1DC** используется как целочисленный радиус поиска в клеточных единицах. Для отдельного вызова сопровождения цели прибавляется2.
- **ChargeTime+0x1CC** преобразуется в32-битный порог, но tick сравнивает его с **однобайтовым счётчиком** успешных проверок. Порог выше255 недостижим этим счётчиком.
- Назначение Traps+0x204 и двух неизвестных полей Terrain не установлено. Все их байты продолжают сохраняться.

## Флаги: файл → модель → native-сохранение

Файловые Flags — DWORD **raw+0x1EC**. Конвертер редактора переносит их в intermediate+0x294; callback0x4A1770 вызывает decoder **0x4260E0**. Encoder **0x426000** восстанавливает DWORD из отдельных BOOL модели. Writer **0x4A8F40** кладёт его в `uStack_78`; начало записи `uStack_264`, разность0x1EC, длина записи0x243.

Формула для полной native-цепочки чтения и записи этого поля:

```text
native_saved_flags = raw_flags & 0x0003FFBF
dropped_bits       = raw_flags & 0xFFFC0040
```

Это не формула всех побочных действий GUI: например, условное обнуление ManaCostToFire уже описано в `EDITOR_UI_FIELDS_RU.md`. Это точная проекция одного поля Flags через исследованные decoder/encoder.

Модель содержит BOOL от0x2A0 до0x2E0, шаг4, пропуская файловый бит0x40. DDX подтверждает13 checkbox-привязок. Биты вне маски не объявляются неиспользуемыми игрой: установлен только их отсев в данном editor writer.

## TriggerType: отдельные ID и callback

Физический путь **raw+0x20B → intermediate+0x2B3 → runtime+0xBD**. Native-таблица Editor Pro по **VA0x514768** содержит три пары ID/UTF-16 подпись:

| ID | Подпись | Callback игры |
|---|---|---|
| 1 | Line Of Sight | 0x4A9290 |
| 2 | Pressure | 0x4A92C0 |
| 3 | Trigger | 0x4A9350 |

ID0 (baseline NONE) отсутствует в этой таблице выбора. Сам native lookup0x471790 ищет ID в отдельном массиве и возвращает-1, если его нет. Это ещё не доказывает, как конкретное состояние с отсутствующим выбором ведёт себя при полном GUI-сохранении.

Игровой initializer0x4A93A0 очищает четыре указателя по0x6E4FD8 и заполняет их из трёх PE-пар по0x66D430. Tick0x4A84E0 проверяет `TriggerType<4`, затем ненулевой callback. При0 и>=4 положительного результата в этом dispatch нет. Наличие других путей активации ловушек этим не исключается.

Callback Line Of Sight0x4A9290 проверяет младшую тетраду instance+0x10C, затем вызывает target helper0x4A9400 с аргументом0. При найденной цели возвращает её ID. Декомпиляции Pressure/Trigger сохранены для дальнейшего разбора, но неполное восстановление регистров/стека не используется как доказательство всех их аргументов.

## TriggerData как радиус Line Of Sight

Путь DWORD **raw+0x1DC → intermediate+0x284 → runtime+0x70**, копирование без /4096. Target helper0x4A9400 читает runtime+0x70, при ненулевом аргументе прибавляет2 и вычисляет порог:

```text
r = (TriggerData + (tracking ? 2 : 0)) mod 2^32
threshold = (r * r * 4096) mod 2^32
```

Порог сравнивается с квадратом XY-расстояния: каждая координатная разность возводится в квадрат, результат сдвигается на12 бит, сумма рассматривается как unsigned DWORD. При обычных небольших значениях TriggerData — радиус в клетках, а не расстояние, уже умноженное на4096. Например,5 даёт квадратный порог25×4096; вызов сопровождения —49×4096.

В tick проверка флага TRACK_NEAREST_TARGET0x80 приводит к вызову этого helper с аргументом1. Это конкретный вызов, для которого подтверждено добавление2; API показывает арифметику отдельно от всей логики сопровождения.

Есть три существенные детали:

1. В новом поиске кандидат должен иметь `distance < threshold` и быть ближе уже выбранного. Равенство границе не проходит.
2. При перепроверке кешированной цели предыдущего тика сравнение допускает `distance <= threshold`, если прошли остальные проверки. Пограничная цель может сохраниться, хотя новый кандидат на той же границе не был бы выбран.
3. При повторном вызове в том же тике helper сначала возвращает кешированный ID **до** пересчёта радиуса. Разные аргументы0/1 в одном тике не гарантируют независимый поиск.

Для больших данных действует32-битное переполнение: radius1024 даёт нулевой threshold, а0xFFFFFFFF с tracking после сложения превращается в1. Это не нормализация авторского диапазона; raw DWORD должен сохраняться, API лишь сообщает фактическую арифметику. Видимость, владельцы, иммунитет и выбор конкретной цели проектором не моделируются.

## ChargeTime:32-битный порог и8-битный счётчик

Путь **raw+0x1CC → intermediate+0x274 → runtime+0x78**. Loader0x4AA440 выполняет32-битный IMUL и логический SHR12:

```text
threshold = ((raw_ChargeTime * ticks_per_second) mod 2^32) >> 12
```

Требуется реальная частота тиков из выполняющейся игры. Её нельзя вывести из одного поля ChargeTime или имени карты. Например, при явно выбранных20TPS значение raw2048 даёт порог10.

Tick после положительного callback увеличивает **байт instance+0x10B**, затем расширяет его нулями доDWORD и сравнивает с runtime+0x78. При отрицательном результате callback байт сбрасывается в0. Последовательность подтверждена инструкциями0x4A8BE9..0x4A8C38 и0x4A8C64.

Следствия именно для этой ветки:

- порог0 всё равно требует положительного callback; начиная с0 первая успешная проверка даёт counter1;
- порог255 достижим после255 подряд положительных проверок;
- порог256 или выше недостижим: после255 байт переполняется в0;
- отрицательная проверка разрывает накопление и обнуляет счётчик;
- достижение порога само по себе не гарантирует выстрел: затем идут проверки состояния и маны.

Это счётчик успешных **проверок в tick**, а не самостоятельный абсолютный таймер. Ранние выходы, пауза состояния и другие действия ловушки не эмулируются. API не заменяет это приближённой формулой «столько-то секунд до выстрела».

## Неизвестные поля

Для **Traps+0x204** подтверждён только перенос16 бит до runtime+0x98 и editor model+0x238. Точный поиск смещения нашёл чтение0x4F8C1C, но оно находится в initializer MyComputerPlayer0x4F8750 с другим устройством исходных данных. Идентичность source+0x98 с определением Trap не установлена, поэтому это чтение исключено из доказательств назначения Traps+0x204. Соответствующая пометка добавлена в `unresolved-field-traces.json`.

Для Terrain+0x198 и+0x224 текущий точный поиск не установил нового смыслового потребителя. Это не доказательство неиспользуемости: смещённые указатели, aliases, bulk-копии и неразмеченный код могут скрывать обращения. Скрытая подпись Mana Gen. по-прежнему не привязана к Traps+0x204; новое имя ей не назначено.

## API и проверка

`native_trap_semantics.py` предоставляет только расчёты и диагностику без изменения входных байтов:

```python
flags = trap_editor_flags_projection(record)
charge = trap_charge_projection(record, ticks_per_second=actual_tps)
radius = trap_los_range_projection(record, tracking=False)
step = advance_trap_charge_counter(counter, condition_met, threshold)
```

Flags-проекция показывает `dropped_bits`, charge — `threshold`, `multiplication_wrapped` и `reachable_by_byte_counter`; radius — точный32-битный порог и правила сравнения. Для обычного сохранения используется прежний raw-preserving codec; эти проекции не являются командой очистить файл.

Проверены **58 граничных сценариев**: каждый из32 бит, границы255/256, переполнение произведения, повторные проверки через полный цикл256 значений байта, сброс, порог0, большие радиусы и неверные аргументы. Сверены **22 выдержки и98 инструкций** первичных доказательств.

Целевой аудит80 файлов карт дал **1261 запись Traps**. При явно выбранном сценарии20TPS нет недостижимых charge-порогов; у текущих записей native Flags-сборка не теряет битов, переполнений LOS-радиуса также не найдено. Это результат сценария, а не утверждение о частоте работающей игры. Отдельно просмотрены три основные области по16 ловушек.

SHA-256 всех17 основных входных файлов,80 выбранных файлов корпуса и обоих EXE совпали с закреплёнными. Игровые файлы и исходники параллельного редактора не менялись; изменённые ловушки в игре/Editor Pro не запускались.
