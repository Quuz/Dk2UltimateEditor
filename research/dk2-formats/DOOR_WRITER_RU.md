# Doors: полный writer Pro/RC3 и восемь неназначенных байт

Этап66. Полностью исполнены writer Editor Pro4A8BF0 и RC34AE400: по21 сценарию, всего42 вызова и50 выведенных616-байтных записей. Найдено конкретное поведение сборки, которое нельзя воспроизводить как правило безопасного сохранения: при ограниченных32 символами строках **восемь байт каждой двери остаются прежним содержимым стекового буфера**.

Это факт проверенного пути writer. Он не доказывает, что именно эти байты приводили к крашу или графическим артефактам: ранее исследованные raw-конвертеры их не переносят в определения. Исторический смысл участков и наличие иных потребителей глобально не установлены. Все эксперименты выполнены в памяти EmulatorHelper, исходные файлы игры и EXE не менялись.

## Какие участки writer не назначает

Смещения hex, от начала616-байтной записи Doors без56-байтного заголовка секции:

| Raw offset | Размер | Адрес относительно ESP при входе в writer |
|---|---:|---|
| 21E | 2 | ESP−4A |
| 220 | 4 | ESP−48 |
| 230 | 2 | ESP−38 |

Запись начинается по EntryESP−268hex; внутри цикла это currentESP+4C. Для stack seeds00/A5/FF и меняющегося шаблона полный native-выход сохранил соответствующие исходные байты. Одинаковый результат получен в обоих редакторах.

Writer не получает исходную raw-запись как источник этих участков. Совпадение сохранённых значений с предыдущим содержимым стека не равно сохранению исходного файла. Собственный редактор должен хранить эти8 байт из входной записи и не обнулять/генерировать их автоматически.

У отдельного `Doors.kwd` ранее наблюдались ненулевые значения99/22/C0FA в этих местах, у каталогов карт — нулевые. Это совместимо с несколькими возможными историями записи; новый опыт не доказывает единственного исторического производителя конкретного файла.

## Повторное использование буфера и длинные имена

Настоящий helper4AB3B0/4B0BC0 копирует **всю CString length**, а аргумент32 использует только для дополнения короткой строки нулями. Он не ограничивает длинную строку32 символами.

Для синтетических имён543/544/548/562 символа проверены точные перезаписи ранее назначенных полей внутри616-байтного output buffer. При562 символах все три неназначенных участка становятся байтами имени. В опыте с двумя моделями первая имела562 символа `Q`, вторая — короткое имя. **Обе выходные записи** содержали `Q` во всех8 участках: второй проход оставил содержимое предыдущей записи в переиспользуемом scratch buffer.

Допустимость таких имён через настоящий GUI здесь не проверена. Сценарии не выходят за616 байт output buffer; переполнение stack или длинного sound string не выполнялось. Это проверка функции/helper и межзаписного состояния, не воспроизведение обычного пользовательского действия с длинным именем.

## Полная сборка и прочие ограничения

Writer копирует шесть84-байтных ArtResource через настоящие getters41CE60/426210; записывает прямые scalar поля, ID, sound name32. Height берётся из modeldouble280, умножается на native binary644096 и преобразуется настоящим ftol. В тестах использованы точные бинарные1.25/2.25; произвольное дробное x87 rounding этим не сертифицировано.

Настоящий flags encoder41F4E0/4299F0 строит толькоE0 из трёх BOOL29C/2A0/2A4. Ненулевые BOOL80000000 тоже считаются включёнными. Сам writer не читает исходный raw FlagsDWORD; вывод о потерях прочих битов при roundtrip дополнительно опирается на ранее проверенный decoder. Независимый сериализатор сохраняет все невыбранные биты.

Заголовок строится как N=contextCount, S=56+616*N, D=616*N. Физический порядок массива сохранён. При этом null slots пропускаются при выводе records без исправленияN/S/D. В четырёх синтетических случаях на два профиля получаются противоречивые файлы с объявленным большим числом записей. Это не доказательство, что настоящий GUI штатно формирует такие массивы. Исправный serializer должен считать именно реально выведенные записи.

В header46/47 при заданном date provider также сохраняются два stack byte — EntryESP−26A/−269. Все56 байт заголовка сравнивались. Подменён только date helper, поэтому эти наблюдения не объявлены полной спецификацией реального Windows timestamp.

## Охват native-проверки

Для каждого случая проверены все байты заголовка/records, полный context, обе модели, массив указателей, исходные CString buffers и счётчики файлового вывода. Native returnAL сохраняется до сравнительного наблюдателя; EAX наблюдателя не выдаётся за полный исходный return register.

Десять полных функций повторно считаны из Ghidra и сверены с исходными PE: два writer и по четыре настоящих helper — flags, resource getter, CString copy, ftol. Writer обеих версий имеет834 байта; различающиеся профили контекста4B8/4BC против4B4/4B8 сохранены явно. Внешние подстановки — только память вместо file Write и детерминированная дата. Совпадение поведения двух редакторов не делает его обязательным правилом формата: они могут иметь общие дефекты.

82 файла содержат656 Doors. Для каждого проверены четыре независимые raw-правки —236,21E,220,230 — с побайтным сопоставлением всего контейнера: **2624 точечных пересборки в памяти**. Все остальные байты, порядок и соседние секции сохранены. Все четыре исходных EXE совпадают с историческими SHA.

Машинная схема `door-writer-semantics.json` вложена в `door-semantics.json.phase66_writer`, пакет остаётся67 компонентов. API `native_door_writer.py`: `record` — явная проекция исходного writer с переданным prior scratch; `patch_word236` и `patch_untransferred` — сохранные точечные правки. Основной безопасный путь — raw-preserving codec, не генерация стекового содержимого.

Воспроизведение: `emulate_door_writer.py`, `prepare_door_writer_primary.py`, `build_door_writer_semantics.py`, `audit_door_writer.py`. Итоговые счётчики — `phase66-validation.json`; входы/выходы — `phase66-door-writer-emulations.json` и соответствующие Ghidra snapshots.
