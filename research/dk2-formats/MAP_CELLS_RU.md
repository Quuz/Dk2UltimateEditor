## Физическая запись карты

Секция Map начинается с36-байтового заголовка. За ним идут `width*height` клеток по4 байта; X меняется быстрее Y, индекс байта клетки —`4*(y*width+x)`.

| Смещение секции | Тип | Значение |
|---|---|---|
|0 |u32 |100 /`0x64`,тип секции |
|4 |u32 |4,длина поля размера секции |
|8 |u32 |полная длина секции |
|12 |u32 |101 /`0x65`,header block |
|16 |u32 |8,длина dimensions |
|20 |u32 |width |
|24 |u32 |height |
|28 |u32 |102 /`0x66`,data block |
|32 |u32 |длина массива клеток |

| Байт клетки | Физическое поле | Проверенный результат |
|---|---|---|
|0 |TerrainId,u8 |ID ландшафта |
|1 |PlayerId,u8 |ID владельца |
|2 |NativeMapFlags,u8 |Набор флагов, native writer отдельно вычисляет значения1/2 для мостов |
|3 |OpaqueFourthByte,u8 |В проверенных loader/converter не переносится; сохранять raw |

Прежнее имя `bridge` у byte2 слишком общее: обычные клетки тоже получают1. В `editor-format-package.json` поле теперь называется`flags`, четвёртое —`opaque`; добавлены явные legacy aliases `bridge→flags`, `unknown→opaque`. Старый summary codec `bridge_values` оставлен для совместимости; его имя не означает доказанный универсальный enum.

## Как игра и редактор читают клетку

Game parser`0x56D2D0` обрабатывает до`0x4000` клеток за блок чтения и сохраняет X/Y между блоками. Для каждой клетки строится промежуточная структура16 байт:

```text
+0 DWORD presenceTerrain = 1
+4 DWORD presencePlayer  = 1
+8 DWORD presenceFlags   = 1
+C byte terrain
+D byte player
+E byte flags
+F byte 0
```

Перед заполнением parser обнуляет весь DWORD+C и читает только первые три байта raw-клетки, после чего сдвигает источник на4. Четвёртый raw-байт не становится промежуточным byteF.

Editor Pro использует converter`0x42D1B0`. Он также читает только byte0/1/2, но flags делает **OR** с уже существующим byteE. В нормальном parser перед этим initializer`0x42D1A0` обнуляет DWORD+C. При отдельном вызове converter без initializer старые биты сохранятся — это проверено native-прогонами с начальным0x40.

Четыре запуска полного игрового parser с одинаковыми картами3×2, различавшимися только четвёртым байтом0/1/0xA5/0xFF каждой клетки, дали одинаковые захваты координат и intermediate-структур. File-read заменён контролируемым буфером, callback клеток — захватом; сама логика parser выполнялась исходными инструкциями.

## Какие флаги записывает Editor Pro

Writer`0x494470` берёт packed массив TerrainId из model+`0x950`, массив владельцев из+`0x954`, width/height из+`0x990/+0x994`, отдельное storedCount из+`0x998`. Для корректной карты storedCount должен совпадать сwidth*height: заголовки используют storedCount, циклы — dimensions.

Особые ID прямо зашиты в код:17,26,36. В предоставленном Terrain.kwd это Wooden Bridge, Stone Bridge, Hero Stone Bridge. Water имеет ID4, Lava —5.

Для обычной клетки, TerrainId которой не17/26/36, writer присваивает flags=1.

Для клетки моста код читает четыре соседа в линейном массиве: `i+1`, `i−1`, `i+width`, `i−width`. Сначала проверяет все четыре наWater4: любое совпадение присваивает1. Затем проверяет все четыре наLava5: любое совпадение присваивает2. Следовательно, при наличии иWater, иLava **последним остаётся2**.

Если среди соседей нет ни4, ни5, **flags не присваивается**. Остаётся byte из общего scratch DWORD: от предыдущей клетки, предыдущей строки или исходного stack-содержимого, если такой мост идёт первым. Поэтому это не чистая функция только от текущего TerrainId и соседей без состояния обхода.

Примеры native-прогонов:

- Мост с соседямиWater иLava получает2.
- Два первых моста без жидких соседей сохраняют явно заданный исходный scratch flag0xA5 у обоих.
- После обычной клетки мост без жидких соседей наследует1.

Границы массива внутри этой ветки не проверяются. `±1` означает соседнюю **ячейку памяти**, включая переход через край строки. Для соседей за всем массивом результат зависит от окружающих байтов памяти. API `writer_cells` использует явно заданный guard, а не приписывает оригиналу ограничение координат. Эти правила относятся к inspected writer; они не являются требованием автоматически пересчитывать флаги загружаемой карты.

## Связь mask02 с runtime-состоянием

В callback игры`0x51EC60` после размещения terrain/room проверяется промежуточный byteE mask`0x02`. В runtime-клетке по`grid.data +16*(y*grid.width+x)` устанавливается или снимается bit`0x1000` WORD+8:

```text
newFlags = (oldFlags & 0xEFFF) | (0x1000 if rawFlags & 0x02 else 0)
```

Младшие12 бит владельца и остальные старшие биты **этим фрагментом** сохраняются. Остальные операции создания ландшафта/комнат остаются отдельными и не подменяются этим API.

С учётом writer mask02 связан с веткой лавового основания моста,01 — с водной веткой или обычным default. Из одного этого callback нельзя вывести все эффекты жидкости, навигации и рендера. Полный room-placement путь здесь не эмулировался.

## Четвёртый байт при native-записи

Writer заполняет только три byte локального DWORD по frameESP+`0x10/+0x11/+0x12`, затем передаёт4 байта сframeESP+`0x10` вfile vcall38. Записи в четвёртый byte`+0x13` в проверенном теле нет. Он сохраняет предварительное содержимое стека, а не исходное поле карты.

В восьми запусках **полного тела writer** заданные scratch byteFlags и fourth byte проходили через обычные циклы и read-only file-capture callback. Проверены весь выходной файл с заголовком, его длина, первый/последний DWORD клетки и FNV. В разных fixtures fourth0/7/0x5A/0xFF попадал в записанные клетки без нового присваивания.

Это аналогичная особенность writer, как ранее найденный F4 у Effects, но здесь подтверждена отдельными функцией и полными native-прогонами. Наш редактор должен сохранять четвёртый raw-байт, а не имитировать stack-содержимое и не подставлять0 на основании отсутствия загрузки.

## Интеграция и границы проверки

`native_map_cells.py` разделяет `decode_cell`, точечный `patch_cell`, игровую проекцию bit1000 и явно native `writer_cells`. Обычное сохранение сохраняет raw4 bytes. Native-генерация требует явного решения пользователя/редактора, поскольку она может менять исходные flags и четвёртый byte.

`phase28-validation.json`:1287 граничных проверок,22 успешных native-прогона и96 точечных пересборок в памяти двух реальных Map-файлов. Проверены изменения каждого из четырёх байтов у первой/средней/последней клетки с сохранением заголовка и всех соседних данных.

В22 входят8 полных editor writer,4 полных game parser,4 editor converter и6 финальных runtime flag fragments. Все подмены относятся к памяти эмулятора; GUI/renderer и реальные игровые процессы не запускались. FNV — только контроль fixtures, не checksum формата. Один ранний runtime-fixture ставил readout до store и сохранён отдельно как superseded; в22 входят исправленные варианты, читающие после исходного присваивания.

Одна первичная цитата и218 инструкций сверены с выгрузками; после эмуляций4 полных assembly выгрузки сохранили инструкции.17 исходных файлов и2 EXE сохранили SHA-256. Воспроизведение: `emulate_map_cells.py`, `build_map_cells.py`, `build_format_package.py`, `audit_map_cells.py`.
