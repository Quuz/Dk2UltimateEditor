Этап139, 30 октября2026. Проверен предоставленный `DKII-DX.exe`, SHA-256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a`. Исходные игровые файлы, EXE и параллельный редактор не изменялись.

## Путь чтения

```text
56D2D0: reader Map
  → 5B3EB0: исходная обёртка чтения
  → native MyFile vslot8 / 5B6EA0
  → native Disc stream vslot4 / 5FFFB0
  → исходная IAT 66C1D4 → внешний ReadFile
```

Выполнены настоящий MyFile constructor `5B6E40`, pushStream `5B6F20` и native refcount-вызов `5D7230`. MyFile использует исходную vtable `671F80`, Disc stream — `672FE8`. Сам 32-байтовый Disc stream имеет явно подготовленное состояние после открытия: handle, offset12, нулевые mapping/semaphore fields. Native open/CRT allocation/close не выполнялись.

Подготовлены только внешние API ReadFile, SetFilePointer и InterlockedIncrement по адресам, уже стоящим в исходной IAT. ReadFile работает с одним ограниченным потоком в памяти и возвращает фактическое число байтов, в том числе0при EOF. Это объявленная модель внешнего API, не тест реальных Windows handles. Ни одна инструкция игры, IAT entry или исходная vtable не заменена; все1056байт IAT защищены и сверены.

## Преобразование клеток и чанки

Reader формирует16байт MapMID на клетку: presence DWORDs=1по0/4/8, TerrainID поC, PlayerID поD, flags поE, нуль поF. Четвёртый raw-байт KLD не читается в эту структуру. Это не runtime mask поC 16-байтовой игровой клетки.

Чанк содержит максимум16384клетки,65536байт; глобальный буфер — `746EC0`. На карте129×128 проверены16512клеток:16384в первом чанке и128во втором. Все координаты и все16байт каждой выходной записи совпали с независимым расчётом, включая перенос между строками и чанками. Второй чанк перезаписывает только начало общего буфера; его остальная часть сохраняется.

На исходном AutoSaveMap.kld проверены все625записей. В другой памяти-копии изменён только opaque BYTE3 одной клетки; все625выходных MapMID и остальные подготовленные области, кроме raw-потока и соответствующего raw-буфера, остались идентичны. Это не новое название неизвестного байта: его смысл в файле по-прежнему не установлен, сохранять его необходимо.

## Дефект обработки короткого чтения

`5B3EB0` сравнивает фактически прочитанное число байтов с запрошенным. В result записывается1при равенстве и0при коротком чтении. Но reader `56D2D0` проверяет только `result < 0`. Поэтому0тоже позволяет продолжить разбор.

Проверены три повреждённые копии маленькой карты3×2. Приёмник записывает callback-данные и не создаёт игровые объекты. Входной общий буфер явно заполнен `A5`; это условие опыта, не гарантированное значение в игре.

| Повреждение payload | Прочитано вместо24байт | Результат |
|---|---:|---|
| Нет последнего opaque-байта | 23 | return1,6callback; MapMID совпадают с ожидаемыми |
| Нет последних flags и opaque | 22 | return1,6callback; flags последней клетки взяты из `A5` буфера |
| Payload отсутствует полностью | 0 | return1,6callback из оставшегося `A5` содержимого буфера |

Три пути выполнены оригинальными функциями; два последних дополнительно подтверждены Ghidra. Никакой вывод о создании корректного мира из таких данных или о краше Windows-игры не делается. На реальном запуске старое содержимое буфера может быть другим.

Совместимый редактор должен **сохранять строгую проверку длины**, а не повторять ошибочное принятие повреждённого файла. Существующий lossless codec не ослаблен: перечисленные усечения он отвергает.

## Заголовки и режим пропуска

При активном callback reader использует число клеток `width×height` с native32битной арифметикой и читает соответствующие raw-байты. Declared DataSize не ограничивает этот путь: копия карты5×5 с DataSize=0прочитана полностью и дала тот же подготовленный мир. Размер внутреннего заголовка также не проверяется этим reader: значение `A5A5A5A5` принято в диагностике. Неверные теги101или102возвращают0.

Без callback данные клеток не читаются: native getoffset/seek пропускают declared DataSize. При внешнем seek-provider, разрешающем позицию за EOF, declared1000дал позицию1036и return1. Это ограниченная проверка выбранного внешнего контракта, не полный тест Windows seek API.

Внешний дескриптор100/4/wholeSize этим входом не проверяется: stream уже находится после него. Не переносить наблюдения об отдельных полях на валидацию всего контейнера. Переполнения произвольных размеров карты отдельно не исследованы.

## Мир из raw-клеток

Пять сцен5×5 используют native reader→`51EC60`→создание/присоединение Temple, декорации и навигацию. Периметр задан исходным Terrain1 и проходит настоящий loader: solid-клетки избегают неподготовленного чтения соседей за границами. Внешние guard-клетки не подставлялись.

Хотя raw PlayerID в этих сценах равен2, исходный `44FC40` назначает не-ownable Terrain1/3явному neutral tag8. Temple22остаётся у владельца2. Начальные player counts и все player-tag указатели заданы согласованно. Проверены итоговые владельцы, здоровье, RoomTag/число клеток, сумма MapMID, маски и NAV, а также полное разбиение Object arena после замены декораций. Это не доказательство произвольных PlayerID/типов комнат.
