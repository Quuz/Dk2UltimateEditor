# Crypt: ритуал продолжается после окончания анимации

Этап 189, 4 ноября 2026 года. Проверен предоставленный `DKII-DX.exe`, SHA256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a`.

**В изученном пути существо остаётся живым участником повторяющегося ритуала. Окончание анимации само по себе не завершает этот ритуал и не расходует участника.** Это ограниченный вывод о действии и выбранном пути ИИ, не доказательство всей дальнейшей жизни существа.

## Два режима действий

Исходный `4950C0` заполняет таблицу с базой `6E4198` и шагом 29 байт. В проверках скопирован фактический результат initializer; стенд не задаёт таблицу вручную.

| Значение | Участник, действие 80 | Танец, действие 76 |
|---|---:|---:|
| Callback | `499CA0` | 0 |
| Режим завершения, DWORD +21 | 0 | 3 |
| Продолжительность, BYTE +27 | 0 | 0 |
| Селектор ресурса анимации, BYTE +20 | 5 | 28 / DANCE |

Это смещения внутри **runtime-записи действия**, не новые поля Creatures.kwd. Название ресурса селектора 5 этим этапом не назначается.

Настоящий `496AA0` для действия 80 проходит: нулевая продолжительность → режим отличается от 3 → ненулевой callback → вызов `499CA0` → возврат 1 → сохранение действия. На этой ветке нет проверки окончания анимации, её счётчика и отсутствия модели. Все 11 RET в первичном листинге callback имеют эпилоги с EAX=1.

Следовательно, этот возврат означает продолжение обработки с сохранением действия, а не «жертва принята» или «ритуал завершён». Таймеры внутри callback задают интервалы отдельных эффектов; они не являются сроком расходования участника.

У действия 76 режим 3 действительно использует признаки завершения. Исходный диспетчер может накопить оба бита и очистить действие. Это даёт причинный контроль: один и тот же сигнал окончания останавливает танец 76 и сохраняет ритуал 80.

## Что исполнено

Каждая из 11 сцен начинает с замороженной композиции этапа 188: полный raw Warlock с изменённым только в памяти UnhappyJob28 → оригинальные загрузчики → обычный ИИ при явно заданном contextMode1 → Job28 → 274 → 6 → 275/80 → лечение 900→905. Новые проверки не задают начальный action80 и не вызывают его callback напрямую.

Далее стенд явно меняет только clock и условия runtime-анимации F1/3AD/3AE, в отдельных случаях DC=0. Это проверка реакции на сигналы, а не наблюдение кадров, рассчитанных настоящим renderer.

| Проверка | Результат |
|---|---|
| Clock104 после последнего эффекта100 | HP905, действие80 и регистрация сохранены |
| Следующее105 | HP910, действие80 сохранено |
| Признаки конца анимации, 105/110 | HP910→915, состояние275, действие80, регистрация101 |
| Оба бита завершения и модель0 | Тот же живой участник и продолжающееся лечение |
| Диагностические значения FF во всех трёх BYTE | Действие80 сохраняется; это не обычное состояние анимации |
| Более поздние возрастающие clock200/205 | HP910→915, состояние275/80 и регистрация сохранены |
| Действие76 без признаков конца | Остаётся76 |
| Действие76 с концом анимации либо двумя готовыми битами | Очищается до0, HP905 |
| Явный исходный `4966A0` для80 | Действие0, HP905, без уничтожения существа |

Контроли 76 используют настоящие start/stop API после изученного ритуала. Они не выдаются за самостоятельное решение участника стать посетителем.

## Переполнение часов и отдельный выход ИИ

Для последовательности MAX→0→4 один диспетчер действий сохраняет регистрацию и действие80; участник остаётся живым, HP915. При добавлении обычных вызовов ИИ та же диагностическая последовательность приводит к повторному выбору Job28 на clock0. В трассе есть второй `483AC0`, второй вход `483790` и запись времени предпочтения 10→0.

Последовательность записей состояния: начальная инициализация1 → 274 → 6 → 275 → повторный274 → очистка1 → запись1. Повторный обработчик входа видит занятую комнату и нулевое число танцоров у Warlock, возвращает отказ; `476FC0` вызывает переход1 через исходный CALL `4772B7`. Снятие регистрации и счётчика не убивает участника. Действие80 при этом остаётся, как уже наблюдалось при явном выходе на этапе181.

Это **диагностика часов, предпочтения и подготовленного contextMode1**, а не штатный срок ритуала и не доказательство эксплойта в живой игре. Возрастающие 200/205 такого выхода в проверенной сцене не дали. Полный World scheduler и все причины прерывания не восстановлены.

## Сравнение с настоящей веткой жертвы

Ранее исполненный храмовый `472930` явно пишет ингредиент в историю и вызывает установку HP=0; см. `TEMPLE_CREATURE_ENTRY_RU.md`. Даже там дальнейшее удаление экземпляра из мира не следует автоматически из HP=0.

Новые Crypt-сцены сохраняют положительные HP и живые registry-записи обоих существ. У проверенного действия нет встроенного расходования по окончании анимации. Поэтому точное описание сейчас — **участник ритуала**, а не обычный работник с доказанной зарплатой/опытом и не обязательная одноразовая жертва. Отдельные неисполненные пути смерти или других версий этим не исключаются.
