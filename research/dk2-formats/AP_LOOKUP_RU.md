# Action Point: поиск ID и сохранение указателей через вызовы

Этап76,28 октября2026. **04 и08 здесь — маски битов Flags**, а не смещения отдельных полей. В raw C5 Flags занимает WORD по payload+12; в runtime AP — BYTE+32. Игровое назначение обеих масок остаётся неизвестным.

Исследованы точные `DKII-DX.exe` и предоставленный старый EXE из `DKII 13`; имя папки не удостоверяет розничный номер версии. Все смещения ниже hex, размеры и количество проверок — decimal.

## Как CWorld находит AP

| EXE | Native getter | Общая таблица tag→pointer | Virtual slot |
|---|---|---|---|
| DX |50FAE0|6EE540|2C8|
| Старый предоставленный |504140|6D95C8|2C8|

Getter берёт WORD head из `world+12`, разрешает его через общую таблицу указателей и сравнивает `entity BYTE37` с **младшим байтом** аргумента. При совпадении возвращает указатель в EAX. Иначе переходит по `entity WORD08` и продолжает до null-указателя.

Следствия, проверенные исполнением обеих функций:

- Порядок ID может быть несортированным: раннего выхода по сравнению величины здесь нет.
- При повторном ID возвращается первый подходящий узел runtime-списка.
- ID0 и255 находятся, если такой узел присутствует. Старшие24 бита аргумента игнорируются.
- Изменение runtime Flags0→0C не влияет на поиск; флаги, kind и owner эта функция не читает.
- Сами функции не проверяют тип узла, владельца, число записей или циклы. Пример с искусственно неверным kind/owner проверяет отсутствие локальной проверки, а не доказывает ошибку редактора или нарушение списка в обычной игре.

Отдельной проверки `tag==0` нет: если в синтетической таблице entry0 содержит указатель, getter его использует и для head0, и при next0. Это не утверждение, что такая таблица возникает в реальной игре. Не путать возвращаемый null с найденным узлом, чей ID или tag равен0.

Вначале декомпилятор показывал return type void. Настоящий EAX сохранён до наблюдателя и проверен как указатель. Предварительная сигнатура декомпилятора не заменяет проверку инструкций и результата.

Из допустимости ID255 для этого getter нельзя выводить отсутствие ограничений в остальных подсистемах или GUI. Raw ID и физический порядок записей нужно сохранять; глобальное автоматическое перенумерование этими проверками не обосновано.

## Почему прежний поиск пропустил известный флаг

В native патруле471EB0 после AP lookup2C8 происходит такая последовательность:

```text
471EF8  сохраняет AP pointer в [ESP+20]
...     вызывает PRNG и получение клетки карты
472053  восстанавливает AP pointer из [ESP+20]
47205E  читает BYTE [AP+32]
472061  проверяет маску40
```

Старый bounded walker очищал всё знание о стеке и frame pointers после любого CALL. Он терял этот AP-указатель и не находил даже уже известный consumer40 при старте от getter. Это ограничение автоматического поиска; прежнее native-доказательство поведения самого40 не отменяется.

Новый проход сохраняет непереданные локальные aliases через явно заданные контракты:

| Вызов DX | Байт аргументов | Снятие аргументов callee |
|---|---:|---:|
| PRNG5558D0 |16|0|
| AP lookup50FAE0 |4|4|
| Map lookup508FE0 |4|4|

Ячейки аргументов, данные ниже активного стека и volatile aliases EAX/ECX/EDX всё равно инвалидируются. Для прочих вызовов остаётся прежний консервативный сброс. Подсказки virtual1D4/2C8 ещё требуют проверки типа получателя для каждого результата.

Это особенно важно для PRNG: его настоящий код меняет seed и использует собственный stack argument3 для промежуточного вычисления. Поэтому нельзя объявлять все аргументы неизменными лишь потому, что непереданная локальная переменная сохранилась.

Четыре native-композиции подтверждают конкретный случай: AP pointer в caller `[SP+20]` и12-байтная позиция `[SP+28]` сохраняются через настоящий PRNG и map lookup. Проверены Flags00/04/08/0C; после вызовов читается исходный Flags. Map lookup возвращает `base +16*(Y*width+X)` после арифметического Q12-сдвига; собственных проверок границ у него нет. Непроверенные координаты не становятся безопасными вследствие этой формулы.

Композиция начинает с настоящего AP getter; синтетический caller исполняется только после его возврата. Это не новый полный прогон патруля, навигации или state machine.

## Что дал расширенный поиск

Проход от8 getter/vslot-точек рассмотрел351 состояние и дал28 зацепок. Восстановлено известное чтение Flags47205E. Новых потребителей04/08 не установлено.

Те же правила применены в отдельном проходе к2623 точкам, включая загрузки общей tag table:135428 состояний,614 контекстов callee,275 зацепок. По сравнению с прежним результатом появился ровно один новый адрес чтения Flags — тот же47205E. Восемь корневых путей и28 анализов callee достигли лимитов.

Общая tag table содержит сущности разных классов. Совпадение смещения32 не типизирует объект как ActionPoint. Поле `function_hint` также является только подсказкой ближайшего известного CALL target: для этого контроля оно может указывать471E80, хотя полная native-функция начинается471EB0. Владельца инструкций устанавливает первичная дизассемблировка.

Косвенные вызовы/возвраты, неизвестные ABI, адреса локальных переменных через pointee, динамические индексы и другие бинарники остаются слепыми зонами. Поэтому отсутствие нового consumer — **не доказательство глобального неиспользования04/08**. Старые отрицательные поиски сохраняют свои ограничения; новый контракт нельзя автоматически применять ко всем функциям игры.

Дополнительно статически просмотрены AP-coordinate users4C8620 и5100B0. Их нельзя объявлять HeroGate consumer по одному факту получения AP; новое назначение масок из них не выводилось.

Сравниваются5888 байт world, все64-байтные узлы, вся заданная tag table, результаты и выбранные stack slots.
