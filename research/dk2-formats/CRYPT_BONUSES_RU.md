## Проверенный механизм

`4D8E60` принимает ECX=комната и новый 16-битный tag. Предыдущий tag хранится в комнате по `WORD53`.

1. При ненулевом предыдущем tag вызывается очистка `4D9570`, затем для активной сущности типа Creature уменьшается соответствующий счётчик.
2. Для нового активного Creature по ID выбирается один из18 счётчиков владельца. Monk19 соответствует `ownerBYTE1095`.
3. Владелец берётся из **roomWORD1D** через настоящий `4E52F0`. Проверка другого владельца подтвердила, что счётчик меняется у владельца комнаты.
4. Новый tag записывается в `roomWORD53` даже при неактивной сущности, другом типе или ID без сопоставления. В самой функции нет проверки типа комнаты; привязка к Crypt находится в вызывающих путях.

Счётчики находятся в `owner+108A..109B`. Карта видов зашита в двух switch-таблицах EXE: для удаления и добавления. Обе таблицы независимо сверены для всех45 индексов:41 ID имеет сопоставление,4 не имеют. По одному представителю каждой из18 групп выполнено на оригинальных функциях. Игровой смысл остальных17 счётчиков пока не назначен.

## Monk и урон

В обычной проверенной ветке `4B2CE0`:

```text
factor = 128
при вселении или WORD443: factor -= 64 один раз
если signed(ownerBYTE1095) > 0: factor -= 8 * ownerBYTE1095
factor = max(0, factor)             # с учётом других модификаторов этапа93
HP_delta = signed32(low32(factor * requested_delta)) / 128, усечение к нулю
```

Дополнительная единица счётчика уменьшает коэффициент на **8/128**, то есть на6,25 процентного пункта исходного обычного урона. При вселении эта величина вычитается из уже уменьшенного коэффициента; её нельзя вычислять как6,25% от окончательного урона.

Проверки используют пострадавшего Vampire ID8 с1000HP и запросом−100:

| Состояние | Итоговый HP |
|---|---:|
| Без вселения, регистрация Monk меняет счётчик0→1 | 907 |
| Со вселением, регистрация Monk меняет счётчик0→1 | 957 |
| Со вселением, подготовленный счётчик1→2 | 963 |
| Со вселением, удаление Monk меняет счётчик1→0 | 950 |
| Monk зарегистрирован у владельца8, пострадавший принадлежит7 | 950 |

Для подготовленного счётчика7 регистрация дала8 и нулевой HP-урон при вселении. Подготовленный15→16 дал нулевой HP-урон без вселения. Это проверки вычисления; фактическое накопление такого количества эффектов в обычной игровой сессии не проверялось.

## Граничные условия

Изменение счётчика выполняется как BYTE-сложение, после которого отрицательный signed8 результат заменяется0. Поэтому `127+1→0`, а `128−1→127`. Это не насыщение на127. Удаление при0 оставляет0. Проверены повторная установка того же tag, неактивная сущность, Object вместо Creature, ID0/1/46/255 и другой владелец.

В новых стендах списки объектов и обитателей комнаты пусты. Настоящая очистка `4D9570` выполняется и очищает `roomDWORD55`, но её ветки уничтожения объектов и изменения состояний обитателей не покрыты этими проверками. Сам зарегистрированный участник — явно подготовленная минимальная запись сущности; пострадавший Creature взят из проверенного нативного снимка этапа90.
