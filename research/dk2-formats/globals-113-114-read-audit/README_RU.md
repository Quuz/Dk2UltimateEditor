# Globals 113/114 — аудит чтений (DX), корректирующий проход 2

Папка: `Tools/dk2-format-research/globals-113-114-read-audit`
Статус: **ограниченный статический аудит**. Вывод — только кандидаты и границы,
без утверждения о неиспользуемости в игре и без подтверждения смысла «+6 %».
Все выводы получены по первичным байтам закреплённого EXE, без нативного запуска.

## Цели

| Тип | Runtime WORD | База + смещение | Десятичное |
|---|---|---|---|
| 113 | `0x006F28F2` | `0x006F2550 + 0x3A2` | 930 |
| 114 | `0x006F28F4` | `0x006F2550 + 0x3A4` | 932 |

Закреплённый EXE: `Dungeon Keeper 2\DKII-DX.exe`,
SHA-256 `d7a8b854e4e4f02709eba271bead6fe2307dd6e332b5a96e70857e5b0e19fb8a`.
Декодирование — установленный Capstone 5.0.7 (`insn.size`, `operand.access`),
самописная таблица опкодов из доказательства удалена.

## Отозванные утверждения прошлого прохода

* «346 parity exclusions» и «133 scale-2 чтения исключены» — **недействительны**:
  сравнивались только стартовые адреса операнда, ширина `bytes` и ширина цели WORD
  игнорировались. Заменены на честный подсчёт кандидатов по пересечению байтовых
  интервалов (см. ниже), без какого-либо исключения.
* `classify_abs_reference` **удалён из доказательства**: он неверно определял размер
  `66 8B 0D`/`0F B7 0D`/`0F 10 0D` и не видел чтения в `CMP`/`ADD` с памятью.
* «Исчерпывающее отсутствие широких чтений» — **снято**. Обзор ниже — это только
  арифметика кандидатов по сохранённым чтениям этапа 200.
* Метка «Type112» для записи `0x51CDB0` **снята**: phase101 помещает запись Type112
  в `0x51D13F -> 0x6F28F0`. Для `0x51CDB0` приводятся только проверенные байты.
* Тождество базы `[0x6E4154] == 0x6F2550` — **условное**, не безусловное доказательство.
* Загрузчик `0x51D14D/0x51D15B` и DWORD `0x47BB4E` — **историческое воспроизведение**
  (phase101/200), а не новые находки и не новая семантика.

## Что проверено в этом проходе

### 1. Структурные кандидаты пересечения (без вывода об отсутствии)

Для каждого сохранённого alias-чтения взято структурное выражение
`[1, disp, [[symbol, scale, 0, mask]]]` и ширина `bytes`; кандидат существует, если
`[disp + scale*index, +bytes-1]` пересекает байты цели. Результат:

* 183 чтения с выражением;
* **33 load PC**;
* **66 пар (чтение, цель)**;
* **132 тройки (чтение, цель, index)**.

Диапазон `0..mask` — это граница **кодирования**, а не доказательство достижимости
или недостижимости. Все тройки остаются арифметическими кандидатами; никакого
исключения по чётности/нечётности не делается. Неподдержанные выражения остаются
неразрешёнными.

### 2. Литеральная база `0x006F2550` (5 вхождений)

* `0x4DBC13`, `0x4DBC82` — `mov eax, dword ptr [0x6F2550]`: чтение DWORD по
  смещению 0 (`0x000..0x003`), не 930/932; используется как слагаемое.
* `0x509A4D` — `mov ecx,0x12C; xor eax,eax; mov edi,0x6F2550; rep stosd; stosw`:
  обнуление 1202 байт от базы — только запись.
* `0x509A96` — `mov dword ptr [0x6E4154], 0x6F2550`: единственная проверенная запись
  литерала базы в alias-указатель. **Идентичность указателя условна** (другие пути
  записи не проверялись).
* `0x51CDB0` — `mov dword ptr [0x6F2550], eax` (байты `A3 50 25 6F 00`): проверенная
  запись 4 байт в смещение 0; значение в EAX не трассировалось. Прежняя метка
  «Type112» снята.

### 3. Две функции-кандидата (единственные, разобранные по dataflow)

Индекс в обеих — байт `+0x403` объекта-существа (поле «Experience level»). Байты и
границы инструкций проверены Capstone по закреплённому EXE.

**`0x00457880`** (нагрузки `0x4578DA` и `0x457988`, таблица `+0x1B9`):

* если `([ESI+0x3E6] & 0x8000) == 0x8000`, то требуется
  `byte[ESI+0x403] < byte[0x006F2976]`, иначе возврат (guard срабатывает только при
  установленном флаге; без флага проверка пропускается);
* `byte[0x006F2976]` — 1-байтовая runtime-копия Variables type 192; в установленном
  `GlobalVariables.kwd` запись type 192 имеет `Value = 8`;
* адрес: `word[[0x6E4154] + (level & 0xFF)*2 + 0x1B9]`; при базе `0x6F2550` это
  `0x6F2709 + 2*level`. Пересечение с 113 даёт индекс 244, с 113/114 — 245,
  с 114 — 246 (сдвиг на байт, а не точное совпадение слова);
* далее: `IMUL` на `word[EDI+0x6B5]` (`EDI=[ESI+0x370]`), деление на 100
  (магия `0x51EB851F`), кламп `[0, 0xFFFE]`; результат сравнивается с накопителем
  `[ESI+0x3FF]`, при достижении вызывается `0x48B120` (level-up).

**`0x00458F60`** (нагрузка `0x459066`, таблица `+0x237`):

* индекс `byte[EDI+0x403]`, где `EDI=[ESI+8]` — тот же объект-существо;
* **внутри функции верхней границы индекса нет**;
* адрес: `word[[0x6E4154] + (level & 0xFF)*2 + 0x237]`; пересечение с 113 даёт
  индекс 181, с 113/114 — 182, с 114 — 183;
* далее: `IMUL` на `byte[[EDI+0x370]+0x5E0]`, деление на 100, кламп `[0, 0xFE]`,
  сравнение с броском `CALL 0x5558D0` (аргумент `0x64`); успех/неуспех ведут в
  `0x4A7D90`/`0x481610`.

**Граница индекса `+0x403`.** Найдены три писателя (все проверены Capstone):
init `0x4875C9` = `1`; level-up `0x48B1E6` = `level+1` при входной проверке
`level != 10`; level-down `0x48B06A` = `level-1` при входной проверке `level != 1`.
Отсюда индуктивный поддерживаемый диапазон **1..10**. Индексы 244..246 и 181..183
в него не входят, поэтому обе нагрузки **не являются потребителями 113/114 в
поддерживаемом домене**. Это статический вывод.

**Оговорка:** полнота перечисления писателей `+0x403` не доказана (возможен
bulk-copy/load путь), а тождество базы `[0x6E4154] == 0x6F2550` условно. Поэтому
кандидаты помечены как разрешённые только при этих двух условиях, а не как
абсолютно закрытые.

## Открытые пути

* Полнота списка писателей `+0x403` (массовое копирование/загрузка).
* Условность базы alias-указателя `[0x6E4154]`.
* 132 тройки из сохранённых чтений этапа 200 остаются арифметическими кандидатами:
  для чтений вне двух выбранных функций индексный producer и границы не выводились.
* Нативных наблюдений не выполнялось; всё статично.
* Смысл и формула 113/114 не установлены; «+6 %» не доказано.
