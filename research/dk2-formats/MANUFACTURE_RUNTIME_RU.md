# Производство дверей и ловушек: файл, скорость существа и очередь

Проверено24 октября2026 на локальном `DKII-DX.exe` через Ghidra, дизассемблирование и изолированную P-code эмуляцию исходных функций. Машинная схема — `manufacture-semantics.json`, API — `native_manufacture_semantics.py`, аудит — `manufacture-semantics-audit.json`. Игровые файлы и код пользовательского редактора не изменялись.

## Что означает требование производства

| Каталог | Файл | Intermediate | Runtime | Использование |
|---|---|---|---|---|
| Doors | +0x234, unsigned16 | +0x2A8 | +0x95 | Требуемые очки производства |
| Traps | +0x1FA, unsigned16 | +0x2A2 | +0x94 | Требуемые очки производства |

Функция добавления задания0x5066E0 берёт эти WORD и записывает в начало элемента очереди без деления на4096 или TPS. Сравнение готовности — unsigned16. Это подтверждает исправление прежнего baseline `Doors.ManufToBuild:u32`: первое слово действительно отвечает за производство, а второе+0x236 остаётся самостоятельным неизвестным полем.

Например, в отдельных каталогах Wooden Door требует3000 очков, Magic Door —12000, Jack In The Box —20000. Смысл чисел установлен по игровому потребителю, а не только по подписи GUI.

## Из Creatures в одно начисление

`Creatures+0xF0A:u16` → intermediate+0x12FA → runtime+0x6BD. Путь одинаков для исследованных записей5449 и5537 байт. Загрузчик0x492320 вычисляет при положительном TPS:

```text
raw == 0 → 0
raw != 0 → max(1, floor(raw / TPS))
```

При явно выбранном TPS20 значения1..39 дадут runtime1;40 даст2. Это пример арифметики, а не измерение TPS запущенной игры.

Функция начисления0x47B190 читает уровень из instance+0x403 и runtime-скорость как unsigned16:

- Уровень1: берёт runtime WORD напрямую, без множителя и ограничения65534.
- Остальные обычные уровни: читает signed16 множитель из `global_variables_runtime+0x213+2*level`, умножает на unsigned скорость, делит на100 с усечением к нулю и ограничивает результат0..65534.

Отрицательный множитель даёт0 после ограничения. Малый положительный множитель также может обнулить начисление. Например, runtime1 при множителе99 даёт0. При уровне1 runtime65535 сохраняется; на других уровнях результат ограничен65534. Ненулевое начисление передаётся в0x4C3200.

Важное различие путей: setter0x494A70, stat ID0x12, пишет low16 аргумента прямо в runtime+0x6BD. Этот setter не выполняет деление на TPS. Нельзя повторно применять преобразование сырого Creatures-поля к значению, уже установленному через runtime stat.

API требует передать реальный множитель уровня, если моделируется соответствующая ветка. Частота вызовов state-функции, ускорения работы, действия других существ и runtime-изменения статов не моделируются; формула описывает одно начисление.

## Очередь — отдельная runtime-структура

Это **не новая структура файла KWD**. У игрока очередь расположена по+0x219, счётчик накопленных очков — WORD по+0x217.

Очередь занимает2056 байт:128 элементов по16 байт и служебные поля.

| Смещение элемента | Размер | Значение |
|---|---|---|
| +0 | WORD | Требуемые очки |
| +2 | byte | Вид:0 Doors,1 Traps |
| +3 | byte | ID типа в соответствующем каталоге |
| +4 | 12 байт | XYZ |

Служебные поля очереди: byte+0x800 opened,+0x801 head,+0x802 nextFree,+0x803 count; DWORD+0x804 world. При count>=128 добавление отклоняется. Добавление также отклоняет неизвестный kind или отсутствующее определение типа.

Возврат1 из add не обязательно означает вставку: если число подходящих готовых ящиков уже покрывает число подсчитанных blueprint, функция возвращает1 без нового элемента. Blueprint сверяются с запрошенным ID каталога, а готовые ящики — с kind и `ManufCrateObjectId` определения. Поэтому общий crate ID у разных типов может влиять на подсчёт покрытия. Пример из standalone: Steel Door и Hero Portcullis используют crate53, Barricade и Hero Barricade —56.

Декомпиляция add0x5066E0 неверно представила часть stack-параметров. Набор байтов item+2/+3 установлен по инструкциям0x5068A5..0x5068C9: первый аргумент —kind, второй —ID. Поисковый вывод с `unaff_retaddr` не используется как описание формата.

## Подтверждённое расхождение в выборе стоимости

Get0x506930 и pop0x506970 выбирают задание по **head**: `queue + 16*head`. Однако две функции используют стоимость из **физического слота №0**:

```text
completed0x506B50:
  count != 0 && unsigned16(progress) >= unsigned16(queue+0)

percent0x506B70:
  count == 0 → 0
  иначе floor(unsigned16(progress)*100 / unsigned16(queue+0))
```

Они не прибавляют `16*head`. Вызывающие функции передают именно начало очереди `player+0x219`: это проверено для обновления прогресса0x4C3200 и обёртки процента0x4C31B0. Обычный pop сдвигает head, но не очищает стоимость старого слота.

Изолированный пример, совместимый с состоянием после удаления первого из двух заданий:

| Состояние | Значение |
|---|---|
| Слот0, предыдущее задание | 3000 |
| Head | 1 |
| Слот1, текущее задание | 12000 |
| Count | 1 |
| Накопленный прогресс | 4000 |
| Результат исходной completed-функции | true |
| Результат исходной percent-функции | 133 |

При перестановке стоимостей, слот0=12000 и head=3000, тот же прогресс4000 даётfalse и33%. Это проверено выполнением исходных инструкций в Ghidra, с нормальным возвратом обоих helpers. Полный игровой сценарий с реальной мастерской не запускался: эффект в игре зависит также от построения/изменения очереди и остальных вызывающих функций. Исправление игры или автоматическая перестановка записей не выполнялись.

Процент не ограничивается100. Эмуляция для стоимости1 и прогресса65535 вернула6553500.

## Переполнение и нулевая стоимость

0x4C3200 прибавляет начисление к WORD-прогрессу с переполнением по65536, затем проверяет готовность. Например,65530+20 становится14. При постоянном чётном начислении из начального0 значение65535 недостижимо; другие работники или изменение начисления могут изменить этот результат. Функция `constant_contribution_reachability` проверяет только такой явно заданный арифметический сценарий.

После положительной проверки готовности есть дополнительный gate размещения/вместимости0x4C3B50. Только при его успехе прогресс обнуляется, выполняется pop и попытка создания ящика. Избыток очков при этом не переносится вычитанием стоимости. При отказе gate прогресс остаётся, и следующее начисление может переполнить WORD.

При count!=0 и стоимости слота0 равной0 completed возвращаетtrue, а percent доходит до **IDIV0 по0x506B93**. Изолированная эмуляция остановилась там с `Divide by 0`. При пустой очереди тот же helper возвращает0 до деления. Это конкретный опасный путь, а не утверждение, что всякая нулевая стоимость всегда вызывает падение игры.

В проверенных80 файлах карт **нет ни одной нулевой стоимости производства** среди640 Doors и1261 Traps; нет и значений выше32767. Все эти записи имеют ненулевой crate ID. Поэтому найденный нулевой делитель не объявляется причиной ранее обсуждавшегося падения.

## Что осталось неизвестным у Doors

Слово файла+0x236 → runtime+0x99 по-прежнему без установленного назначения. Поиск точных WORD-обращений дал ложный кандидат0x49B9F0: это stream-сериализация `CObject`, где три signed слова+0x95/+0x97/+0x99 разворачиваются в трёхкомпонентный блок DWORD. Это другой объект и не доказывает смысла поля Doors.

Результаты поиска сохранены в `phase15-door-word-candidates.json`; ограниченный поиск по смещениям не исключает алиасы, вычисляемые указатели, неизвестные функции и другие EXE. Неизвестному слову не присвоено предполагаемое имя.

& '../ghidra-mcp-runtime/venv/Scripts/python.exe' build_manufacture_semantics.py
& '../ghidra-mcp-runtime/venv/Scripts/python.exe' audit_manufacture_semantics.py

Проверены84 граничных сценария,72 пересборки реальных каталогов в памяти с изменением только двух байт требования производства и побайтовым сохранением остального контейнера. С исходными инструкциями сопоставлены14 эмуляций:13 нормальных возвратов и1 ожидаемая ошибка деления на0. Аудит сверяет входные снимки очереди с read-only API, результаты регистров,4 текстовые выдержки и199 инструкций.

Целевой корпус:80 файлов,3642 Creatures,640 Doors,1261 Traps. SHA-256 всех17 основных входов и обоих EXE сохранены. В общем `editor-format-package.json` теперь25 компонентов. Полные входные registers/memory и результаты изолированных вызовов сохранены в `ghidra/phase15-emulation-*.json`.

API: `manufacture_record_projection`, `creature_manufacture_projection`, `manufacture_contribution`, `manufacture_queue_projection`, `constant_contribution_reachability`. Они не записывают игровые файлы и не исправляют особенности родного движка автоматически. Runtime-очередь следует хранить отдельно от структур файлов KWD/KLD.
