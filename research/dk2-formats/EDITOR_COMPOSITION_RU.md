# Lean и связанные данные Rooms / Terrain

Продолжение расшифровки через Ghidra, 23 октября 2026. Исследован предоставленный Editor Pro, SHA-256 `989c45df779bccfc9a9e509b2ad0224a9bd269629f74792adc0320fa4b99fb09`. Новая машинная схема — `editor-composition.json`; проверка — `editor-composition-audit.json`. Это уточнение к `EDITOR_UI_FIELDS_RU.md`.

## Шесть Lean-значений — шесть отдельных байтов Terrain

| Направление | Положение | Raw offset | Intermediate | Модель редактора | Контрол диалога230 |
|---|---|---|---|---|---:|
| Horizontal | Top | `0x1CF` | `0x287` | `0x362` | 1762 |
| Horizontal | Middle | `0x1D0` | `0x288` | `0x363` | 1763 |
| Horizontal | Bottom | `0x1D1` | `0x289` | `0x364` | 1764 |
| Vertical | Top | `0x1D3` | `0x28B` | `0x365` | 1765 |
| Vertical | Middle | `0x1D4` | `0x28C` | `0x366` | 1766 |
| Vertical | Bottom | `0x1D5` | `0x28D` | `0x367` | 1767 |

Init `0x4500A0` читает первые три значения getter `0x425480`, затем ещё три getter `0x425440`. Они читают по модели +`0x362+i` и +`0x365+i`; при i>=3 возвращают0. Ресурс диалога230 связывает контроли1762..1764 с колонкой Horizontal Lean и строками Top/Middle/Bottom;1765..1767 — с Vertical Lean.

DDX `0x450130` проверяет все шесть чисел в диапазоне0..255. Commit `0x450200` берёт младший байт каждого члена диалога и вызывает `0x4254A0` или `0x425460` с индексами0,1,2. Setter не пишет при i>=3. Converter и writer Terrain подтверждают соответствующие файловые смещения. Это unsigned-представление исходного GUI без масштаба4096; формула геометрии/поведение знакового бита в рендерере этим не установлены.

`WibbleH` по+`0x1CE` и `WibbleV` по+`0x1D2` являются соседними отдельными байтами. Массив16 WORD по+`0x1AE..0x1CD` — другая область, её назначение не установлено. Он не является этими шестью Lean-полями.

## Кнопка Lean в окне Rooms меняет Terrain

Окно свойств комнаты содержит два разных указателя:

- panel+`0x13C` — определение Terrain;
- panel+`0x144` — определение Rooms.

Заполнение `0x4675F0` сначала находит Terrain по выбранному ID, затем перебирает определения Rooms, сравнивая Room model+`0x4E0` с ID найденного Terrain. При совпадении сохраняет Room pointer; явного break нет, последнее совпадение заменяет предыдущее. В вашем наборе26 Rooms имеют разные TerrainId, поэтому неоднозначности здесь нет.

Путь внешнего ключа комнаты:

```text
Rooms raw+0x394 (TerrainId)
  → converter0x42DF90, intermediate+0x468
  → callback0x49FC30, Room model+0x4E0
  → сравнение с Terrain model+0x168 (TerrainId)
```

Обработчик кнопки `0x468900` передаёт в конструктор Lean-диалога `0x450060` указатель **panel+0x13C**. Значит, при редактировании Lean из окна Rooms изменяются шесть байтов связанной записи Terrain. Отдельного набора Lean в записи Rooms этот путь не использует.

Примеры в самостоятельных каталогах: Treasury RoomId1 → TerrainId10; Lair RoomId2 → TerrainId11; Crypt RoomId26 → TerrainId41. Сопоставление должно выполняться внутри фактической области определений. Нельзя связывать Room из карты с первым попавшимся самостоятельным Terrain.kwd, если карта использует иной Globals.

## Свойства одного окна хранятся в двух каталогах

В `0x4675F0` и применении `0x467BB0` установлены следующие владельцы данных:

| Свойство окна комнаты | Фактическая запись | Raw offset |
|---|---|---|
| MaxHealth | связанный Terrain | `0x1FF` |
| StartingHealth / Initial Health | связанный Terrain | `0x1D7` |
| Depth | связанный Terrain | `0x188` |
| Damage | связанный Terrain | `0x194` |
| WibbleH | связанный Terrain | `0x1CE` |
| WibbleV | связанный Terrain | `0x1D2` |
| LightHeight | связанный Terrain | `0x18C` |
| Lean H/V | связанный Terrain | шесть байтов таблицы выше |
| HealthGain | Rooms | `0x41D` |

Например, MaxHealth попадает из Terrain model+`0x34A` в panel+`0x7C`; HealthGain — из Room model+`0x4F0` в соседний panel+`0x7E`. После применения оба возвращаются в свои объекты. Визуальное соседство в диалоге не означает соседство байтов или даже один файл.

Для собственного редактора полезно показывать единую панель, но сохранять ссылки на исходную запись и владельца каждого свойства. Общий setter «все свойства комнаты пишутся в Rooms» здесь некорректен.

## Принудительные изменения исходного GUI

Применение `0x467BB0` безусловно обнуляет три WORD связанного Terrain:

| Raw Terrain | Поле | Присваивание модели |
|---|---|---|
| `0x19A` | GoldValue | +`0x36A` =0 |
| `0x19C` | ManaGain | +`0x36C` =0 |
| `0x19E` | MaxManaGain | +`0x36E` =0 |

В assembly `0x467BCA` обнуляет EDI, затем `0x467BFE`, `0x467C0B`, `0x467C18` пишут DI в эти поля модели. Следовательно, это не только предположение декомпилятора о значении переменной.

Там же присваиваются boolean-члены флагов Terrain. Сопоставление с native flag writer `0x4254C0` даёт для подтверждённой группы формулу:

```text
projectedFlags = (oldFlags & ~0x00007FDF) | 0x00000014
```

Это устанавливает Ownable+Room и сбрасывает другие флаги указанной маски. Attackable0x20 исключён из маски: он присваивается отдельно из panel+`0x128`. Остальные поля/флаги, в том числе освещение, имеют отдельные операции; формула выше не является эмуляцией полного writer или всех неизвестных битов.

Собственный редактор не должен неявно повторять эти изменения при побайтовой пересборке. Это поведение применения свойств исходного GUI. `room_terrain_projection` сообщает только эти установленные присваивания, не меняет входные данные и не моделирует все проверки/действия диалога.

В трёх проверенных областях существующие связанные Terrain уже имеют нули в этих трёх числах и соответствуют принудительным битам. Поэтому78 проверок связей не показывают изменений для текущих объектов; побочное действие видно в коде и дополнительно проверено на искусственных ненулевых значениях.

## Неизвестный ресурс Objects — не In Hand Mesh

Сохраняется отдельный84-байтовый слот `Objects+0x170`:

```text
raw+0x170 → intermediate+0x1F0 → editor model+0x16C
```

Кнопка `In Hand Mesh...` control1595 вызывает `0x45B4D0`, затем getter `0x472D10`, который возвращает model+`0x1C8`. Writer `0x4A9390` сериализует это в **другой** ресурс `raw+0x11C`. Тот же writer отдельно сериализует model+`0x16C` в raw+`0x170`.

Итак, гипотеза «неизвестный ресурс — это In Hand Mesh» не соответствует этому пути. Следующий проход установил native-привязку этого слота к **In Hand Icon...**, а также загрузку в игровой CWorldEntry+0x1B: см. `OBJECT_RESOURCES_RU.md` и `object-resource-bindings.json`. Это отдельный слот от baseline InHandIconResource+0xC8; его84 байта нельзя заменять копией соседнего ресурса или удалять. UnknownResource Rooms+`0x1C4` остаётся неизвестным; переноса в редакторскую модель недостаточно, чтобы назначить имя по соседним кнопкам.

## Проверки и использование

`native_editor_composition.py` предоставляет:

- `terrain_lean(record)` — шесть значений с именами осей/положений;
- `set_terrain_lean(record, axis, values)` — меняет ровно три байта одной оси, принимая три целых0..255;
- `room_terrain_projection(room_record, terrain_records)` — проверяет внешнюю ссылку и показывает известные побочные присваивания исходного GUI, не меняя записи.

При отсутствии Terrain или повторяющемся TerrainId проектор сообщает проблему, а не выбирает кандидат молча. Для нескольких Rooms с одним TerrainId аудит отдельно сообщает совместное использование. Это не точная эмуляция нативного выбора «последняя Room в массиве», а диагностический API для безопасной работы с файлами.

Проверено20 граничных случаев. Выполнено246 изменений реальных записей Lean с пересборкой секции и повторным чтением: изменяются только три выбранных байта, сохраняются остальные записи, неизвестные16 WORD и соседние Wibble-байты. Проверены78 внешних связей Rooms→Terrain в трёх отдельных областях: самостоятельные каталоги, AutoSaveGlobals, указанный в descriptor kop4Globals. Пропущенных связей и дубликатов в этих областях нет.

Ни оригинальные файлы, ни исходники параллельного редактора не изменялись. Новые игровые карты/изменённые файлы в игре не запускались. Доступ к Ghidra, ранее недоступный из-за лимита проверки разрешений, в этом проходе восстановился; отдельные тайм-ауты проверки были успешно повторены один раз.
