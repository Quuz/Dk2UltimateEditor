# Traps: создание выстрела, ShotOffset и состояние после выстрела

24 октября 2026. Продолжение разбора по игровому EXE. `trap-fire-semantics.json` содержит точные коэффициенты поворота из PE, инструкции и правила переноса; `trap-fire-audit.json` — результаты проверки и значения реальных записей. SHA-256 образа закреплён в обоих артефактах. Старые raw-схемы сохраняются.

## Практический результат

Установлено, как игра поворачивает три координаты `ShotOffset`, переносит `ShotData1/2` в экземпляр выстрела и обновляет ловушку после успешного создания выстрела. Это позволяет собственному редактору точно показать точку появления снаряда и диагностировать сужение таймеров. Расчёт не запускает игру и не гарантирует создание выстрела: отдельно остаются выбор цели, состояние ловушки, ресурсы и проверки маны.

Специальный случай: для **TrapId16, Jack In The Box**, обычный вызов по ненулевой цели после создания выстрела заменяет **Data2** идентификатором этой цели. Поэтому значение ShotData2 из KWD не всегда является итоговым значением снаряда.

## Путь создания

`0x4A7FD0` подготавливает положение цели и вызывает creator **0x4A80E0**. Creator читает указатель определения из instance+0xF7. Нулевой ShotTypeId, полученный из raw+0x20D в definition+0xBB, приводит к выходу0 ещё до создания. Ошибка функции создания shot0x4B7CD0 также возвращает0; перечисленные ниже действия после создания при этом не выполняются.

В ветке ненулевой цели `0x4A7FD0` берёт её XYZ и добавляет к Z половину значения из виртуального getter цели. При отсутствии цели выбирается точка перед ловушкой. Это подготовка **целевого вектора**, а не точки появления снаряда. Точка появления отдельно рассчитывается внутри creator по ShotOffset.

## ShotOffset: точная целочисленная геометрия

Путь трёх signed DWORD:

| Координата | Raw | Intermediate | Definition |
|---|---|---|---|
| X | 0x231 | 0x2D9 | 0xC1 |
| Y | 0x235 | 0x2DD | 0xC5 |
| Z | 0x239 | 0x2E1 | 0xC9 |

Единица файловых координат —1/4096 клетки. Поворот берётся из WORD instance+0xF4; это состояние размещённой ловушки, отдельного поля heading в записи Traps нет.

Creator использует две2048-элементные таблицы signed DWORD: sine view по **0x6C1488**, cosine view по **0x6C1C88**. Вторая начинается на512 DWORD позже первой; области перекрываются. Коэффициенты имеют16 дробных бит. Они сохранены в JSON точно, включая округления исходной таблицы. Для0/512/1024/1536 коэффициенты соответствуют0/90/180/270 градусам;2048 единиц составляют полный оборот.

С учётом исходных координат P и смещений O расчёт имеет вид:

```text
mul16(a,b) = arithmetic_shift_right(signed32(low32(a*b)),16)

shotX = P.x + mul16(O.x,cos) - mul16(O.y,sin)
shotY = P.y + mul16(O.y,cos) + mul16(O.x,sin)
shotZ = P.z + O.z
```

Сложение/вычитание заворачиваются в32 бита. Каждое умножение сохраняет **только младшие32 бита до сдвига**: это не64-битное произведение, поделенное на65536. Каждое произведение округляется своим арифметическим сдвигом отдельно; нельзя сначала сложить произведения с высокой точностью, а потом округлить сумму.

Примеры относительно P=0:

- O=(4096,8192,2048), heading0 → (4096,8192,2048);
- тот же O, heading512 → (-8192,4096,2048);
- O=(4096,0,0), heading256 → (2896,2896,0), точно по коэффициенту46340;
- O=(-1,0,0), heading256 → (-1,-1,0): отрицательные произведения сдвигаются с округлением вниз;
- O=(32768,0,0), heading0 → **(-32768,0,0)** из-за32-битного переполнения умножения.32768 —8 клеток в файловых единицах.

В creator нет локальной маски или проверки границ heading: он прямо индексирует таблицу WORD-значением. Исследовательский API принимает только0…2047; он не делает `heading %2048` и не воспроизводит чтение за исследованной таблицей. Из этого не следует, что игра обычно передаёт неверные направления: нормализация может происходить ранее.

`Height+0x1C4` не подменяет Z этого расчёта: creator непосредственно прибавляет `ShotOffset.Z`. Другие применения Height не объявляются отсутствующими.

## ShotData1/2 и цель

После создания creator записывает low16 target tag в shot instance+**0x147**, затем вызывает0x4AB830. Этот helper копирует переданный XYZ-вектор в shot instance+**0x131/0x135/0x139**. Порядок не смешивается с положением появления выстрела.

После этого:

```text
raw ShotData1+0x1E0 → definition+0x7C → shot instance+0x13D
raw ShotData2+0x1E4 → definition+0x80 → shot instance+0x141
```

Оба поля переносятся целыми DWORD без масштабирования. Их смысл зависит от ProcessType/DamageType выбранного Shots; сами переносы не устанавливают универсальную единицу этих параметров. В creator при TriggerType, отличном от1 и3, и ненулевом low16 target tag дополнительно записывается1 в shot instance+0x14D. Другим веткам в этой записи не приписывается нулевое значение: исходное состояние экземпляра определяется отдельно.

Для TrapId16 в обычной ненулевой целевой ветке caller0x4A7FD0 **после** успешного возврата creator выполняет `shot+0x141 = target_tag`. Условие проверено инструкциями0x4A8043/0x4A804A/0x4A804C. В файле при этом не меняется ни байт; это дополнительное присваивание экземпляру выстрела. API показывает отдельно исходную копию и последующую возможную замену.

## RechargeTime и видимость после выстрела

`RechargeTime` raw+0x1C8 переносится через intermediate+0x270 в definition+0x74. Loader применяет:

```text
recharge_ticks = ((raw_RechargeTime * actual_TPS) mod2^32) >>12
```

После успешного создания shot creator сбрасывает ChargeTime-счётчик instance+0x10B и задаёт:

```text
instance.recharge_at_time+0xFF = (current_tick + recharge_ticks) mod2^32
```

Это абсолютный DWORD момента следующей проверки, а не ещё один дробный интервал. Полную корректность всех сравнений на границе переполнения глобального времени эта схема не устанавливает.

При файловом Flags.REVEAL_WHEN_FIRED0x2 creator сбрасывает0x10 в instance flags+0x10C и вызывает0x4A9F10 для обновления видимости. Это изменение текущего экземпляра: **файловый INVISIBLE0x20 не очищается**. Применение полного renderer/ownership/blueprint состояния не моделируется.

## ThreatDuration: два разных размера

Definition хранит ThreatDuration как32-битные тики:

```text
duration_ticks = ((raw_ThreatDuration * actual_TPS) mod2^32) >>12
```

После успешного создания shot происходят отдельные присваивания:

```text
instance+0x10E (u8)  = duration_ticks &255
instance+0x10F (u32) = 0, если duration_ticks==0;
                       иначе unsigned16(raw Threat+0x1EA)
```

Второе условие проверяет **полный DWORD**, а не уже усечённый байт. Поэтому при256 тиках и Threat74 получаются `duration_byte=0`, `Threat=74`. При45 секундах и явно выбранных20TPS получаются900 тиков, сохранённый байт132; при60 секундах —1200 тиков, байт176. Это не доказательство, что фактическая угроза длится6,6 или8,8 секунды.

Причина оговорки: tick0x4A84E0 уменьшает ненулевой duration byte, но позже проверяет **только instance Threat!=0** перед вызовом функции0x4B32A0. Условие `duration_byte!=0` в этом gate отсутствует; прямого обнуления Threat при исчерпании duration в исследованном tick нет. Это подтверждается раздельными диапазонами0x4A857F..0x4A858B и0x4A8CD3..0x4A8D09.

Таким образом, файловое имя ThreatDuration нельзя безоговорочно выдавать за проверенный срок прекращения воздействия. Глобальную «вечную угрозу» схема тоже не утверждает: другие переходы состояния, удаление объекта, косвенные присваивания и код за пределами исследованного тела остаются отдельной задачей.

Отладочная функция самого EXE0x4AA130 подписывает эти поля `ThreatDuration` и `Threat`, а byte-счётчик ChargeTime —`ChargeTimeBeforeShot`. Это native-подписи экземпляра; они не отменяют установленную разницу ширин и условий.

## Что осталось неизвестным

Целевой поиск потребителей флагов0x4/0x8/0x400/0x4000 пока не дал подтверждённых игровых назначений. Поиск63 функций с обращениями по смещению0xF7 содержит и **Doors**: совпадающие смещения definition+0x88/0x8B не доказывают одинаковый класс. Кандидаты сохранены отдельно; новым именем поля они не стали. Биты продолжают сохраняться как отдельные raw-маски.

Назначения Traps+0x204, Terrain+0x198/+0x224 и Objects+0x34C остаются неустановленными. Ненахождение прямого обращения в ограниченном поиске не доказывает неиспользуемость.

## API и проверка

```python
from native_trap_fire import trap_shot_origin, trap_post_creation_projection

origin = trap_shot_origin(record, position_raw=[x,y,z], heading=heading)
after = trap_post_creation_projection(
    record, ticks_per_second=actual_tps, current_tick=tick,
    target_tag=target, instance_flags=flags_byte)
```

Origin принимает координаты4096 единиц/клетку и возвращает точный signed32 результат, срабатывания переполнений умножения и итоговых координат. Post-creation проекция **условна на успешное создание**: флаги стоимости/состояния не превращены в предсказание выстрела. Для ShotTypeId0 явно сообщается ранний выход creator.

Проверен31 граничный сценарий: четыре направления, диагональ, отрицательное округление, переполнение произведений и координат, пороги duration255/256, wrap момента перезарядки, raw-перенос Data1/2 и специальная замена Jack In The Box. Выполнено48 правок ShotData1 на реальных записях с пересборкой секций и повторным чтением; соседние байты и остальные записи сохранены.

Целевой аудит80 файлов карт:1261 запись Traps. При явно выбранных20TPS у804 записей32-битный ThreatDuration сужается при записи в байт; случаев нулевого duration byte при ненулевом Threat в этом наборе не найдено. Это анализ заданного сценария, не измерение частоты работающей игры.

Для девяти различных троек ShotOffset из корпуса проверены все2048 направлений —18432 расчёта. Переполнений произведений у этих троек нет. Отдельная искусственная тройка с8 клетками подтверждает необходимость воспроизводить native-переполнение. Сверены5 выдержек и138 инструкций; таблицы коэффициентов закреплены собственными SHA-256.

Все17 основных входных файлов,80 выбранных файлов карт и оба EXE сохранили закреплённые хеши. Игровые файлы и исходники вашего редактора не менялись. Изменённые ловушки в игре/Editor Pro не запускались.
