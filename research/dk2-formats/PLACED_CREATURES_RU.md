Ширина gold остаётся16 бит, health32 бита, AP32 бита. Нельзя уменьшать их из-за внутренней модели редактора.

Конвертеры игры `56F330/56F430/56F540` и редактора `42F410/42F510/42F620` переносят запись в intermediate56/84/64 байта с признаками присутствия. Флаги OR-ятся в предварительно инициализированные байты. Путь исходного parser включает initializer; отдельному converter нельзя без проверки давать грязный буфер. Смещения intermediate перечислены в JSON и отличаются от файловых.

Game callbacks `520180/520460/5208B0` сначала передают весь intermediate в world checksum. Затем создатель получает центры клеток Q12: `low32((X<<12)+800h)`, аналогичноY и **Z=0**. Raw Z всё равно переносится и участвует в пути суммы. В обычном сохранении независимого редактора следует оставлять исходный DWORD08.

## Золото и здоровье являются процентами

Baseline названия `GoldHeld` и `InitialHealth` не задают единицы. Здесь подтверждены проценты относительно характеристик существа с учётом уровня.

Основа золота берётся из unsigned WORD определения runtime69C, здоровья — runtime692. При raw Level1 используется сам WORD. При остальных уровнях, включая0, применяется signed WORD роста из Variables runtime:

```text
gold growth:   [global6E4154 + 13Bh + 2*level]
health growth: [global6E4154 + 0E1h + 2*level]
scaled = trunc_toward_zero(unsigned_base_WORD * signed_growth_WORD / 100)
```

Произведение этих16-битных аргументов помещается в signed32. При последующем FILD результат помещается в младший DWORD qword со старшим DWORD0. Поэтому отрицательный scaled интерпретируется как большое unsigned32; этот крайний случай не исправляется нашим raw codec.

Для золота загрузчик вычисляет `unsigned rawGold * double0.01 * unsigned32(scaledGold)`, преобразует через `634F30` в signed64 и передаёт младший DWORD helper `48AE70`. Он прибавляет его к текущему instance3FB по модулю2³² и ограничивает **unsigned** сравнением с актуальной вместимостью. Начальное количество зависит от создания экземпляра и не объявляется здесь всегда нулевым. Raw Gold100 означает100% вместимости в этом пути, а не100 монет.

Здоровье сначала меняется дельтой `1-currentHealth`, затем дельтой:

```text
ftol64(unsigned rawHealth * double0.01 * unsigned32(scaledHealth) - double1.0).low32
```

Для Good actual CreatureId1C используется helper490120, для прочих —4B2CE0. Это путь задания процента; итоговое состояние зависит также от обработчика здоровья и ветки умирания. Формула `finalHealth=rawHealth` неверна, а универсальная точная формула итогового здоровья этим этапом не заявляется.

Константы0.01/1.0 прочитаны из PE66EB28/66EB30. `634F30` включает округление к нулю в x87 control word, выполняет FISTP qword и возвращает EDX:EAX. Семь native-прогонов подтвердили вычисление выражения здоровья до этого вызова, включая Level0 и отрицательный growth; ST0 захвачен в64-битном представлении. Это не проверка всех80-битных округлений, преобразований за диапазоном int64 или полного damage helper.

После создания вызывается48B120 до достижения raw уровня: `max(level-1,0)` вызовов. Предела10 в проверенных callbacks нет. Игра сама не превращает raw Level0 в1; Editor Pro делает это в своей модели.

## Два прежних неизвестных байта

`WanderRadius`: raw Neutral17/Good1D → intermediate37/51 → instance418. В native diagnostic dump490240 значение явно выводится с подписью **WanderRadius** по строке69CF3C. Подтверждены имя и перенос полного byte. Поиск по8729 размеченным участкам нашёл инициализацию, переносы, trigger assignment и diagnostic read, но **не установил алгоритм радиуса и его единицы**. Не выдавать это поле за проверенную дистанцию в клетках.

`PartyId`: raw Good1E → intermediate52 → instance417, native diagnostic подпись **PartyId** по строке69CF54. Найден конкретный потребитель458C70:

1. У действующего существа должен быть runtime46F bit2, Leader.
2. Оно обходит связный список существ владельца.
3. Кандидат должен иметь тот же byte417, bit4 Follower и состояние25E либо ожидающее состояние32D равноеDE.
4. Для кандидата вызываются objective48BE20(0C,leader40D,0) и state48AD30(E2).

В этом потребителе FF не исключается как sentinel: два FF сравниваются равными. Это подтверждает реальное участие байта в группировке. Полная логика отрядов, spawn и встроенные записи C9 относятся к дополнительным путям.

## Flags и Flags2

Good callback передаёт все8 бит Flags в настоящие setters, соответствующие runtime byte46F. Neutral/Keeper передают только маску **F9**, пропуская Leader/Follower02/04; прежние runtime биты02/04 сохраняются. Это не повод удалять эти биты из файла.

Good Flags2 передаётся иначе:

| Raw маска | Runtime3EA маска | Дополнительная запись |
|---:|---:|---|
| 01 | 00000080 | — |
| 02 | 00000100 | — |
| 04 | 00000800 | — |
| 08 | 00000200 | instanceF0=1/0 |

Остальные runtime биты сохраняются. Старшие raw Flags2 F0 этим callback не используются, но независимый редактор должен сохранять их. START_AS_DYING в основном Flags80 включает дополнительную ветку проверки здоровья и вызова умирания; она не вошла в эмуляции фрагмента флагов.

Trigger setter49A950 сохраняет WORD в419; при ненулевом ID ищет trigger518090 и копирует его byteF в instance4F9. Границы ID и восстановление при отсутствии trigger этим путём не установлены.

## Нормализация Editor Pro

Для map model DWORD60 !=1, проверенной современной ветки:

| Вход | Результат для модели gold/health |
|---:|---:|
| 99 | 99 |
| 100 | 100 |
| 255 | 100 |
| 256 | 0 |
| 300 | 44 |
| FFFFFFFF, только DWORD health | 100 |

Сначала берётся **low8**, потом применяется `min(byte,100)`. Модель хранит здоровье в byte1A и золото в byte1B. При сохранении они расширяются обратно до DWORD/WORD с нулевыми старшими байтами. Поэтому ограничить весь raw DWORD числом100 до сужения — другое поведение. Raw Level0 становится1;255 остаётся255.

У map model major60==1 есть отдельная x87 ветка: значения преобразуются из абсолютных через Health WORD15EA/MaxGold WORD1622 определения в проценты, затем снова low8/min100. Она исследована статически и исключена из числового API и native-прогонов. Поля версии модели60/64 нельзя автоматически приравнивать к версии произвольного заголовка KWD.

Для **отдельного Good C7** callback490EB0:

- В model21 явно записывает PartyId **FF** и не читает input intermediate52.
- Загружает Flags, затем финализатор41CF20 очищает Leader/Follower02/04.
- При unsigned major60<=2 и minor64<50 дополнительно очищает ReturnToHeroLair10.
- Objective0 заменяет на19, AP на3; иначе AP setter41CF40 сохраняет только low8 DWORD.

Для Keeper AP сохраняется полным DWORD в model1C. Не применять к нему Good byte-правило. Для Neutral/Keeper здесь нет вызова Good-финализатора флагов.

Полный Good serializer4952F0 обнуляет32-байтовое назначение, пишет Z0, gold byte→WORD, health byte→DWORD, WanderRadius/PartyId из model20/21, Flags codec8/Flags2 codec4. Нулевой model Objective22 меняет на19, причём изменяется сама модель. AP getter41CF30 явно zero-extend byte24. При null model destination остаётся нулевым. Ветка unique/clone может заменить записываемый CreatureId; в native-fixtures она выключена, её полная логика здесь не проверена.

Отряды C9 имеют другой callback, который может задавать участникам PartyId и групповые флаги. Сбросы **отдельного C7** не следует без дополнительного анализа переносить на сохранение участников C9.

Независимый редактор должен сохранять raw значения, включая старшие биты процентов/AP/Flags2, PartyId и Z. Совместимость с конкретными потерями Editor Pro должна быть отдельным явным режимом.
