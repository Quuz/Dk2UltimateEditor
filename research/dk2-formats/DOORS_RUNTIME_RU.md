## Поле изготовления состоит из двух слов

Baseline-поле `ManufToBuild:u32` по+0x234 нужно уточнить. Оба нативных конвертера читают его как два отдельных WORD; загрузчики и writer тоже переносят их раздельно:

| Файл | Ширина | Intermediate | Runtime | Модель Editor Pro | Установленный смысл |
|---|---|---|---|---|---|
| +0x234 | u16 | +0x2A8 | +0x95 | +0x292 | Нативная подпись `Manf. To &Build:` |
| +0x236 | u16 | +0x2AA | +0x99 | +0x28A | Не установлен |

Первое слово связано с контролом12691, panel+0x70. Нативный диапазон ввода0..32767. Второе слово загружается и сохраняется, но в исследованной панели свойств отдельной привязки для него нет. Из этого не следует отсутствие других потребителей.

При редактировании количества изготовления менять только два байта+0x234..235. Старшее слово сохранять отдельно. Оригинальные baseline-схемы оставлены для аудита; `door_semantics.manufacture_split` в общем пакете имеет приоритет для этих физических границ.

В640 записях дверей из80 файлов карт старшее слово равно0. Это наблюдение корпуса, а не основание выкинуть поле.

## HealthGain: знаковое слово и точный таймер

| Файл | Нативное чтение | GUI Editor Pro |
|---|---|---|
| +0x22C Health | unsigned16 → runtime+0x91 | Health,0..32767 |
| +0x21C HealthGain | signed16 → runtime+0x93 | Health Gain,0..32767 |
| +0x238 ManaCost | слово → runtime+0x9B | Mana Cost, signed16,-32767..32767 |

В tick0x4A55F0 восстановление проходит, когда дверь не мертва по проверке vtable+0x28, **текущий unsigned tick строго больше** instance+0x11A и signed HealthGain ненулевой. Из unsigned максимума Health вычитается текущее DWORD-здоровье с32-битным переполнением; результат сравнивается как signed32 с signed16 HealthGain. Меньшее значение затем сужается до signed16 и передаётся helper0x4B2CE0, если ненулевое. Для двери этот helper прибавляет дельту к здоровью; отрицательное значение уменьшает его.

Поэтому `FFFF` означает−1, `8000` означает−32768. Ввод таких значений через hex не увеличивает лечение. Нативный GUI ограничивает HealthGain положительной половиной диапазона.

Следующий срок считается как **предыдущий срок + TPS**, а не текущий tick+TPS. Даже при дельте0 срок сдвигается, если HealthGain ненулевой и временной gate пройден. Внутри вызова нет цикла догоняющих начислений. При равенстве текущего tick сроку начисления нет. API требует явно передать TPS, текущий tick и срок; значение TPS не угадывается из файла.

## Флаги и неизвестные участки

Native decode0x41F510/encode0x41F4E0 восстанавливают только маску **0xE0**: Secret0x20, Barricade0x40, Good0x80. Полный проход родного редактора через эти функции теряет остальные биты. Собственный сериализатор должен сохранять неизвестные биты, меняя только явно выбранную маску. В проверенном корпусе таких теряемых битов нет.

Участки+0x21E:2байта,+0x220:4байта,+0x230:2байта не переносятся в промежуточную структуру исследованными raw-конвертерами игры и Editor Pro. Это ограниченное наблюдение, не доказательство отсутствия любых обращений в остальных частях программы.

В640 записях карт эти8 байт нулевые. В отдельном `Data/editor/Doors.kwd` у всех8 дверей стоят соответственно `63 00`, `16 00 00 00`, `C0 FA`. Это **не доказательство их смысла**. Они сохраняются целиком; автоматическое обнуление или присвоение названий не вводится.

## Magic Door использует данные Traps, но собственную ветку выстрела

Door.TrapTypeId+0x227 → intermediate+0x29B → runtime+0xB0. Tick берёт соответствующую ловушку через world vtable+0x160. В standalone Magic Door это TrapId12; в корпусе карт559 дверей имеют0,80 имеют12 и одна имеет15. Все ненулевые ссылки найдены среди Traps того же контейнера; разрешение внешних каталогов этим тестом не моделируется.

После проверки времени и выбора подходящей цели дверь должна быть закрыта. Далее проверяется Trap.ManaCostToFire+0x1D4/runtime+0x9A: helper0x4C1740 принимает0 либо signed cost<=signed player mana.

В разрешённой по мане ветке:

1. Начальный XYZ снаряда равен позиции двери, Z увеличивается на0x800 — половину клетки. **Три Trap.ShotOffset не применяются в этой ветке**.
2. Тип снаряда берётся из Trap.ShotTypeId+0x20D/runtime+0xBB, factory0x4B7CD0 вызывается напрямую.
3. Только при успехе factory в shot+0x145 пишется low16 тега двери, в+0x147 — low16 тега цели. Helper0x4AB830 задаёт target XYZ; если у типа снаряда включён флаг0x20, отдельный helper0x4AB8A0 перед этим получает координаты цели с половиной её высоты.
4. Trap.ShotData1+0x1E0 и ShotData2+0x1E4 копируются в shot+0x13D/+0x141. Специальной подмены Data2 для TrapId16 из обычного trap-caller здесь нет.
5. Код переходит к списанию маны и учёту расхода, затем записывает instance+0x105 = текущий tick + Trap.RechargeTime в runtime ticks.

**При отказе factory выполняется шаг5.** Переход0x4A6378 идёт прямо на0x4A6431; создание не требуется для списания и перезарядки. При недостатке маны возможен ManaCostToFireEffectId в точке двери, после чего эта ветка заканчивается без обновления срока.

Здесь нет вызова trap-creator0x4A80E0 и его gate ChargeTime, reset/reveal/threat присваиваний. Это утверждение о выбранной ветке0x4A6328..0x4A6469, а не симуляция всей двери или утверждение об отсутствии любых других механизмов.
