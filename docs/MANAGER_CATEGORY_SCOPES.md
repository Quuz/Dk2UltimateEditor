# Смена категории объекта и сценарные точки

16 октября 2026, ManagerCategoryScopes-20261016. Результаты именно текущей DLL
перечислены в [CURRENT_STATUS](CURRENT_STATUS.md). Все23 области и семь очередей
остаются в [REMAINING_WORK](REMAINING_WORK.md).

## Поведение исходного менеджера

Things_ManagerModify сначала копирует всю MAPTHING в рабочий шаблон. Изменение
типа меняет node.type/id, но не uniqueid. После принятия исходник копирует
MAPTHING обратно; многократное изменение добавляет записи в соответствующие
новой категории списки. При этом он не меняет TRIGGERLINK.node.type, его
операнды, event IDs или события. Это подтверждено полным проходом этой функции,
включая single Things_Select и pass10; Source/ не изменён.

Редакторский менеджер теперь следует этому правилу:

| Переход | UID объекта | Старая точка |
| --- | --- | --- |
| дверь → ловушка | сохранён | остаётся door-scope64 без владельца |
| ordinary object → special item | сохранён | остаётся object-scope128 без владельца |
| special item → ordinary object | сохранён | остаётся magic-scope256 без владельца |
| creature keeper/hero/neutral | сохранён | creature-scope2 остаётся у того же существа |

При возврате того же объекта в прежнюю категорию его прежняя точка снова
находит владельца по UID и scope. В native raw root восстанавливается только
при явном изменении категории данного объекта, если имеется ровно одна
подходящая orphan точка и один живой носитель UID. Изменение соседнего объекта,
пересчёт смещений или простое чтение документа не дают права автоматически
присоединять точки или исправлять неоднозначные импортированные данные.

Пустые точки ведут себя так же, как непустые. Новая категория не получает
другую копию старой точки и не требует подтвердить её удаление. После обратного
перехода сохраняется исходная точка, а не созданный заново граф. Если старая
точка удалена отдельной командой Delete Point, возвращаться уже нечему.
UID физического объекта при этом может оставаться назначенным: удалённая
точка без владельца не должна очищать ID другого физического носителя.

Общие вопросы об использовании в сценариях сохраняют [исходные правила](SHARED_SCENARIO_REQUESTS.md).
Менеджер проверяет creature operand, поэтому door/object point не создаёт
выдуманного дополнительного вопроса. В дочернем редакторе исходного менеджера
скрыт generic флажок detachment; вместо него есть объяснение EN/RU о сохранении
старой точки/ID. Принятый исходный запрос передаётся в план и проверяется
на актуальность перед изменением карты.

## История и данные

Одно принятое изменение менеджера остаётся одним Undo родителя. Source
MapChanges считает обработанные записи и отдельные удаления заменяемых
объектов по прежним правилам. Single редактирует свою позицию; multi записывает
источники в выбранном порядке. Undo восстанавливает полные прежние байты,
порядок, ID, category, точки и производную цель кристалла — по согласованному
пользователем поведению. Events section DKM остаётся буквально неизменной,
native event buffers тоже; raw pointer меняется только из-за действительной
смены поддерживаемого owner scope.

Универсальные ApplyObjectBatchModification и PlanObjectBatchModification
сохраняют отдельный существующий контракт: миграцию совместимой привязки или
явное разрешение detachment с сохранением событий. Эта правка касается
ApplyEditorObjectBatchModification и PlanEditorObjectBatchModification;
generic guards не ослаблены глобально. Прямое редактирование raw bObjectID в
инспекторе также не объявляется эквивалентом команды менеджера.

## Native рабочий формат D2OS

В GAME* файлах нет uniqueid вещи. Рабочая [таблица владельцев](NATIVE_OWNER_SCOPES.md)
связывает его с физическим адресом, а orphan строка сохраняет прежний scope,
root и UID. При переходе категории образуется живая строка новой категории
без точки и orphan строка прежней точки с тем же UID. Это не две физические
копии объекта. Next-free allocator продолжает резервировать все ID, включая
orphan, чтобы новая вещь не получила чужой сценарий.

Ловушка не имеет сценарного owner scope, но должна сохранить назначенный ID
бывшей двери. Для неё введена D2OS версия2, сохраняющая прежние header16/row36
и offsets. Дополнительная допустимая строка:

| Поле | Требование |
| --- | --- |
| File / Ordinal | действительный живой адрес GAMETRAP |
| Member | -1 |
| Scope | 0, только identity-only |
| ID | сохранённый uniqueid MAPTHING |
| Band / Root / Present | 0 / 0 / false |
| Reserved WORD/DWORD | 0 / 0 |

Scope0 не создаёт root в ScriptGraph и не предлагает ловушку как владельца
новой точки. Его UID переносится в DKM MAPTHING и обратно через compiler.
Version1 по-прежнему читается. Writer используетv2, когда нужны identity-only
строки; без них записывает прежнююv1. Versions вне1/2, identity-only строка
с Present/root/band, orphan address или reserved payload отвергаются.

Существующая native таблица без такой строки остаётся v1 и не меняет базовые
игровые байты. Неизвестные или укороченные игровые layouts не объявляются
поддержанными этим расширением. Внешние game files не получают D2OS companion.

## DKM и игра

Сохраняйте рабочий DKM вместе с native-source ZIP. DKM хранит прежние точки
и UID; compiler переносит их в рабочую таблицу native документа. Круг
native→DKM→native поддерживает ID ловушки и пустую/orphan точку; повторный
переход восстанавливает связь без переписывания событий.

Игровой экспорт содержит ровно семь официальных файлов. Игровой KWD не хранит
UID ловушек и orphan/empty редакторские точки: повторное открытие только
игрового комплекта не заменяет рабочий DKM. Перенос несоответствующей категории
точки в работоспособный сценарий игры требует содержательно вернуть владельца
или явно изменить сценарий; сама сохранность байтов не подтверждает геймплей.
Установленные карты и прежний TestMap не изменяются. Любая реальная game
приёмка — DK2Preview_6a88240eaf814f78 через DKII-DX.exe -q -level.

## Время жизни флажков подтверждения

В исходнике `Config_SetToDefault` обнуляет весь Config при создании главного
окна. `RequestsFlags` затем используется через указатель `requestbits`;
Registry сохраняет только Recent, SafeFlag и GamePath. Сохранения этих
флажков между запусками в предоставленном Source нет. Наши реализованные
общие bits2/16/256 остаются в ObjectManagerSession, вне карты, Undo и
AppSettings. Новый запуск начинает с нуля: добавлять persistence ради
соответствия исходнику не требуется. Остальные Config настройки и request
callers остаются в очереди сверки. Хеши файлов, все References/Registry
calls и граница вывода записаны в evidence `config-request-lifetime.json`.
