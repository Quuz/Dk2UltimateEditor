# Object batch insertion — placement/planning stage

This document records the historical read-only planning milestone. The later [full-template and atomic insertion stage](OBJECT_BATCH_INSERTION.md) adds the actual EN/RU command and application transaction. `ObjectBatchPlacement.cs` itself still only builds read-only previews and validates candidate selections; it never modifies a map or creates Undo entries.

## Source-derived behavior

The reference is `Things_Functions.c::Things_CanPaintEx`, `Things_Manager.c::Things_ManagerAdd` passes 1–6, `Manager.h`, `Compiler_Conversions.c::Compiler_GameMapToEditorMap`, `Map_Setup.c::Map_CreateLimitWall` and `Map_Functions.c::Map_GetRealIDFromMap`.

- All five source families are separate: creatures, doors, traps, ordinary objects and special items. Native hero/neutral/keeper signatures are classified as creatures; C2 IDs 0x75–0x81 are special items, as in `Game_ExtractThings`. Project Things versions 1–6 retain their explicit family.
- One, rectangle and random-rectangle modes retain row-major order. Whole-map insertion includes the source's final row/column, then locks those candidates. Explicit selection bounds remain a rectangle, not an implicitly narrowed interior. Random frequency is 2–32; default is 2; rejected candidates disappear before validation, not after it. Empty sampling requires no preview. The later insertion stage repairs the historical frequency-slider save defect.
- Owner zero derives the **editor-projected** tile owner, not the raw native owner. The original loader first corrects invalid owners/options, resolves World → Rooms → Gates → Walls, forces fixed catalogue owners outside room terrain and falls back to neutral earth for unknown tiles. Its outer-edge FE/neutral projection is recreated without overwriting a single source tile. Explicit interior FE is also locked. Reserved bytes never become catalogue discriminators.
- Solid terrain rejects all things. Doors/traps additionally reject the source room/bridge list, water/lava and mana vaults, plus another owner's terrain. Portals/hearts have their original restrictions; ordinary crystal ID 28 is the exception on heart and hero-gate types 1/4. Ordinary hero-box ID 130 can use enemy terrain; neutral ordinary/special objects have their own exemption, not one inherited by doors/traps.
- Creature water/lava checks precede territory checks and use actual edited global definition flags where verified. Missing definitions use the preserved source reset defaults; unsupported definitions are **unknown**, not false/default. Source unknown creature IDs are safe on water and fatal on lava. Unclaimed earth, closed mana vault and enemy prison retain their creature exceptions.
- Overlap resolution takes the first door before the first trap, or first ordinary object before the first special item, independent of native mixed-file order. `Misc_Lists.c::List_AddEntry` appends, so within-family source file order is retained. Creatures do not use these replacement pairs. “Same family” means the exact family, not the pair.
- Warning overrides run before replacement policy, as in the source. All/same-ID/same-family can therefore enable a replacement despite a terrain/enemy/fatal warning; that warning still calls for preview. None/ask disable the default candidate; ask requires preview and permits an explicit decision. Outer-edge/out-of-map locks cannot be overridden.

The original preview has keep/delete/add toggles. For **addition**, pass 7 only executes candidates whose `modify` flag is set; setting `remove` alone does not delete an existing map object. The modern planning stage models add/skip decisions only. It does not invent a destructive “delete existing object” interpretation for that original no-add choice. Bulk removal remains its own real manager operation.

## Guards and remaining work

Plans capture a whole-document fingerprint, including definitions, tiles, objects, metadata and scripts. Another document, changed bytes, duplicate/out-of-range selection indices and explicit attempts to enable a locked candidate fail. Byte-exact Undo restoration can make a plan equivalent again. Selected candidates stay in plan/source order; resolution does not resample.

Deliberate additional safety: negative/out-of-range positions do not dereference C pointers; unknown/partial record layouts and required unverified creature flags are shown as incompatible and locked. The source's unsafe pointer reads and an unknown-layout guessed default are not reproduced. Lossless loading remains available; this does not establish editing support for 5537-byte creature definitions. Unknown IDs/data already preserved by the modern loader are not dropped merely because the historical `Game_AddThing` discarded unknown names.

At this planning milestone full templates, actual application, scopes, capacity checks and EN/RU controls were still missing. Their later implementation and separate acceptance are recorded in [the insertion stage](OBJECT_BATCH_INSERTION.md). A passing planner alone is not proof of those requirements.

Next template evidence: `Editor.c` initializes five independent manager templates. Creature: ID 1, automatic owner, health 100, held gold 0, level 1, hero options 0, creature options 9, objective 0x13, area/unique ID/enemy 0. Door: ID 6, automatic owner, data/status 0. Trap: ID 4, automatic owner, shots 4. Ordinary object: ID 1, neutral owner, data 0. Special item: ID 0x75, neutral owner, data 0. All non-creature health/gold/options/objective/area/unique ID/enemy fields are zero. These differ from the generic current single-record defaults and must not be silently replaced by them. `Things.h::MAPTHING` defines every template member; the existing verified project-to-native compiler supplies owner-dependent creature record and property mappings.

`Compiler_GenerateCreatures` further confirms that owner 1 creates C7/40-byte heroes, owner 2 C6/32-byte neutrals and other owners C8/36-byte keepers. For heroes `bGlobalPlayer` is the **enemy/target**, not the owner; standalone hero band ID is 255. Held gold, level, behavior and type ID use explicit byte casts; health is full-width; hero-only area/objective/options have their own mappings. `Compiler_GenerateObjects` writes gold for IDs 1–3, spell for ID 4 and zero inactive payload fields otherwise; special items have neither gold nor spell payload. Doors carry locked status and a door script root; traps carry shots and no root. A batch serializer must use these verified family/owner semantics, never blindly clone one native creature signature across automatically derived owners or copy an old entity's unique identity/root. Existing project scope helpers distinguish creature/door/object/special ownership; replacement script cleanup needs its own explicit acceptance.
