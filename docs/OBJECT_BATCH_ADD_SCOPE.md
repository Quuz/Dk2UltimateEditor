# Original object-manager batch insertion: source scope

The initial gap below is now addressed by [full templates and atomic batch insertion](OBJECT_BATCH_INSERTION.md), which documents current implementation, tests and deliberate differences. This source audit remains the requirement reference; bulk modification/removal/sorting still need their own acceptance.

The real `Things_Manager.c::Things_ManagerAdd` is not the general-search stub. It handles three manager families: creatures, doors/traps and ordinary/special objects. `Source/Includes/Manager.h` defines three insertion modes: one object, rectangle and random rectangle. The current modern named-record command adds one item at the canvas cursor; repeating that command or editing raw coordinates is not evidence of this original bulk workflow.

The read-only [placement/planning stage](OBJECT_BATCH_PLACEMENT.md) covers source terrain rules, candidate modes/order/owners, overlap priorities, replacement decisions and stale/locked guards in Core. The later insertion stage supplies full template serialization, atomic application and EN/RU WPF integration; the planning-stage tests alone do not establish that workflow.

The source builds a temporary candidate per bounding cell, copies the active family template, samples random insertion in row-major order and removes rejected candidates before validation. `Manager->onmap` uses a whole-map range; otherwise it uses the current selection. The source whole-map range starts at (1,1) with width/height equal to map dimension minus one, so it also generates candidates on the last row/column and subsequently locks them through validation. A modern source-equivalent plan must not silently substitute a smaller region without documenting and verifying that choice.

An owner-zero template derives its owner from the candidate tile. Each candidate is checked through `Things_CanPaintEx`, including terrain, enemy, fatal, boundary and overlap warnings. Doors/traps overlap as one pair of families; objects/special objects as another. Creature insertion does not use those same replacement controls. The five replacement policies are all, same exact type/ID, same family, none and ask. Warning override flags, preview/confirmation and per-candidate modify/locked state control application. Boundary/out-of-map candidates cannot be enabled by those overrides.

The final pass removes an approved replacement, inserts the new template and records child undo entries under one root operation. Empty application restores/removes the unused root. Copying source structs into the new formats must additionally preserve modern unique identities, graph ownership and lossless unrelated bytes; direct C pointer/list copying is not an acceptable native/project serializer.

`Things_ManagerAddInit` exposes random frequency 2–32 through the dialog slider; editor configuration initializes it to 2. Unlike terrain random painting's fixed-source setting, this is a real separate object-manager frequency UI. However, in this revision `Things_ManagerAddSave` copies mode, warning flags and replacement policy but never reads/saves the slider frequency. Its HSCROLL handler only updates the displayed number. This is an initialization/save defect to document and deliberately repair, not a reason to omit the intended control or claim the old setting worked.

Remaining implementation and acceptance include all five object categories and their template properties, one/whole-map/selection/random modes, source candidate order/probability, automatic owner, terrain/enemy/fatal/boundary rules, all replacement policies and per-candidate previews, single atomic application with exact undo/redo/no-op/failure rollback, stale/foreign document/template guards, identity/script integrity, saved/compiled native/project files, EN/RU controls and cancellation/source immutability. General bulk modification/removal and manager sorting have separate real source routines and also need complete audits; implementing only batch addition will not establish whole-manager parity.
