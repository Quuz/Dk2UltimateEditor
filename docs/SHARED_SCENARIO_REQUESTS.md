# Общие запросы об использовании в сценариях

16 октября 2026, SharedScenarioRequests-20261016. Текущее исполненное состояние
и границы проверок — в [CURRENT_STATUS](CURRENT_STATUS.md). Это этап общей
задачи; все23 области и очереди A–G остаются в [REMAINING_WORK](REMAINING_WORK.md).

## Команды менеджера

В менеджере объектов Preview фиксирует выбранные строки в порядке отображения.
Remove открывает исходный общий запрос Yes/No. Если выбранные существа
используются в сценариях, после Yes появляется второй запрос Yes/No/Cancel.
Старые флажки «включать сценарные объекты» и «подтверждаю удаление» в этом
маршруте заменены этими запросами; отдельная копия разрешения в окне не хранится.

- Yes второго запроса удаляет все выбранные элементы, сохраняя сценарные точки
  и события по [правилам владельцев](NATIVE_OWNER_SCOPES.md).
- No сохраняет **каждый выбранный элемент с назначенным уникальным ID**,
  включая элемент без своей точки. Удаляются только элементы с ID0.
- Cancel или закрытие вопроса не меняет карту и не запоминает ответ.

Это буквальная фильтрация Things_ManagerKill: после обнаружения первого
используемого creature-операнда цикл проверяет uniqueid, а не наличие точки
у каждой последующей строки. Если совпадений не найдено, дополнительного
вопроса нет и общий Yes включает все строки. Door/object point сам по себе
не заменяет source creature-предикат.

Modify задаёт вопрос об использовании **до открытия редактора значений**.
Yes включает все строки, No исключает все строки с назначенным ID, Cancel
прерывает команду. Если после No список пуст, дочерний редактор не открывается,
карта и Undo не меняются. При оставшейся одной строке исходный режим multi
сохраняется, если первоначально выбрано несколько: маски, общий шаблон,
подтип и порядок записи не переключаются в режим свойств одного объекта.
Скрытый IncludeScripted дочернего редактора не служит отдельным разрешением;
план строится по принятому и ещё актуальному исходному запросу.

No удаления с полностью пропущенным набором всё равно оставляет исходный
родительский шаг Undo, уведомление и современную операцию. Source MapChanges
при этом получает0, по числу реально удалённых элементов. Для непустого
удаления/изменения счётчик увеличивается на число обработанных элементов;
заменённые записи учитываются прежними отдельными правилами. Полный Undo
предметов с прежним порядком и целью кристалла выбран пользователем и сохранён.

## Общие флаги и срок действия

EditorRequestPreferences хранится в ObjectManagerSession рабочего окна и
передаётся также EditorRegionRemovalPolicy. Это runtime preference вне карты,
DKM, игровых файлов и Undo. Одновременно активен один подтверждающий запрос;
соседний policy не может заменить его или сбросить его настройки.

| Бит | Исходный запрос | Использование |
| --- | --- | --- |
| 0x2 | REQUEST_MNGRKILL | общий запрос удаления в менеджере |
| 0x10 | REQUEST_RECTEXKILL | общий запрос областей, ворот, эффектов |
| 0x100 | REQUEST_TRIGGERS | used-area и used-creature remove/modify |

Запомнить можно default Yes. С установленным флажком No/Cancel отключены;
закрытие окна не превращается в Yes. Запоминание происходит до команды,
поэтому не отменяется Undo и сохраняется даже после отказа записи/переполнения.
Отказ до ответа не меняет preference. Успешный commit с ошибкой последующего
observer не выдаётся за отменённую команду.

Yes, запомненное для сценарной области, подавляет такой же запрос существ
при удалении **и изменении**. Обратное также верно. Общие удаления0x2 и0x10
остаются независимыми. «Спрашивать перед удалением объектов» сбрасывает
0x2/0x100; кнопка регионов —0x10/0x100. Посторонние биты сохраняются.
Новый документ того же workspace использует тот же runtime store. Перенос
всего жизненного цикла исходной Config и его сохранения между перезапусками
не заявлен этим этапом.

Первый запрос следует за мышью с ограничением рабочей областью монитора;
вопрос использования центрируется относительно владельца. Используется
тот же встроенный исходный question icon. EN/RU обновляются ресурсами,
выбор строк и документ не меняются при переводе. Физическая работа окон,
focus, Enter/Escape, close, системный звук и hardware/DPI ещё требуют ручной
приёмки: окна, renderer и игра инструментами не запускались.

## Проверка данных и authority

Source Triggers_GetFirstTrigger ищет creature operand во всех TRIGGERLINK,
не проверяя node.type. ID0 не является используемым; пустая явно созданная
точка считается используемой. DKM следует этому предикату буквально.
Для native известные creature/member точки берутся из рабочей таблицы UID,
включая orphan и empty rows. Неизвестные layouts не дают права на удаление.

Begin фиксирует канонические поля и неизменяемый порядок, EditRevision и SHA
всего рабочего состояния до/после чтения входного списка. Изменяющий карту
enumerator не получает запрос на уже подменённых владельцев. Чужие, дублированные,
устаревшие записи, live pen и вложенная транзакция отвергаются до ответа.
Проверки повторяются перед применением; UI сверяет также текущую selection,
документ и срок действия родителя. Старый редактор значений закрывается перед
новым запросом. Закрытый родитель или новая selection после ответа не создают
нового действующего дочернего редактора.

Generic ApplyObjectRemoval / PlanObjectBatchModification сохраняют прежние
контракты; source менеджер использует явные EditorThingRequest и
PlanEditorObjectBatchModification. Сам вопрос Modify ничего не записывает.
Операция над значениями сохраняет свои проверки ссылок, layouts и detachment.
Её последующая ошибка не выдаётся за уже завершённое удаление.

## Вспомогательный band operand участника

Source Files_Game.c при импорте передаёт в point поле видимого Heros->id.
Triggers_ActionPoints.c при Finish считает физический номер отряда в списке.
Эти значения различаются, например при band ID42 и позиции1.

D2OS/v1 теперь сохраняет `TRIGGERLINK.band` живого участника как отдельное
буквальное значение. Синхронизация raw GAMEBAND, переименование его ID,
компиляция и повторная DKM конверсия не подменяют его видимым ID. Удаление
другого отряда тоже не переписывает старое значение само по себе. Явный Save
сценарной точки устанавливает её текущий физический номер, в том числе при
Modify на том же владельце. Это metadata-only изменение имеет собственный Undo.
Привязка к участнику разрешается по уникальному ID и физическому слоту.

Обычный игровой KWD не хранит это редакторское поле. Повторный импорт только
семи игровых файлов снова выводит operand из native parent ID, как исходник.
Для сохранения рабочего значения нужны DKM и его native-source ZIP. Проверены
пустая/непустая точки, два compiler прохода, реальный Save/reopen, ID77 против
ordinal1/0, перестановка участника и полный game+metadata Undo/Redo.
