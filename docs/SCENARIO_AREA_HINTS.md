# Площадь зоны и контекст владельца сценария

Основной код,13 октября2026. Описание относится к
`artifacts/Evidence/ScenarioAreaHints-20261013`; физические окна не запускались.

На трёх страницах условий восстановлена информация оригинала:

| Страница | Информация |
| --- | --- |
| `TRIGGER_CLAIMAREA` |Площадь и число клеток периметра|
| `TRIGGER_AREACONTENT` |Площадь|
| `TRIGGER_SELECTAREA` |Площадь|

Источник — `Triggers_TriggerDlgParamsInit`: он получает AREA через
`Context->TriggerCtx.ParentPoint->area`, вызывает `Map_CorrectRect`, затем
заполняет static101/102. Это родитель зоны сценария, а не operand условия.
`Map_CorrectRect` нормализует обратные координаты и включает оба конца:
ширина=`abs(x2-x1)+1`, высота=`abs(y2-y1)+1`. Ограничения по размерам карты
в этой функции нет. Площадь — произведение ширины и высоты.

Исходный периметр:

```
width > 1 ? (width - 2) * 2 + height * 2 : 1
```

Поэтому у зоны1×4 оригинал показывает площадь4 и периметр1. Это правило
сохранено, включая32-битную LONG арифметику. Для непроверенной геометрии или
неоднозначных identities информация недоступна; данные не исправляются.

## Как выбирается правильная зона

`ScenarioAreaContexts` собирает физические AREA-владельцы, чьи действующие
root-связи достигают выбранного события. Если владелец один, он выбирается
однозначно. Если общая ветка принадлежит нескольким зонам, окно использует
контекст выбранного в дереве экземпляра. Без такого выбора оно предлагает
явно выбрать зону для информации, а не берёт первый root.

Каждый узел дерева теперь несёт свой корневой контекст через вложенные AND
и sibling/next узлы. Восстановление выбора после refresh учитывает этот root
и исходную project scope identity. Finish мастера также сохраняет исходный
корневой контекст выбора. Это изменения App selection; физическая проверка
раскрытия дерева и сохранения выбора остаётся отдельной приёмкой.

Выбор зоны в информационном списке не перепривязывает событие и не меняет
параметры, bytes, Undo или счётчики. При неизвестном/непривязанном событии
показывается недоступность информации. Проверка самого сценария и управление
его настоящими связями остаются прежними командами дерева.

## Приватный мастер

При вставке нового события root ещё не записан в приватном документе.
`ScenarioCreationAreaContexts` проверяет живую session и исходную связь
вставки, находит AREA-владельцев в исходном графе, затем переводит записи
через `session.Files` в приватную копию. В editing wizard сохранены все
реальные владельцы общей ветки. Вариант содержит исходного владельца для
устойчивого выбора и приватного владельца для чтения геометрии.

Back/Next сохраняет выбранный информационный контекст, в том числе явное
отсутствие выбора; смена EN/RU его также сохраняет. После внешнего изменения
документа информация очищается и доступность выключается. Перевод старого
окна не обращается к инвалидированному контексту. Cancel не добавляет запись
или binding. Только обычный Finish применяет ранее существующий план сценария.

## Что проверено

Source capture хранит два хеша и исходные три Init case/Map_CorrectRect.
Модель проверяет3 страницы ×5 независимых размеров ×2 формата:30 случаев,
включая одиночную клетку/строку/колонку. Отдельно — обратные координаты,
две общие AREA, отсутствие произвольно выбранной зоны у unlinked события,
private insertion/editing correspondence и foreign/stale/nested guards.
Чтение сравнивается с полными буферами, ревизией, Undo и editor counter.

В project fixture создание scope-записей передвигает коллекцию событий.
Первоначальный focus обнаружил устаревший offset теста; fixture теперь
разрешает событие заново по сохранённому ID. Guard текущего record не ослаблен.
Результаты текущих checks/build/publish находятся в CURRENT_STATUS.

WPF smoke подготовлен для EN/RU ×native/project: два разных родителя с общей
вложенной веткой, выбранная вторая AREA, смена информационного контекста,
Back/Next, перевод, Cancel и внешний edit/перевод stale окна. Он только
компилируется, не исполнялся. Source/Core доказательства не заменяют эти
физические проверки и не закрывают все ворота FEATURE_PARITY.

## Ручная последовательность

1. На копии карты задайте две зоны разной площади, например1×4 и2×3.
   Откройте условие захвата зоны через её сценарий: первая должна показывать
   площадь4/периметр1, вторая — площадь6/периметр6.
2. Для общей ветки выберите её экземпляр под второй зоной, затем откройте
   изменение через мастер. Информация должна относиться ко второй зоне.
   Если открыть событие без выбранного экземпляра, явно выберите контекст.
3. Выберите первую зону для информации. Пройдите Back/Next, переключите EN/RU:
   выбор и цифры сохраняются. Cancel не меняет карту или историю.
4. На страницах содержимого/выделения зоны проверьте площадь без периметра.
   При внешнем изменении карты старое окно должно требовать повторного открытия;
   смена языка в нём не должна приводить к вылету.

Все игровые проверки используют только `DK2Preview_6a88240eaf814f78`, ровно
семь экспортированных файлов и
`DKII-DX.exe -q -level DK2Preview_6a88240eaf814f78`.
