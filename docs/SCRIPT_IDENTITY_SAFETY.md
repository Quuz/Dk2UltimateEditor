# Изменение сценарных ID без неоднозначного переноса ссылок

15 октября 2026. Ручное изменение ID через существующие свойства записи
обновляет связи только при однозначном старом ID. Установленные карты
автоматически не исправляются; загрузка и обычное сохранение сохраняют
импортированные ID и данные.

## Правила

| Состояние старой записи | Изменение ID |
| --- | --- |
| Единственная запись с ненулевым ID | Обновляются все действительные входящие связи и project backlinks |
| Несколько записей с тем же ID и есть ссылки | Отказ: нельзя угадать, к какой записи относились ссылки |
| Несколько записей с тем же ID, ссылок нет | Можно исправить выбранную запись на свободный ID |
| Старый ID 0 | Меняется только выбранная запись; ссылки со значением 0 остаются пустыми |
| ID введён без изменения | Импортированные данные сохраняются, даже если ID некорректен |

Новый ID должен быть ненулевым и свободным во всём пространстве событий.
В историческом проекте условия используют 1–32767, действия — 32768–65535
как битовое представление отрицательного signed short. Нативный формат
использует весь ненулевой WORD. Исходные Triggers_GetTriggerFreeId и
Triggers_GetActionFreeId начинают распределение соответственно с 1 и −1.
Это не обещание повторять небезопасное переполнение исходного allocator.

До исправления native и project имели отдельные процедуры. Native обходил
словарь ScriptGraph.Events, в котором повторные ID оставляют только первую
физическую запись. Это могло пропустить её соседей при перенумерации другой,
однозначной записи. Обе старые процедуры также могли перенести все входящие
ссылки от неоднозначного старого ID к одной выбранной записи.

Текущий RemapScriptIdentity проверяет новое значение, все физические события,
все настоящие связи и project previd до записи. Неоднозначность отклоняется
атомарно. Native ACTION.ChildAnd является сохранённым резервным payload и
не переписывается. Обычные числовые параметры не становятся ссылками только
из-за совпадающего значения. Идентичность других событий сохраняется.

## Проверки и границы

Модели native/project × condition/action проверяют нулевые и повторные ID,
пустые связи, hidden backlinks, исправление неверной signed категории,
коллизии нового ID, все физические связи при посторонних дубликатах,
native резервные байты, полные данные и атомарные счётчики/Undo/Redo.
Прежние проверки диагностики импортированного неверного ID сохранены через
буквальный повреждённый fixture, а не создание некорректного ID публичным API.

Первый новый fixture ошибочно поместил previd по смещению 8. Он исправлен
на исходное смещение 12: Win32 NODE содержит два указателя и DWORD. Неудачный
журнал focus-node-fixture-failure сохранён; проверка продукта не ослаблялась.
Сценарий WPF перенумерации общего родителя использует допустимый ID своей
категории. WPF/редактор/игра не запускались; изменение уже существующих
свойств ID и его визуальная обработка требуют ручной приёмки.

## Ручные шаги

1. В свойствах выбранной событийной записи измените нулевой ID на свободный
   ненулевой ID. Проверьте, что пустые связи сохранили 0; Undo возвращает ID.
2. Для project действия используйте 32768–65535, для условия — 1–32767.
   Неверная новая категория должна отклоняться без изменений.
3. При однозначном ID проверьте сохранение всех входящих связей после изменения
   и Undo. При дубликате со ссылками должен быть отказ. Сначала явно разберите
   и отсоедините неоднозначные связи; редактор не выбирает их владельца сам.
4. Сохраните отдельную копию и откройте её снова. Установленные исходные карты
   остаются прежними. Для игры используйте только DK2Preview_6a88240eaf814f78.
