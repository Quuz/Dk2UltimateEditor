# Main-map physical object display

## Source scope, not invented sprites

`Source/Sources/Windows/Windows_MainWindowProc.c` draws doors, traps, special items, ordinary objects and finally creatures in its main `WM_PAINT` path. `Source/Sources/Things/Things_Display.c` implements these as geometric marks and creature counts, **not item bitmap sprites**. Catalogue pictures in the chooser/manager are a different workflow. Earlier ledger references to missing main-map object sprites were imprecise; this stage restores the actual source display semantics instead.

- Doors prefer horizontal left/right solid neighbours, otherwise require both vertical neighbours. Invalid positions use a small square; door IDs 6/7 use the barrier square. Status 2 gives two outlines. Only a valid non-barrier status-1 door receives a lock X: source jumps for barriers/invalid positions bypass that code.
- Traps use an owner-coloured circle, a diagonal half-ellipse for zero shots, or a smaller circle for solid/mismatched-owner positions. Older project Things versions 1–4 use the source read default of four shots rather than interpreting inactive stored union bytes.
- Ordinary objects occupy the upper-right corner, normally source COLORREF `0x005555FF`, optionally the owner's colour. Special items occupy the lower-left corner, normally `0x00FFFF00`, with a grey plus. Solid-tile positions are black; browsing does not repair them.
- Creatures aggregate by cell and owners 1–7. Detailed view draws owner-coloured counts in source owner order; simple view draws the total on white. On a solid tile the display is white `!!!` on red. Owner 0 is not silently counted as a real player. The source routine's misleading local `NeutralCount`/`HerosCount` names do not swap actual owner IDs or the `Players[]` colours.

`Things_IsSolid` supplies the seven editor terrain IDs 1/2/6/7/9/30/254. Colours come from `Datas_Thumbnails.c` `Players[]` and `Thumbnails.h`, not the modern approximate owner strip palette. Geometry preserves the source float-percentage/integer-truncation rules. The managed viewport supports its existing 2–48 cell-size range; this stage does not change the zoom range or claim pixel-identical GDI text/ellipse/outline rasterization. WPF text uses the system message font and DPI.

## State and editing safety

`MapObjectDisplay` is an immutable read-only physical snapshot. Native and project records share the existing physical type/owner/data projection. Nested band members and region identities are not treated as placed creatures; malformed out-of-map positions are skipped without edits. Missing border neighbours are treated as solid instead of reproducing source out-of-bounds reads. Invalid owner colours use a safe neutral fallback without changing bytes.

`MapCanvas` rebuilds the snapshot on document assignment and actual changes/Undo/Redo, not on every paint or mouse move. It draws the five source layers, then the existing region overlays. Selection, placement and patrol overlays remain separate. Closing/replacing a document clears the snapshot. The existing entity master switch hides the physical layers too.

An EN/RU Object display menu exposes five category flags, detailed counts and the two source owner-colour flags. Numeric bits match `Config.h`; defaults match the physical-object subset of `Properties_Editor_Config.c`. Choices survive language and map changes and round-trip via `AppSettings.MapObjects`. Old settings with no field use source defaults; unrecognised bits are retained rather than reinterpreted. No map mutation, transaction, script plan, confirmation or selection is created by view commands. The remaining terrain/regions/cameras/gate-detail source flags and whole-editor view preferences are **not** claimed by this eight-option subset.
