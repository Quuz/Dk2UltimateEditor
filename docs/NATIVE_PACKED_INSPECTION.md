# Инспекция packed-определений и хвосты коллекций

Последующий этап [HistoricalSectionInspection](HISTORICAL_SECTION_INSPECTION.md) согласовал DKM/AREA preview с parser и добавил explicit opaque whole-native-file policy. Текущий остаток I04 перечислен в [20-row matrix](I04_FORMAT_MATRIX.md), F01.

Состояние на 25 октября 2026, `NativePackedInspection-20261025`.

Инспектор KWD теперь использует тот же статический разбор определений, что и
загрузчик. Проверяются соседние frames, внутренние заголовки известных семейств,
count/stride/payload и границы. Рабочий документ, таймер статистики и другие
ссылочные файлы при этом не создаются. Ограничение размера companion-файла
проверяется до чтения его целиком.

Нарушения, которые загрузчик отклоняет, теперь дают ошибку и в инспекторе:
неправильные count/payload, нулевой stride и усечённый следующий frame.
Будущие внутренние заголовки остаются непрозрачными; их count не используется
для создания строк. Для неподтверждённой схемы обе стороны дают одинаковый
DK2N008. Новое предупреждение DK2N048 сообщает об unknown frames и суффиксах;
оно также одинаково в инспекторе и валидаторе и переведено на EN/RU.

Разбор ограничен известными root-signatures: семь editable семейств и четыре
сохраняемых readonly семейства F0/104/10E/FA. Если packed-файл начинается с
readonly семейства, следующие известные editable секции теперь видны загрузчику.
Раньше их мог видеть copy-walker, но `Records()` пропускал такой файл целиком.
Смысл полей readonly семейств этим изменением не объявляется расшифрованным.

Сканирование идёт только по соседним подтверждённым границам. После начала
непрозрачного суффикса поиск похожих заголовков внутри bytes не выполняется.
Неизвестный stride сохраняется одной непрозрачной секцией вместо создания
множества пустых строк. Проверка со 100000 однобайтовых предполагаемых строк
подтвердила это без реального исчерпания памяти. Известные 44/46-строчные
варианты creatures со stride 5449/5537 сохраняют свои prefix fields.

## Конвертация

Для Players, Things, Triggers и Variables теперь отдельно учитывается суффикс
после всех учтённых записей. Если он непустой и сама коллекция подтверждена,
DKM-подготовка сообщает `OpaqueCollectionData` уровня Loss. Используется уже
существующий механизм согласия на потери: отказ не создаёт файл, согласие
публикует DKM вместе с immutable source companion. В нём остаётся исходный
файл целиком, включая хвост. Обычный native SaveCopy не меняет эти bytes.

Это подтверждённая потеря модели, а не предположение о риске: для каждой из
четырёх коллекций проверены save/reopen DKM, полное совпадение source archive
и отсутствие исходного 96-byte суффикса в регенерированной игровой коллекции.
Пустой суффикс не создаёт нового Loss. Неподтверждённый целый заголовок остаётся
блокирующим `UnverifiedCollection` и не превращается в необязательное согласие.
Предупреждение `OpaqueDefinitionData` для definition frames/tails сохранено.

## Доказательства и остаток I04

До изменения первые семь групп дали 5 FAIL / 2 PASS. После подключения общего
разбора они прошли. Отдельно воспроизведено создание 100000 speculative rows
при неизвестном stride; после исправления итоговые восемь групп PASS.
Дополнительно прошли связанные layout, packed-tail, creature/default/placement,
script partition, native→DKM, official bundle и payload-retention группы.
Итоговые числа и хеши находятся в `artifacts/Evidence/NativePackedInspection-20261025/`:
`source-packed-proof.json`, логи с кодами завершения и `delivery.json`.

Проверки реального DKM/level1 сохраняют семь файлов, все 1800 клеток и все 711
payloads событий. Source/Binaries, fixtures и установленные карты не изменялись.
Ни GUI, ни игра, ни Computer Use не запускались. Полного corpus-прогона не было;
исторические 1840 PASS / 63 FAIL не пересчитывались по частичным результатам.

I04 не закрыт. Остались согласование исторических DKM/AREA sections с инспектором,
политика целиком неизвестных native companions и конечная таблица
inspector/load/raw-edit/named-edit/export. Raw fields при известном stride и
named catalogue tools с проверенным count/ID порядком — разные уровни поддержки;
этот этап не ослабляет более строгие проверки named tools. Полная цель и 23
ручные группы остаются открытыми.
