# Object manager: selected removal and display sorting

The EN/RU **Object manager** command is next to batch insertion on the Properties tab. This milestone implements the original selected-object removal and five list sorts. The subsequent [masked modification/group-translation workflow](OBJECT_BATCH_MODIFICATION.md) is implemented separately; this removal milestone's gate counts do not establish its acceptance.

## Source evidence

- `Source/Sources/Things/Things_Manager.c:1214–1312`: `Things_ManagerKill` obtains the actual selected list entries, confirms the count, offers cancellation/keeping scenario-bound entries, removes approved entries below one `UNDO_THINGS` root, and re-sorts the list. A deletion is not a batch-add “skip” decision.
- `Things_Manager.c:488–594`: list-only `LVM_SORTITEMS`, five choices (position/name/owner/ID/type), doors before traps, special items before ordinary objects; position is row-major with equal-coordinate equality, other ties fall back to catalogue offset and signed data.
- `Source/Sources/Things/Things_Functions.c:352–386`: creature catalogue order is BadCreatures → BadElites → Heros; other categories use their own original list; special ordering uses Magics even for version 17. Unknown type offset is zero.
- `Source/Sources/Triggers/Triggers_Functions.c:641–760`: usage checks depend on scope bindings, not arbitrary identity allocation. The original manager calls only `SCOPE_CREATURE|SCOPE_KILL` even for its other families; skipping by nonzero UID subsequently over-skips unbound identities.
- `Source/Sources/Map/Map_Undo.c:411–580`: child deletions remove physical list entries and retain their bytes for undo. They do not traverse/delete an event graph or remove orphan scenario bindings.

## Implemented workflow

Three original families (creatures, doors/traps, ordinary/special objects), plus an all-category view, expose all five categories and all three native creature signatures. Multiple selection, all-visible/none, bilingual name/ID filtering, map-selection bounds and an explicit refresh are available. The five sorts affect **only display order**. Unknown names display their numeric IDs. Sorting compares localized names case-insensitively and retains source catalogue/data tie rules; the invalid one-sided original subtype comparison is repaired with an antisymmetric family rank. This is not a byte-level physical reorder command.

The removal preview uses selected physical file/offset entries, de-duplicates repeated selection and includes an actual scenario count. Scenario-bound objects are kept by default; an explicit include option and group confirmation permit deleting them. Changing selection, filters, policy or document revokes confirmation; document changes revoke the preview and selection. Language changes retain the preview and selected physical entries. Pending generic field edits must commit first and invalidate an older preview. Cancel, replacement windows, document replacement and unloading unsubscribe and revoke callbacks. Sorting/search do not change terrain, canvas selection or the copy buffer.

The Core preview is read-only, immutable and fingerprinted over complete document bytes. Foreign/stale plans and selections that mutate the document during enumeration fail. Empty/fully-skipped work does not emit changes, consume redo or upgrade historical sections. All prepared buffers are committed in one transaction and one history entry. Undo/Redo restore complete bytes, including unaffected records, headers, pointers, padding and native opaque tails.

Project removal deletes only exactly owned nonzero scope+identity bindings (creature 2, door 64, object 128, special 256). It never acquires orphan zero bindings. If a retained same-scope owner shares the identity, removal is refused; explicitly deleting all such owners is supported. Events, aliases and shared/unlinked branches remain byte-for-byte intact. This is a deliberate correction of the source's stale binding/creature-only checks, **not a claim of automatic orphan-graph cleanup**. A nonzero freshly allocated project UID with no binding is not treated as scripted; an empty existing project binding is still a binding. Native nonzero root fields are treated as scripted, including dangling roots, without requiring the target event to be present.

Historical Things versions 1–6 can be removed in their current verified layouts without silently upgrading them. Unknown scenario project layouts disable automatic removal because binding ownership cannot be established. Known physical objects outside map bounds or on borders remain removable; removal is not constrained by insertion terrain rules. Native counts/payload/file size and project Things/Events size/root-count headers are updated while all other bytes are retained.

An additional native compatibility audit found an unsigned-size underflow: the original loaders and modern reader accept understated generic size metadata (including zero), but subtracting deleted record bytes from zero previously threw. Group removal, generic collection deletion and smaller batch replacements now retain the stored-size delta when it is representable; if it would become negative, they write the actual resulting file size. Independent zero/1/55/normal stored-size fixtures retain opaque tails and recover exact original metadata on undo. No-op operations do not repair or rewrite metadata.

## Verification

`ObjectManagerChecks` covers all categories/signatures, script-free allocated identities, actual/shared scopes, empty project bindings, stable display sorts and comparator contracts, signed data, foreign/stale/mutating/duplicate selections, no-op/redo behavior, invalid coordinates, historical versions, ambiguous owners, unknown scenario versions, exact native tails, 1024-entry batches, save/reopen and project native compilation. Each successful real native corpus case now additionally checks all five EN/RU display sorts and removal/undo of up to seven verified entries with exact event/all-file preservation.

Four actual in-process WPF cases (EN/RU × native/project) cover command availability, all source family filters, five sort bindings, bilingual search, map bounds, multi-selection, preview counts, keep/include scenario policy, confirmation invalidation, one-step Undo/Redo, pending real DataGrid commits, external edits, language retention, copy-buffer preservation and closed/replaced-window lifetime. These are offscreen integration tests, not hardware mouse/game acceptance. Rendered EN/RU previews were inspected; minimum column widths/wrapping and explicit content background corrected clipped names/headers.

Focused Core and WPF tests pass in both configurations; Debug and Release builds have zero warnings/errors. After the stored-size fix, full Debug is terminal with **71 groups / zero failures** (`Test/object-manager-size-fixed-debug-20261007.json`, exit 0). Full Release corpus is terminal with **1720 passes / 94 failed checks** (`Test/expanded-corpus-object-manager-size-fixed-20261007.json`, exit 1): 71 synthetic / 560 native / 530 supported-text / 559 original-policy passes. The complete ordered failure array exactly equals the preceding insertion report; this does not make the corpus green. Earlier pre-fix and no-external-map runs remain diagnostic checkpoints; they are not substituted for these final gates. All final test sessions are terminal.
