# Scenario variable/timer naming

Source-derived implementation, 2026-10-07. The [source audit](SCENARIO_NAMES_SOURCE_SCOPE.md) distinguishes editor aliases from game values and defines the exact original reference-count rules. This stage implements the named manager and alias-aware ordinary event-property choices, not the entire original scenario wizard or descriptive formatter.

## Human workflow

The actual Scripts-tab command opens a modeless EN/RU window with all **129 variables and 17 timers**, indexed name/usage lists, raw alias input, explicit Apply, Discard/refresh and Close. Each accepted change is one reversible document edit; unchanged input creates no history. Usage counts follow all physical condition/action records, including unlinked events and repeated operands, rather than an ID-keyed graph. Display-timer references deliberately do not enter the original timer-manager count. Unverified event layouts produce an explicit partial-count notice.

Variable 128 (Score) and timer 16 (Time limit) retain their original fixed display captions without erasing their independently editable stored aliases. Relevant ordinary event-property pickers use names with numeric fallback: variable lists contain 129 choices, timer conditions/display-timer contain 17, and set-timer excludes reserved timer 16. Imported unknown numeric IDs remain selected/editable rather than coerced. Inactive secondary operands do not gain misleading named choices.

Both languages preserve pending input. Document changes and Undo invalidate the draft; Apply commits pending ordinary property edits before reconsidering authority. Document/workspace replacement, replacement-and-restoration, unload and closed-shell lifetimes cannot reuse a draft. Revision plus a complete bounded byte fingerprint also rejects raw changes that bypass notifications; a rejected stale draft disables Apply until refresh. Errors are localized; CP1252/NUL/63-byte limits refuse unrepresentable input rather than transliterating it. Russian UI does not imply that the original Western-ANSI alias format can store Cyrillic names.

## Persistence and compatibility

DKM KTRG versions 2/3 retain the original **146 × 64-byte** table. Current table offsets are resolved after record insertion/removal, not cached. Historical V1 requires explicit existing project upgrade, including exact undo; future layouts remain opaque/read-only. The compiler copies raw slots, including noncanonical padding, into editor metadata rather than normalizing imported bytes.

Native game files have no original alias table. A native editable copy with stored names therefore exports an adjacent **`<map>.kwd.dk2names`** editor companion. Keep this file with the descriptor. Its v1 header is 12 bytes (D2SN signature, version, size), followed by the alias table: **9356 bytes = 12 + 146 × 64** in total. It is not a KWD-linked game collection: aliases do not alter `Files`, game event arguments or game-file validation. Metadata-only edits nevertheless participate in dirty state, the same transaction/rollback/history budget, Undo/Redo and draft fingerprints. Unchanged default-empty native names need no extra file; an already-loaded companion is retained. Unknown bounded companion signatures/versions/layouts export byte-exact and disable naming; a truncated header or oversized input is refused.

This companion solves scenario aliases only. Other native/editor metadata classes remain part of the full parity objective. It neither adds invented game fields nor establishes that original software reads this new editor-specific companion.
