# Thumbnail export: preserved pre-implementation source audit

The subsequent [thumbnail implementation and acceptance record](MAP_THUMBNAILS.md) now covers this workflow. The notes below retain the original audit and decisions; they are not its current implementation status.

The minimap/fullscreen raster is not a complete implementation of the original thumbnail tool. Source inspection establishes these requirements for the remaining workflow:

- `Windows_Thumbnail.c` exposes preview sizes 144 and 96, explicit Refresh, display-options and Save commands. `Thumbnail_GenerateFile` exports the 144 preview as **128 × 128**, while the 96 preview exports **96 × 96**.
- The output is a **24-bit uncompressed bottom-up BMP**, with the original 14-byte file header, 40-byte info header and BGR pixels. These sizes need no row padding beyond their naturally four-byte-aligned widths. Export is not PNG or a screenshot of window chrome.
- `Thumb_DisplayProc` has nine world flags (limit, water, lava, gold, gems, solid, rock, unclaimed, hero rest) and four independently editable categories for each of seven owners (walls/claimed paths, rooms, portals, hearts): 37 display controls total. Closed mana follows neutral-room visibility; hero gates follow hero-portal visibility. Heart/portal colours still come from the original palette.
- `THUMBOPTS` stores hidden COLORREF, optional colour-key compositing, selected owner, two flag words and a bitmap-lifetime option. `Properties_Editor_Config.c` initializes both flag words to all bits set and KeepOldBitmap true. Remaining default colour/key/owner and persistence fields should be checked against configuration load/save before implementation. KeepOldBitmap is a native allocation/lifetime control, not an editable map feature.
- `Thumbnail_CopyBitmap` uses the shared `Config.MinimapKeepProps` preference. It supports stretched square or aspect-retaining placement, with the original 144-pixel background resource **996** (`Bitmaps/Interface/Carte - Fond.bmp`) behind margins and optionally behind hidden-key pixels. The colour key is composited into this background; the saved BMP does not have an alpha channel.
- Changes to display flags/hidden colour regenerate the filtered per-tile bitmap; size/key settings control its compositing. Preview and exported bitmap dimensions are distinct. `Thumb_UpdateWindow` is called on map loading; source edits/refresh semantics and document replacement require explicit lifetime tests.

One preserved-source defect needs a deliberate decision rather than blind copying: the Heroes-heart branch of `Thumbnail_GenerateExt` checks **WorldFlags & TOF_SHOWHEROESHEARTS**, while the actual Heroes-heart checkbox updates **PlayersFlags**. The numeric flag is 0x80, which in WorldFlags means unclaimed terrain. Thus the original renderer couples Heroes hearts to the unclaimed checkbox instead of its own visible heart control. Implement the named heart control's intended effect, retain source evidence and add an independently reproduced regression; do not silently claim complete byte/pixel equivalence to that defect.

The old writer uses CREATE_ALWAYS and deletes a failed output. The modern implementation must preserve the project's no-overwrite rule: publish only a chosen/new output and retain existing user files on failure. Original source/game maps must remain unchanged. Required acceptance includes every flag/owner/category, hidden-colour collisions, both sizes and orientations, source bitmap channels/headers, immutable bytes/history, EN/RU actual controls, stale/closed-document guards, preview-versus-export dimensions, no-overwrite/atomic failure and historical/game acceptance as separate scopes.

This audit itself did not implement a command; the subsequent implementation is documented separately above. See the [parity ledger](FEATURE_PARITY.md) for other remaining editing work.
