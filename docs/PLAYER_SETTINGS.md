## Original evidence

- `Properties_Map_Computer.c`: selecting the profile list changes only `PlayerAI`; button 101 calls `Properties_MapOptionsKeeperAI` to restore the profile's assigned parameters. These are distinct commands in the new tab, not an automatic reset when a combo-box selection changes.
- `Properties_Map_Global.c`, `Properties_MapOptionsKeeperAI`: cases 0–8 each contain 84 assignments, including fifteen room-build priorities. The preserved C source is embedded as the runtime assignment catalogue; all nine branches are validated for unique fields and their own profile number.
- `Texts_Map.c`, `szCfgCPUAI0`–`szCfgCPUAI8`: Master, Conqueror, Psychopath, Stalwart, Wise old man, Idiot, Jailer, Tough guy and Paranoid. English/Russian labels are curated translations, not extracted game-language strings.
- `Properties_Map_Players.c`, `Properties_MapPlayerToDefault`: the real per-player default button calls `Properties_MapOptionsToDefault` for the selected player. The dialog copies the player's row; OK commits it, Cancel does not. Gold beyond treasury capacity is a warning, not a block; no invented treasury-capacity restriction is added here. The treasury summary/warning UI is now implemented; see [map statistics](MAP_STATISTICS.md).
- `Properties_Map_Global.c`, `Properties_MapOptionsToDefault`: first zero the whole MAPOPTIONS, set health 100/gold 3000/control, apply profile 0, set all six camera/build coordinates to -1, then assign names, pools and keeper availability. In particular NPC availability becomes zero on a complete player reset, unlike the optional table reset that deliberately retains NPC availability.
- `Texts_Global.c`: source player names are `Good Player`, `Neutral Player`, `Keeper 1`–`Keeper 5`. New-map construction and text import now use these names rather than the previously invented `Heroes`/`Neutral` stored names. Owner/category labels remain independently translated.
- `Compiler_Generate.c`, `Compiler_GeneratePlayersFile`: 91 project-to-native assignments, CP1252 names, camera/build-area expansion and separately attached player script roots. `PlayerUseCountInFirstAttack` has no verified native compiler assignment and is not written into an unknown byte; the field remains supported in projects.
- `Files_Game.c`, heart gate case `0x0E`: player health comes from `wGateHealth`, with later matching records overwriting earlier ones. It is not a GAMEPLAYER field.

## Operations and compatibility

Changing AI type writes exactly one verified field. Applying profile defaults writes only the assigned AI fields; name, gold, control, health, camera, build bounds, pools, availability, identities and scenario links remain unchanged. Both commands support preflighted multiple-player batches in the core; the tab edits one selected player, matching the original dialog. A profile can configure dormant computer parameters without forcing the control checkbox on.

A confirmed complete player reset restores all known semantic MAPOPTIONS fields in current projects, including CreaturesAvailable zero, exact source pools and availability. Padding is retained rather than treated as editable data. Project camera/build coordinates return to -1. Native reset writes the proven compiler fields/name, expands default build bounds to (2,2)–(width-2,height-2), and resolves camera using the source first-heart/centre rule (NPCs 0,0; no recognized heart 0,0). Native reset never deletes/reorders players or invents a missing heart/player record. Stored native health is editable/resettable only if a matching heart gate exists; only its last matching record changes. Earlier duplicate heart payloads are retained.

Native pools/availability reset through the map-only variable collection, never shared `GlobalVariables.kwd`. Scalar updates preserve earlier duplicates; removing a source-unspecified value removes exact matching map overrides. NPC availability zero is accepted only through this verified full-default operation, not added to the matrix's manual source radio range. Alliances, creature modifiers, global map variables, terrain, objects, scripts and other players are untouched. Every whole-player batch is one byte-snapshot undo operation; errors roll back and unchanged repeats create no history.

Native players are addressed by actual stored ID, not array position. Duplicate/out-of-range identities are read-only in the specialized workflow and fail preflight without editing a preceding valid player. Absent native players are not fabricated. V2 project general/AI fields are usable where verified, but full reset requires explicit upgrade because its camera fields are ignored by the historical reader. V1 shows known source-name/Gold/Health/AI aliases read-only until upgrade; future layouts are not guessed. Missing native map-variable files disable only the full reset, not unrelated general/AI editing. Raw properties remain a separate workflow for repairing imported data.

The specialized native workflow verifies version 4 of its player file; future player versions are read-only. Native health requires a verified version-4 things file, and full reset requires a version-4 map-variable collection. An unverified heart/rule file cannot receive a guessed health/default write; unrelated verified player fields remain usable. These guards do not claim that the older generic raw editor has verified every future native layout.
