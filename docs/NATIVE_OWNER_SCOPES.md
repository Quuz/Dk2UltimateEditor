# Рабочие сценарные точки существ, дверей, предметов и отрядов

16 октября 2026, NativeOwnerScopes-20261016. Это описание текущей реализации;
проверки конкретной поставки перечислены в [CURRENT_STATUS](CURRENT_STATUS.md).
Все23 области исходной задачи и семь очередей [остатка](REMAINING_WORK.md) сохранены.

## Поведение редактора

Для native карты отдельно сохраняются рабочий ID владельца и наличие сценарной
точки. Поддержаны шесть scope: существо2, отряд8, участник16, дверь64,
обычный предмет128 и специальный предмет256. Нулевой указатель события сам
по себе не отличает пустую созданную точку от отсутствующей точки; рабочая
модель хранит это различие. Области4 используют отдельную существующую
[модель областей](USED_AREA_REMOVAL.md); player/level остаются inherent roots.

Удаление через редакторский менеджер предметов, замена предмета при добавлении,
удаление отряда и удаление его участников в родительском окне сохраняют
сценарные точки удалённых владельцев. Исходная Properties_RemoveThings /
Things_RemoveAtMapPosEx при обрезке карты тоже только исключает предмет
из списка: точка и операнды событий остаются. Существующие производные цели
кристалла/ворот пересчитываются по своим правилам. Обрезка не добавляет
отдельного сценарного запроса. Общее поведение REQUEST_TRIGGERS0x100 для
manager remove/modify и region callers объединено в
[SharedScenarioRequests](SHARED_SCENARIO_REQUESTS.md); прямой mouse-safe caller
и остальные маршруты остаются в G.

Точка без владельца отображается как «Удалённый владелец · ID …» и остаётся
в сценарном графе. Её события можно редактировать; Delete Point удаляет саму
точку и её полный допустимый граф. Циклические, разделяемые и висячие ветки
требуют явного исправления. Новое существо или предмет не получает эту
точку автоматически. В отличие от областей с повторно используемым area ID,
уникальный ID такой точки остаётся зарезервированным.

Undo удаления полностью восстанавливает прежние байты, порядок записей,
рабочие ID, точки и прежнюю цель кристалла. Это явно выбранное пользователем
поведение. Исходный append-порядок Undo удаления предметов не воспроизводится.
Решение не изменяет отдельную сверку Undo регионов и ранее согласованный Undo
паузы патруля/параметров сценария. Пустая точка теперь тоже создаётся и удаляется
с Undo; inherent пустые level/player поля по-прежнему не создают таких записей.

Generic ApplyObjectRemoval / ApplyObjectBatchInsertion / RemoveBandMember
сохраняют прежний контракт удаления собственных bindings. Source callers
явно выбирают сохранение точек; это не глобальное ослабление защиты ссылок.
Перенос/дублирование сохраняет ID живых владельцев, а копия получает свой ID
и копию графа. Перестановка участников переносит ID вместе с записью.

## Выбор и перераспределение ID

Свободный ID выделяется при создании точки, а не при обычном размещении
native владельца. Уже выделенный ID без точки остаётся зарезервированным
для generic API; source Delete Point освобождает его. Source Modify сначала
освобождает прежнего владельца, затем выбирает минимальный безопасный ID,
включая повторную перераздачу при сохранении на том же владельце. Если
состояние уже совпадает, Save сохраняет исходный счётчик без нового Undo.

Имеется намеренное отличие от старого allocator: Triggers_GetFreeUniqueID
в Source/Sources/Triggers/Triggers_Functions.c ищет только creature/door/band/
member, пропуская object/magical-object и orphan точки. Современный DKM уже
резервирует все известные ID и точки без владельцев; native модель следует
этому правилу, чтобы новый предмет не получил чужой сценарий. Это не заявлено
как буквальное совпадение исходного allocator. Повреждённые/неоднозначные
импортированные ID не исправляются автоматически; соответствующие choices
отключаются или операция отказывает до изменения карты.

## Формат рабочего состояния

NativeOwnerScopes.cs хранит виртуальный файл `<descriptor>#OwnerScopes`.
Он не входит в игровую коллекцию Files и не создаётся рядом с семью игровыми
файлами. Это часть transaction snapshots, dirty state, fingerprints, независимых
диалоговых копий и native-source ZIP рабочего проекта.

Все числа little-endian. Заголовок16 байт:

| Смещение | Тип | Значение |
| --- | --- | --- |
| 0 | DWORD | 0x534F3244, ASCII D2OS |
| 4 | DWORD | версия1; версия2 допускает живой identity-only trap Scope0 |
| 8 | DWORD | полная длина |
| 12 | DWORD | число строк, максимум1000000 |

Строка36 байт:

| Смещение | Тип | Содержание |
| --- | --- | --- |
| 0 | INT32 | индекс BE-файла в рабочем документе |
| 4 | INT32 | порядковый номер среди всех верхних BE-записей файла |
| 8 | INT32 | -1 для владельца, 0–15 для участника отряда |
| 12 | DWORD | один из шести scope; вv2 Scope0 для trap identity-only |
| 16 | DWORD | уникальный ID |
| 20 | DWORD | band operand / ID родительского отряда |
| 24 | WORD | корневой event ID |
| 26 | WORD | reserved0 |
| 28 | DWORD | явное наличие точки0/1 |
| 32 | DWORD | reserved0 |

Пара File=-1/Ordinal=-1 означает точку без владельца; Present обязателен.
Повторный живой адрес запрещён. Повторные логические ID могут сохраняться
как импортированные данные, но не дают права автоматически выбирать владельца.
Адрес участника включает верхнюю запись GAMEBAND и его индекс. GAMEBANDHERO
не увеличивает ordinal. У NativeAreaScopes ordinal считается только по
GAMEAREA; смешивать эти адресные пространства нельзя.

При удалении любой верхней BE-записи пересчитываются следующие ordinals,
включая удаления областей/ворот/ловушек перед владельцем. Пакетное изменение
учитывает записи, перенесённые в конец файла, и изменение размера. При
компактизации отряда двигаются адреса участников; удалённые точки переходят
в orphan строки. Родительский диалог хранит проверяемое отображение исходных
слотов, сравнивает каноническую реконструкцию и применяет payload+metadata
одной операцией. Cancel не меняет основной документ.

Синхронизация сверяет BE-байты и таблицу по SHA256. Исчезнувший живой адрес без
явного rebasing приводит к отказу, а не к молчаливому назначению другой записи.
На первом чтении native файла ID получают только ненулевые корни поддержанных
владельцев, для участников — активный непрерывный префикс. Неизвестные layouts
и неактивные хвосты не объявляются полностью расшифрованными.

## Сохранение и игровые файлы

Для продолжения работы сохраняйте DKM и его native-source ZIP вместе.
Native→DKM переносит UID, явные пустые и orphan точки в TRIGGERLINK; compiler
восстанавливает рабочую таблицу из проекта. Старый архив без D2OS читается
с первоначальной реконструкцией по ненулевым native корням.

SharedScenarioRequests-20261016: вспомогательный `TRIGGERLINK.band` живого
участника теперь сохраняется буквально через DKM→native→DKM. Изменение
видимого ID/удаление другого отряда не переписывают его автоматически. Явный
Save точки обновляет физический номер отряда; plain game import использует
native parent ID, как исходник. Привязка разрешается по уникальному ID участника.
[Правила, source distinction и проверки](SHARED_SCENARIO_REQUESTS.md).

Игровая компиляция выдаёт ровно семь официальных файлов. В них нет полей для
пустых/orphan редакторских точек и рабочих UID. При повторном открытии только
игрового KWD реконструируются корни, которые сам игровой формат способен
хранить; это не замена рабочему DKM. Поставляемый TestMap и установленные карты
на этом этапе не изменяются. Все ручные игровые проверки используют
DK2Preview_6a88240eaf814f78 через DKII-DX.exe -q -level.

## Проверки и границы

EditorScenarioPointChecks включает шесть семейств × пустую/непустую точку,
сохранение orphan ID, полные game+metadata UndoRedo, DKM/archive/reopen/compiler,
семифайловый экспорт и Delete Point без владельца. Дополнительно проверяются
пакетная перестановка, сдвиг/удаление участников, private parent Cancel/Save,
дублирование, перераспределение ID, source/generic replacement и32 сочетания
native/project × четыре типа предметов × empty/nonempty × boundary/outside crop.
Окна редактора, renderer и игра инструментами не запускаются. Физическая
EN/RU, GUI, hardware/DPI и игровая приёмка остаётся ручной.

## ManagerCategoryScopes-20261016

Source category change сохраняет UID и прежний point scope. Live owner новой
категории без точки и orphan прежней точки могут иметь один UID: это один
physical owner. Trap хранит identity-only Scope0/Root0/Presentfalse в D2OSv2;
v1 по-прежнему читается. UID переносится через DKM/compiler. Явный обратный
переход восстанавливает уникальную old-scope точку; unrelated rewrite или raw
поле не дают права автоматически чинить связи. [Формат и scope](MANAGER_CATEGORY_SCOPES.md).
