# Object manager bulk edit/removal: source audit history

These are chronological audit notes, not current completion claims. Selected removal and five list sorts are implemented in [the object manager](OBJECT_MANAGER_REMOVAL.md). The subsequently implemented [masked modification/group-translation workflow](OBJECT_BATCH_MODIFICATION.md) follows the complete modify/options/preview audit; [batch insertion](OBJECT_BATCH_INSERTION.md) remains a distinct operation. Statements below saying that code still needs reading describe the earlier checkpoints.

Read source so far: `Things_Manager.c` selected parts of `Things_ManagerModify` (1314 onward), `Things_ManagerKill` (1214–1312), and add passes 1–7 to distinguish addition from modification. The remaining modify passes/options/preview implementation must be read before implementing their behavior.

Confirmed requirements from the inspected source:

- Modify uses the actual selected manager entries. Single modification opens its individual property dialog; multiple modification uses a family template plus masks. Filtering scripted entries precedes candidate construction.
- Creature multiple-coordinate mode can use one identical destination or translate the selected group relative to its minimum X/Y. Doors/traps and ordinary/special objects force relative-group mode. This is not independent per-record absolute editing, nor a generic delta applied to the user's destination values.
- Type/ID and owner are separately masked. Owner zero resolves at each new position; out-of-map source logic falls back to neutral, but negative pointer access must not be copied.
- Creature level, held gold and health have separate masks. Hero/creature options can replace all bits or only a specified mask: `(old & ~mask) | (template & mask)`. Objective, area and enemy are applied together.
- Multiple-creature modifications clear hero options/objective/area/enemy on nonhero owners when hero options/objective are nonzero, emitting an incompatibility warning. Hero objective zero becomes 19 with a warning. **Addition does not have this normalization pass**; don't retrofit it into the accepted batch-add serializer.
- Door data supports open 0, locked 1 and blueprint 2; barricades IDs 6/7 cannot retain locked status, and cross-family status conversion has source rules. Trap data converts door blueprint 2 to trap blueprint 0; door locked 1 becomes built 4 with a warning. These are real type-conversion semantics, not generic byte casts alone.
- Object data preserves gold IDs 1–3, validates spell IDs for book 4 and clears unsupported/inactive payload with an incompatibility warning. The remaining special-item cases still need inspection.
- Bulk removal confirms count, checks triggered objects, permits cancellation or keeping triggered entries, and deletes approved selected entries under one undo root. Its preview/remove meaning must not be confused with add-mode skip choices.

Modern integration needs fresh attention: current project entities have allocated unique IDs even when no scenario is bound. Copying the source's `uniqueid != 0` filter would wrongly skip every newly added project entity; use verified actual bindings/roots to express its scripted-entry choice. Preserve stable identities while editing, remap native owner-dependent creature signatures, retain existing graph ownership, and avoid deleting shared event graphs. Source trigger-scope calls need separate auditing across all five families before general cleanup is implemented.

Sorting is a separate read-only list-view feature (`LVM_SORTITEMS` / `Things_ManagerSort`), not evidence of a physical record reorder command. Read its comparator, tie-breaking and all five choices before claiming sorting parity.

Removal/sorting audit update: the complete comparator (488–594), `Things_GetOffsetFromID` (352–386), `Things_ManagerKill` (1214–1312), `Triggers_GetFirstTrigger` / `Triggers_IsUsed` (641–760), and `Undo_StoreEntry` (411–580) have been inspected. Removal has a physical grouped transaction and scoped-binding cleanup retaining all events; sorting is display-only with source catalogue/data ties and a valid antisymmetric family rank. See the dedicated evidence note for deliberate fixes and tests. This does not complete the remaining modify passes/template/options workflow.

Modify pass-8–10/preview follow-up: inspected 1761–2202 and `Things_ManagerPreviewToggle` (3685 onward), plus the complete Manager.h constants. Preview has **Keep / Remove / Modify**, not an add checkbox: locked out-of-map/boundary candidates still permit removal of the source object. Pass 9 removes Keep candidates from the worklist, then re-evaluates overlaps: an object previously assumed to vacate may now remain, so a new preview/confirmation is required before replacing it. This must not be implemented as unconditional deletion of the original selected worklist. Pass 10 handles source removals separately from approved overlap removals; multi-modified objects retain their physical identity but move to the end of the destination family list. The modern implementation must reconcile that ordering with byte-preserving records and atomic no-op behavior, while preserving exact script ownership during owner-dependent native signature and project category conversions. No masked-modification implementation is claimed by this audit.

Subsequently inspected: `Manager.h`, `Things_ManagerModifySave`, the special-item normalization and pass-6/initial pass-7 branches, and comparator lines 499–594. Special data nonzero is cleared with an incompatibility warning. Pass 6 ignores an overlap if its target is itself in the selected worklist; otherwise door-before-trap and ordinary-before-special priorities apply. The source comparator prioritizes door versus trap and special versus ordinary before the chosen sort; position is row-major, name is case-insensitive, owner and ID ascend, and every non-type tie falls back to catalogue offset then signed data. The initial subtype comparisons are asymmetric C returns, so a modern comparator must use an antisymmetric family rank rather than reproduce an invalid comparison contract. The beginning of the comparator, catalogue-offset resolver and remaining modify/preview passes are still required before implementation. No new bulk-edit command is claimed here.
