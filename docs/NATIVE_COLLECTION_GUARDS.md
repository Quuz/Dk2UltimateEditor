# Подтверждённые структуры игровых коллекций

Последующий этап [NativeScriptPartition](NATIVE_SCRIPT_PARTITION.md) исправил указанный ниже D5/D6 дефект: условия вставляются перед actions, private action offsets переносятся, неправильные split-counts/order сохраняются opaque. Описание этого дефекта в конце документа относится к состоянию до последующего этапа.

Состояние на 25 октября 2026, `NativeCollectionGuards-20261025`.
Это следующий участок I04 после [исправления границ вставки](NATIVE_COLLECTION_BOUNDARIES.md).

## Общая политика

Загрузчик, инспектор KWD и редактор используют один `NativeCollectionLayout`.
Внешний формат должен быть version 4. Внутренний заголовок проверяется до чтения
числа записей: info marker, размер info и define marker. Неподтверждённый
внутренний заголовок сохраняется целым непрозрачным файлом; его count не
интерпретируется. Усечённый заголовок или запись при подтверждённой структуре
остаётся ошибкой чтения. Будущая внешняя версия не объявляется поддержанной.

| Коллекция | Signature | Header | Info marker / размер | Define marker | Структуры записей |
|---|---|---|---|---|---|
| Players | B4 | 56 | B5 / 28 | B6 | 205 bytes |
| Things | BE | 56 | BF / 28 | C0 | Таблица ниже |
| Triggers | D2 | 60 | D3 / 32 | D4 | D5 и D6 по 24 bytes |
| Variables | E6 | 56 | E7 / 28 | E8 | 16 bytes, четыре DWORD |

| Things signature | Структура | Bytes |
|---|---|---|
| C2 | GAMEOBJECT | 32 |
| C3 | GAMETRAP | 24 |
| C4 | GAMEDOOR | 28 |
| C5 | GAMEAREA | 64 |
| C6 | GAMENEUTRAL | 32 |
| C7 | GAMEHERO | 40 |
| C8 | GAMEKEEPER | 36 |
| C9 | GAMEBAND | 563, включая 16 слотов по 32 с позиции 51 |
| CB | GAMEEFFECT | 44 |
| CC | GAMEGATE | 28 |

Эти размеры следуют структурам и фиксированным шагам `Files_Game.c`, а не
догадке по числу помещающихся полей. Известный signature с другой длиной и
неизвестный signature Things/Triggers получают категорию `Opaque.NativeCollection`
без редактируемых полей. Например, наблюдавшийся CA/24 сохраняется; исходный
Things-reader попадает для него в `REPORT_BADTHINGHEADER`.

Проверка физической структуры события не подтверждает смысл неизвестного Type.
Его существующая отдельная политика сохраняется: сырые данные доступны в
известной 24-byte структуре, а DKM сообщает блокирующий `UnknownEventType`.
Неизвестные ключи Variables остаются четырьмя DWORD и сохраняют существующие
правила сырого представления и retention.

## Операции и сохранение

Непрозрачный файл или запись сохраняется обычной native-копией побайтно.
Инспектор и валидатор дают одинаковый `DK2N047` с файлом, смещением и длиной;
предупреждение и категория переведены на EN/RU.

Добавление, копирование, удаление и редактирование полей в неподтверждённой
коллекции отклоняются. То же правило проверяется перед публикацией всей
транзакции: специализированное окно, которое пишет известные spans напрямую,
не может обойти запрет. Сверяются прежняя и новая структура, неизменность
категории коллекции и точное сохранение её непрозрачного суффикса. При отказе
восстанавливаются прежние bytes без шага Undo. История разрешённых операций
сохраняет выбранное пользователем полное восстановление.

Выделение, вставка и преобразование выделения, а также resize не делают
предположений о геометрии неизвестной записи. Они требуют подтверждённых native
коллекций. Обычная покраска клеток доступна, когда она не меняет эти файлы.
После смены типа события можно продолжать обращаться к прежней записи по её
физическому месту: защита не требует полного совпадения старого списка полей
с новым списком параметров.

Подготовка DKM возвращает блокирующий `UnverifiedCollection`; весь исходный
комплект остаётся в immutable source snapshot. Непрозрачная запись не попадает
в typed-конвертер под видом частично прочитанного объекта и не исчезает молча.
Текстовый MAP также отказывает для неподтверждённых не-сценарных данных.
Режим `OriginalNoScenarios` может явно исключить неподтверждённую коллекцию
сценариев; режим с поддержанными сценариями её не пропускает.

Размер payload не является признаком неподдержанной структуры. Расхождения,
обнаруженные в 111 из 437 ранее инвентаризированных файлов, по-прежнему
поддерживаются: [вставка идёт по фактическим границам](NATIVE_COLLECTION_BOUNDARIES.md),
неизвестный хвост сохраняется. Установленные файлы не исправлялись.

## Доказательства и оставшийся объём

Первый прогон новых семи групп: 6 FAIL / 1 PASS. После введения layout guards
все семь прошли. Отдельно воспроизведены два обхода — прямое изменение состава
отряда и resize с неизвестной геометрией — и добавлена проверка транзакции.
Итоговый набор содержит девять групп, включая все штатные templates,
24 короткие/расширенные формы Things/Triggers, 12 вариантов внутренних
заголовков, усечение, будущую внешнюю версию, точный raw Save/reopen,
согласованные предупреждения, отказ конвертации и отсутствие побочных изменений.

Логи, коды завершения, сравнение с исходником и хеши поставки находятся в
`artifacts/Evidence/NativeCollectionGuards-20261025/`. Итоговые численные
результаты фиксируются в `source-guard-proof.json` и `delivery.json`.
Смежная проверка исходной политики MAP обнаружила излишне строгую проверку
списка полей после смены типа события; исправлен продуктовый guard, исходная
проверка не переписывалась.

Отказ `Compilation lost the exact owner of scope 2` воспроизведён на прежней
опубликованной DLL и разобран по выводу физических и виртуальных roots.
Это оказалась реальная ошибка восстановления рабочих владельцев: compiler
пишет категории в другом порядке, а `RestoreCompiledNativeOwnerScopes`
сопоставлял их с несортированным source list. Возникали лишние
`Working.OwnerScope` рядом с правильными игровыми roots. Теперь оба маршрута
используют один `CompilerThingOrder`; сами игровые payloads и порядок writer
не менялись. Новая проверка смешанного списка, native→DKM и все девять scopes
проходят. Создание новой связи при глобально неоднозначном UID по-прежнему
отклоняется; это не следует путать с typed retention уже импортированных связей.

Первый дополнительный fixture не задавал специальный ID для magical object;
он исправлен по уже существующему каноническому fixture. Отдельное ошибочное
ожидание новой связи при общем UID заменено проверкой существующей политики
отказа. Исправленный положительный fixture воспроизвёл ошибку на прежней DLL
до итогового успешного запуска; промежуточные FAIL не скрыты.

Два старых отказа также классифицированы и устранены в тестах. Полное сравнение
native template payloads теперь учитывает исходный порядок пяти списков
`Compiler_GenerateThingsFile`, вместо сравнения с несортированной историей
вставки. Валидный scenario fixture теперь содержит hero/neutral player slots
1 и 2: до этого общий validator правильно давал DK2N035/036, а тест ошибочно
считал их ошибками сценария. Само условие отсутствия semantic warnings не
ослаблено; диагностический вывод сохранён. Обе группы проходят.

I04 ещё открыт: инспекция packed definitions, поддержанные исторические секции
и итоговая таблица inspector/load/edit/export. Следующий конкретный дефект:
native `InsertRecord` добавляет событие в конец, тогда как исходный
`Game_ExtractTriggers` требует сначала D5 conditions, затем D6 actions.
Нужно вставлять новое условие перед actions и переносить соответствующие
рабочие привязки; одного пересчёта общего payload недостаточно. Это ещё не
исправлено данным этапом. Полного corpus-прогона, GUI, игры,
аудио и Computer Use не было. Цель целиком не завершена.
