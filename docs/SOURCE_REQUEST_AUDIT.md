## Ошибки Undo: точное исходное поведение

Undo_PrintError (Map_Undo.c) — сообщение, а не разрешение операции. Оно
использует REQUEST_UNDOERROR0x8, OK, default1, error icon, follow-mouse и
MBF_AUTOREPLY. Возврат не используется как veto. Современная транзакция уже
сохраняет полный rollback при подготовительных сбоях; это не означает, что
manager recovery UI уже реализован. Само informational сообщение0x8
добавлено в HistoryMemoryNotice.

Things_Manager.c содержит семь активных REQUEST_MNGRUNDOERR calls: пять в
modify/remove-пакете и два в add/replace-пакете. Показаны Continue, Cancel,
Cancel all (исходное Continuer|Annuler|Tout annuler). Реальные ответы1/2/0:
Misc_Requests.c переводит последний из нескольких buttons в0, Close тоже0.
1 продолжает,2 прекращает цикл с уже сделанными изменениями,0 вызывает
Undo_Restore и прекращает цикл. Запоминание действует только для default1.
Поэтому выводить return codes только из номеров надписей нельзя.

Важная исходная аварийная ветка: Undo_CreateNewChild(&Undo,TRUE,...) при
ошибке выделения уничтожает текущего родителя и обнуляет его указатель.
После этого ответ0 в manager вызывает Undo_Restore(), который выбирает
последний сохранившийся entry общего UndoList. При наличии предыдущего шага
это может быть он, а не уничтоженный текущий пакет. Это вывод из конкретной
цепочки кода, не результат физического запуска исходного EXE. Буквально
переносить такую потерю границы пакета нельзя считать корректным recovery.

Текущие HistoryFailureAtomicity checks показывают противоположную безопасную
границу современной транзакции: подготовительный отказ сохраняет прежние
Undo/Redo, bytes/counters, а pen закрывает неуспешный frame. Согласованные
пользователем полный Undo предметов и Undo параметров/паузы не менялись.
Выбор между сохранением полного rollback и добавлением source вариантов
продолжения задан пользователю отдельно; ответа на момент этой сверки нет.
Вопрос не о разрешении запуска редактора; GUI не запускать.

## Остальные новые уточнения

Генератор: RectEx_GenerateGates спрашивает при сумме existing+needed>=256
для areas/gates, а при допустимом количестве показывает counts и Yes/No.
Современные PlanHeroGateGeneration/PreviewRegionGateGeneration и сами
действия существуют, но workspace GeneratorConfirmed и дочерний confirm
checkbox тогда не реализовывали request bits0x4000/0x8000; теперь заменены
маршрутами GateGenerationRequests с default-only remember/reset.
Валидаторы импортированных/зарезервированных ID при добавлении запросов
нельзя обходить ради подтверждения пользователя.

Копирование: исходный Config.RequestsFlags обнуляется при новом процессе.
На момент исходного аудита ApproveBufferReplacement при remembered Yes устанавливал
ConfirmCopyBufferReplacement=false; MainWindow.SaveSettings записывает этот
же bool в AppSettings. Следующий процесс наследовал ответ. Это исправлено в CopyConfirmationLifetime. В современном меню
есть отдельная полезная постоянная настройка, поэтому R05 требует разделить
две причины отключения, сохранив явный пользовательский выбор в меню.
